# 客户端编译发行手册（魔法裁判）

> 目的：把「发一个新版客户端」一次做完，不再重复排查环境。
> 适用：本机这份仓库副本（`C:\Users\Nahida\Documents\ievil JIO sent-ky`）；换机器只需替换路径。
> 事实来源：2026-09-27 发布 1.0.13 时的实测记录。规则层面的约束见根目录 `AGENTS.md`。

## 2. 发版七步

### 2.1 找上一个发版点（决定更新日志范围）

```powershell
git log --oneline -- client/lib/src/client_version.dart client/pubspec.yaml
```

第一条是当前版本，**第二条就是上一版**（最近一次改版本号的提交）。本次范围即 `git log <上一版提交>..HEAD`。
再按文件过滤，只留客户端相关：

```powershell
git log --name-only --format="### %h %s" <上一版提交>..HEAD
```

### 2.2 改版本号（两处，必须同步；`+N` 不动）

- `client/lib/src/client_version.dart`：`const kClientVersion = '1.0.13';`
- `client/pubspec.yaml`：`version: 1.0.13+1` → 只改三段版本名，**`+1` 保持原样**

`+N` 是 build 号，Gradle 通过 `flutter.versionCode` 把它当安卓 `versionCode`（现在恒为 1，按约定不动）；
`x.y.z` 是后端比对与客户端 UA 用的版本名，必须是三段数字。

### 2.3 写更新日志（两个平台各一份）

改 `data/updates.json` 里两个条目的 `title` 与 `notes`：

- 范围：上一版以来**只看涉及 `client/`（含 Windows 更新器）的改动**；纯后端、文档、发布脚本的提交不进客户端日志。
- 分组顺序：新功能 → 修复 → 其它；写用户能读懂的话，不抄提交信息。
- `title` 里的版本号同步改成新版本，`notes` 首行 H1 也要改。
- 发布脚本会**保留**手工写的 `title` / `notes` / `minimum` / `guide_url` 与更窄区间条目，只刷新兜底区间的 `latest` / `url` / `size` / `sha256`（逻辑在 `tools/update_manifest.py`）。
- `data/` 已 gitignore，改它不会进提交，但它是部署机上的真配置；日志写错版本或照抄上一版是事故。

### 2.4 编译（两个平台串行跑，别并发）

```powershell
cd "C:\Users\Nahida\Documents\ievil JIO sent-ky\client"
C:\src\flutter\bin\flutter.bat build apk --release --target-platform android-arm64
C:\src\flutter\bin\flutter.bat build windows --release
```

- 不要两个一起跑：共用 `client\build\` 与 `client\.dart_tool`，会互相踩。
- 实测耗时：APK 约 7 分钟（Gradle `assembleRelease` 428s）、Windows 约 3 分钟（189s）；首次或依赖变动更久。
- `flutter pub get` 会自动执行，不用单独跑。
- Windows 这一步同时构建 `Updater.exe`（CMake 从 `client/pubspec.yaml` 注入 `UPDATER_VERSION_STRING`，不用手改）。
- 长任务建议后台跑并留有日志，别在一条命令里 `Out-String` 后再看进度（会整段缓冲，中途看不到输出）。

### 2.5 发布

```powershell
cd "C:\Users\Nahida\Documents\ievil JIO sent-ky"
cmd /c package-release.cmd
```

一次做完：打 zip → 上传 3 个对象（键带版本号）→ 回读校验 → 刷新 `data/downloads.json` 与 `data/updates.json`。

常用开关：`--dry-run`（只打包、不联网、不改配置）、`--skip-zip`、`--skip-upload`、`--no-updater`、`--no-downloads`、`--no-updates`。
上传期间不要动 `Release\` 目录：脚本比对打包前后的文件指纹，发现变化就拒绝出包（防止打进新旧混合的半成品）。

### 2.6 核对（脚本已做大部分，这里是判据）

- APK 版本：`client\build\app\outputs\apk\release\output-metadata.json` 的 `versionName` 等于新版本、`versionCode` 仍为 1。
- 三条对外地址：脚本已用真实 GET 取 1 字节比对总长度（只看 HEAD 看不出 CDN 缓存）。长度不符直接判失败；顺带看 `cf-cache-status`，`HIT` 却长度不符说明键被旧对象占住了。
- 部署接口（后端现读 `data/`，改完**不用重启**）：

```powershell
curl.exe -H "User-Agent: seven-double-flutter/1.0.12 (windows)" http://127.0.0.1:8000/api/health
curl.exe -H "User-Agent: seven-double-flutter/1.0.12 (android)" http://127.0.0.1:8000/api/health
curl.exe -H "User-Agent: magicjudge-updater/1.0.13 (windows)" http://127.0.0.1:8000/api/health
curl.exe http://127.0.0.1:8000/api/downloads
```

  - 旧版本 UA：`client_latest` 是新版本，且带 `update`（是否 `required` 看 `minimum`）。
  - 新版本 UA：`client_latest` 是新版本、**没有** `update`。
  - 更新器 UA（第三条，把版本号换成刚发布的版本）：**一定要有 `update`**，`update.url` / `update.updater_url` / `size` / `sha256` 都是新版的——它按当前发布版取包、不做版本比较，这一条最能提前发现「更新器报 update.url 为空」。
  - 不带 UA 或 UA 形状不对时后端一律不下发平台更新信息，这是设计，不是故障。
  - `/api/downloads` 三条链接应指向 `S3_PUBLIC_BASE` 且版本号是新的。

### 2.7 提交并推送

```powershell
git add client/lib/src/client_version.dart client/pubspec.yaml
git commit -m "版本 x.y.z：内置版本号与 pubspec 同步"
git push
```

只 `git add` 这两个文件：仓库里经常有别人未提交的后端/文档改动，别用 `git add -A` 把它们卷进来。

## 3. 环境相关的坑（本次实际踩到）

1. **`flutter` 不在 PATH**：pwsh 与 cmd 都找不到，必须 `C:\src\flutter\bin\flutter.bat` 全路径调用。
2. **改 `client/pubspec.yaml` 报 `ReplaceFileW EIO (Win32 1175)`**：VS Code / Dart 分析器占着这个文件。**重试一次即可**（本次第二次就成功）；持续失败就关掉占用的编辑器进程。
3. **PowerShell `Select-String` 读 `AGENTS.md` 匹配不到中文**（编码失配，返回空结果，容易误判成「文件里没有」）：用 DSH 的 grep / read 工具，或 `Get-Content -Encoding utf8`。
4. **控制台中文乱码**（`ħ������ 1.0.13`）只是码页显示问题，文件本身是 UTF-8。校验 JSON 用 `.venv\Scripts\python.exe -X utf8`，别照抄乱码去判断内容。
5. **`Release\` 里的上一版 `魔法裁判Windows.zip` 是正常的**：脚本会先把它排除在打包文件清单外再重新打包，日志里的「跳过发行目录里已有的压缩包」不是错误。
6. **对象键必须带版本号**（`releases/app-release-1.0.13.apk` 这样）：自定义域会把同名对象缓存在边缘且忽略 query，复用同一个键会让客户端和更新器下到上一版的旧包。`Updater.exe` 内容变了也要发新版本号。
7. **`data/updates.json` 每次请求现读**，刷新后 `/api/health` 立刻生效、不用重启后端：版本标签的唯一来源就是它，后端不再读 `GAME_CLIENT_LATEST` / `GAME_CLIENT_MINIMUM` 之类的版本环境变量（留着旧值只会和清单里的新版本号打架）。
8. `/api/health` 的版本下发与「是否拒绝入局」都只看 UA 里的版本号；UA 缺失一律放行（浏览器、模拟器、检查脚本都不发这个 UA）。

## 4. 上传速度（S3 / Cloudflare R2）

**结论：分片参数已经到顶，别再调大小或并发；1.0.13 那次 293.8s 是「一条连接卡住」，已改成 30s 无进展就换连接重传。**

### 实测（2026-09-27，本机上行）

| 配置 | 文件 | 总耗时 | 聚合速度 |
| --- | --- | --- | --- |
| **8MB × 6（现用）** | Windows zip 43.9MB | **15.3s** | **2.9 MB/s** |
| 5MB × 12 | Windows zip 43.9MB | 18.4s | 2.4 MB/s |
| **8MB × 6（现用）** | APK 51.4MB | **16.9s** | **3.0 MB/s** |
| 5MB × 12 | APK 51.4MB | 18.5s | 2.8 MB/s |

- 单片 8MB 实测 6-17s（约 0.5-1.6 MB/s），6 路并发的聚合速度稳定在 ~3 MB/s —— 这就是本机上行上限（约 24 Mbit/s）。
- 把片拆小、并发加大**只会更慢**（每片被摊薄、请求数变多），不用再试。
- 三个对象串行上传、总量约 96MB，正常一次发布的上传耗时约 35-40s。

### 1.0.13 那次 293.8s 的成因与修复

- 现象：43.9MB 的 zip 上传 293.8s（聚合 153 KB/s），紧随其后的 APK 只用 19.1s（2.7 MB/s）；同一个 zip 事后重传只要 15.3s。
- 成因：分片 PUT 当时跟其它请求共用 `S3_TIMEOUT`（默认 300s），一条连接卡住就得干等到 300s 才重传。
- 修复：分片 PUT 改用独立的 `S3_PART_TIMEOUT`（默认 30s），30s 没有进展就换连接重传该片；日志同时打印总用时、聚合速度与最慢一片，整体明显慢于基线时给一句提示。
- 验证超时机制：临时 `set S3_PART_TIMEOUT=1` 跑一次上传，能看到 `The write operation timed out` 与逐次重试（正常上传请用默认值）。
- 回归检查：`checks/test_package_release.py` 固定住「分片超时必须短于 `S3_TIMEOUT`，且能被 `S3_PART_TIMEOUT` 覆盖」。

### 还能更快吗

只有两条路：换上行更大的机器/线路，或减少要传的字节（zip 已经是 `compresslevel=9`，没有空间）。
`--skip-upload` 只在「对象都在远端、只想刷新配置」时有用；整次重跑发布会重传全部对象。
