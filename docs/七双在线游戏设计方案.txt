七双在线游戏设计方案

一、目标与设计边界

本方案用于制作“魔法裁判·七双”在线游戏，玩法以《七双模式游戏介绍与完整规则.txt》及之后确认的规则为依据。七名玩家各持两张角色牌，一名固定主持人管理对局。确定的规则由程序执行，没有明确规定的情况交给主持人裁决，不再以补齐全部自动裁决规则为开工前提。

本文记录产品、交互及已实现的软件结构，并提供启动说明。前后端应用、角色图片及回归检查均已落地；不沿用 docs/old 中已被后续回复推翻的要求。实际验证范围见第十二节。

本次落实的要求：
- 后端 Python + FastAPI，业务按职责分模块，不使用微服务或通用规则引擎。
- 前端使用 Node.js 工具链，实现手机和电脑浏览器共用的网页；另有 Flutter 原生 Android / Windows 客户端，共用同一套后端协议。
- 玩家用 QQ 群验证登录；账号与对局参与身份分离，长令牌保存在独立鉴权数据库。
- 新对局暂不可加入；主持人“开放加入”后，已登录账号自行选择加入或观战，无需审核。
- 玩家掉线后通知本局所有人，包括主持人、玩家和观战者。
- 聊天区分公屏与私信，各自独立列表、已读游标与生命周期；私信有邀请、同意、拒绝、结束。
- 不设计反作弊、设备指纹、IP封禁、行为风控、举报审核、竞技排名等系统。
- 保留正常身份验证、房间权限、输入校验和私密信息隔离；这些是游戏正常运行的要求，不是反作弊功能。

首发运行范围：一个服务实例供一名主持人管理一局七双；结束后可新建下一局。保留观战和替补入口。不做13人模式、公开匹配大厅、多个并行对局、语音聊天或独立成就系统。规则提到的“本局禁用成就”只保留局内标记。

二、技术方案与模块边界

1. 技术选择

后端：FastAPI + Uvicorn；Pydantic 校验传输输入；JSON兼容字典保存领域状态，标准库 sqlite3 保存本地数据，secrets 生成登录挑战、令牌与随机洗牌种子，random.SystemRandom 处理游戏内洗牌与已注明概率的效果。
前端网页：Node.js + npm + Vite + React + TypeScript；CSS Grid/Flex 实现响应布局；使用浏览器原生 fetch、WebSocket、Canvas。无需 Next.js、SSR、Redux、Socket.IO 或大型组件库。
原生客户端：Flutter + Material 3，仅依赖 flutter_secure_storage 与 shared_preferences；使用 Dart 自带的 HTTP、WebSocket 与 JSON，不引入状态框架、路由框架或动态 UI 包。
存储：两个 SQLite 文件。对局库保存对局数据，鉴权库保存账号与登录令牌。无需 PostgreSQL、Redis、消息队列或 ORM。
部署：前端构建后由 FastAPI 同源提供网页、API 和图片；Node.js 用于前端开发与构建，不再另设一套 Node 游戏后端。Uvicorn 首发只运行一个 worker；QQ 登录另有一个独立的 NapCat 网关进程。
已在 Python 3.14.3、Node.js v24.13.0 环境安装依赖并完成生产构建；源码使用Python 3.14语法，Node.js最低要求22.12.0。依赖分别记录在 backend/requirements.txt、gateway/requirements.txt、requirements-dev.txt 与 frontend/package-lock.json。

依赖方向：页面 → API/实时连接 → FastAPI路由 → 领域函数 → 状态结果；存储和消息推送在领域函数之外完成。
领域模块不得导入 FastAPI、WebSocket 或浏览器类型；实时连接模块不得判断角色技能；前端不得自行判定命中、死亡、魔女化或胜利。角色规则只维护一份，由后端提供目录给前端显示。

不为每个角色建立继承体系，不引入插件注册框架或抽象仓储。按白天、夜晚、触发效果分组的普通函数足够；模块拆分用于隔离职责，而不是增加转发层。

三、身份、登录与生命周期

1. 登录入口

网页首页提供“QQ 登录”和“主持人登录”两个入口；原生客户端在玩家页提供 QQ 登录，在主持人页输入同一固定密码。
QQ 登录沿用已运行的 NapCat OneBot 流程：客户端或网页调用 POST /api/auth/challenges（原生为 /api/native/auth/challenges）取得六位挑战码，用户在指定 QQ 群发送“活动登录 123456”，网关用 X-Gateway-Token 调用 POST /api/internal/qq/login 绑定 QQ 号、群昵称与头像。挑战码一次性消费，过期或重放一律拒绝；网关共享密钥用 secrets.compare_digest 校验，真实密钥只从环境变量读取，不写入客户端资源或仓库。登录页始终给出整句“活动登录 123456”：原生客户端提供一键复制到剪切板，网页把同一整句放在可全选的只读输入框里，玩家不必自己补上“活动登录”前缀或手抄六位码。
挑战完成后，网页换成 HttpOnly、SameSite=Lax Cookie（HTTPS 部署时启用 Secure），原生客户端取得 Bearer 长令牌并由 flutter_secure_storage 持久保存；两者查同一张 login_tokens 表，共用账号、过期与撤销语义。客户端启动时调用 /api/me 核对，只有 401 才清除本地令牌。玩家退出只撤销当前令牌，不删除账号。
网关对失败的登录尝试一律在玩家发言的那个群里回一句，不让群里只有沉默：绑定被拒时把后端 HTTPException 的原因转述成「某某，登录失败：登录码无效、过期或已经使用」这类文案（后端不可达则回「服务端暂时不可用」）；「活动登录」写了但码不是 6 位数字时回格式提示。回复只发回来源群，多群同时监听时不会串群；非登录内容的群消息保持不回应。

2. 账号、参与身份与开放参局

账号（accounts）与对局参与身份（participants）分离：账号记录 QQ 号、群昵称与头像，长期有效；参与身份属于单局，记录玩家或观战、席位、禁言与本局拉黑状态，通过 account_id 关联账号。
新对局建立时为不可加入状态。主持人管理动作 room.open_join（短名“开放加入”）宣布对局可用并产生全体系统消息；已登录账号通过 GET /api/lobby 看到当前开放对局，用 POST /api/games/{game_id}/participations 选择 player 或 spectator，无需主持人审核。
选择玩家时，仅在首次发牌前随机占用空席；七席已满或已发牌则拒绝并保留“观战”选择。选择观战不占席位。以 (game_id, account_id) 唯一约束保证同一账号不能重复加入或重抽席位。
替换旧的统一邀请码：不再有邀请码 /join 与客户端邀请码文案。入场靠主持人「开放加入」+ 账号主动参局，或对局内非观战身份从「在线玩家」名单向某个在线账号发定向邀请（受邀者仍须等开放加入后才能接受入席，可拒绝；同一局同一账号只保留一条待处理邀请，10 分钟未响应即失效）。刷新、换设备登录和重连都按 QQ 账号恢复原参与身份，不重新分席或重发牌。

创建一局时：
- 主持人确认本局11名魔典角色，系统随机排列；没有明确的魔典名单不由程序臆测。
- 系统先建立7个空席，不在创建时发放角色牌。
- 七名玩家各自主动加入后随机入席。七名玩家首次全部准备后，系统一次性随机分配14张牌到7个席位，每席2张，确保可可与雪莉、米莉亚与希罗不在同一席位，且艾玛、米莉亚、亚里沙三张牌分别落在三个不同席位的下层。发牌同时生成魔女阵营：随机选定两个不同席位作为 A、B，且不选艾玛席与另一张牌是米莉亚/亚里沙的席位；私下告知这两人「你是魔女阵营」（第1天 A 当值、第2天 B 当值），并常驻“我的”页状态卡。
- 发牌后玩家只能看到自己的两张牌，私下选择上下顺序并再次准备；主持人确认七席都完成第二次准备后才能开局。
- 两轮准备和排序期间，公开席位与聊天均不显示角色头像；玩家自己的牌和明确授权给主持人的信息仍按权限可见。

发牌后凭证丢失或玩家被移出时，由主持人让观战者接管空席；接管不重抽角色，也不重置技能次数与既有裁定状态。角色牌、技能次数和既有裁定状态不因换操作者而重置。

对局数据只保留到下一局建立为止：主持人建立新对局或点击「一键初始化」时，清空对局库中的参与身份、进度、聊天与证物；QQ 账号、玩家登录令牌和主持人登录都保留，下一局重新开放加入即可参局。账号与令牌保存在独立的 auth.sqlite3，不受清空对局影响。

3. 观战与替补

观战账号不占7个玩家席位，不获得角色牌，也拿不到玩家或主持人的游戏行动。观战取得与主持人相近的只读牌桌：能看到全席双牌、生死、状态、阶段和结果，但不返回玩家/主持人行动、主持人待办、参与者管理或席位代操作；所有游戏命令、证物提交和管理请求都在服务端拒绝。
观战的全牌面视角不扩展私信与证物授权：公屏发言与私信仍按普通非主持人成员的频道权限开放，观战不能读取未加入频道的历史、实时消息或附件。
替补由主持人从观战者中选择，并指定一个待接管席位。操作前展示将继承的牌、状态、剩余次数、已提交行动和可见历史，由主持人确认私密信息范围。
接管不重抽角色、不重置技能；是否保留已提交行动、是否继承原操作者私密历史都由主持人确认。原玩家对该席位的参与身份失效，新的操作者接管原席位。公开通知只说明某席位更换操作者，不公开双牌或私密信息。
本局拉黑只让该账号在本局的参与身份失效，不删除其全局 QQ 登录，也不影响其在下一局重新加入；踢人同理。不使用IP或设备指纹。

4. 掉线全局通知

“全局”指本局全体在线成员，而不是其他对局或所有访问网站的人。
每个参与身份记录在线连接数；同一人开两个标签页，关闭其中一个不算掉线。最后一条连接正常关闭或心跳判定断开后，状态变为离线，只广播一次“3号玩家【公开称呼】已掉线”。
应用心跳建议每20秒一次，连续60秒未收到响应判定连接失效；正常关闭可立即识别。恢复连接后广播一次“已重新连接”，并重新下发当前获准查看的状态。
掉线不是死亡、弃票、投降或技能放弃，不自动结算。主持人可以等候、按规则警告并在30秒后结束该行动，或邀请替补。状态与已确认行动不因网络断开丢失。
不设计房主转移、选举或自动换主持人；固定主持人的身份和权限不会因浏览器刷新改变。

账号级在线名单与掉线通知分开：大厅里没有 WebSocket 的账号靠定时轮询 /api/lobby、/api/online 续期，对局内连接由 pong 续期，最近 60 秒内有活动即视为在线（realtime.presence）。这份名单只用于大厅与「状态」页展示和定向邀请，不参与任何规则判定；不展示 QQ 号或令牌。
Android 玩家端收到新的定向对局邀请时额外发一条系统通知（通知栏“收到对局邀请：某某邀请你加入对局”），因为大厅轮询在应用切到后台时用户看不到界面横幅。判定沿用同一次 /api/lobby 轮询：客户端比较这次与上次的邀请 id 集合，首次刷新只记基线，登录后已堆着的旧邀请不重复提醒；同一账号只保留一条通知，点开进入应用。通知走已有的原生 MethodChannel（与保活同一个通道），Android 之外的平台是空操作，不引入本地通知插件；用户名与通知权限由系统设置决定，用户关闭通知不影响大厅里的邀请本身。

四、玩家页面与聊天

1. 页面清单

入口页：游戏名称、简短玩法、邀请码输入、主持人登录。
候场页：7个席位与准备情况、自己的双角色卡、上下交换按钮、公开称呼、准备按钮；穗乃香另可在开局前私下记录一次示人角色。公开头像由上层牌决定，玩家不能自行指定。准备进度只公布已准备人数，玩家看不到具体谁已准备（会发现上层牌锁定时机）；主持人仍看得到每个席位的准备状态；穗乃香在排序阶段能看到已准备玩家的上层角色名（仅文字，不带头像）。
玩家桌面：顶部日夜与阶段，中部公开席位/聊天，自己的角色与私密信息，当前可操作的行动面板。
主持人桌面：相同公开桌面，加全量角色状态、所有行动、裁决待办、魔典、13水、投票、阶段推进、替补管理。
结算页：获胜方、特殊胜负、主持人裁定说明；是否公开全部身份和历史由主持人决定，不默认披露全部私聊。

2. 头像与身份不混用

登录席位、真实角色牌、公开示人身份是三个不同概念。
自己的角色卡和主持人私密面板使用真实角色头像。公开聊天只使用已公开或依规则示人的角色头像；不因为后台换牌、魔女化或下层仍隐藏，就自动向其他人换成真实头像。
尚无公开角色时使用中性的座位号头像，不借某张角色图暗示其真实身份。公开头像始终等于该席当前上层牌的角色：开局时由上层牌决定，下层登场或复活后随当前角色更新，主持人可在席位视图中核对同一结果。穗乃香只能在自己于上层时示人一次，之后公开头像使用被示人角色的图，但这不授予其真实技能；系统不向全场广播“某号示人为某角色”，该记录与开局前的私下选择都只给主持人。主持人始终使用 img/月代雪.png。
旧聊天消息保存当时的公开称呼和头像；换牌或回溯不把旧消息重新渲染成现在的秘密身份。

3. 聊天交互

他人消息：左侧头像 + 公开称呼/座位号 + 左对齐气泡。
自己消息：右对齐气泡，可显示自己的公开头像。
主持人公告、阶段变化、掉线/重连通知：居中系统消息，不伪装成玩家发言。
公屏与私信分开：公屏讨论、私信频道、系统与私密信息各自独立列表和已读游标，不再把所有可见消息混成一条时间线。网页消息页顶部提供“全部 / 公屏 / 私信 / 系统 / 主持人”筛选；原生客户端在消息页顶部提供同样的分段筛选。GET /api/games/{game_id}/messages 增加封闭 scope 查询参数，先按频道权限过滤再分页，因此筛选历史不是只过滤本机最近一页。
“主持人”筛选指包含主持人的私信频道，不是旧版单人主持频道的残留；旧的 host:<参与身份> 频道已随邀请码入口一并删除。

私信频道的生命周期：
- 玩家或观战可以创建一对一或多人私信，创建表单从本局有效参与身份和主持人中多选邀请对象并填写频道名，不经过主持人审核。
- 频道保存 creator_id、status（pending/active/ended）、邀请名单、已同意名单和结束时间。同一非主持人账号同时至多参加一个 active 私信，主持人不受此限制。
- 非主持人发起时，受邀非主持人成员逐人看到“同意 / 拒绝”；主持人被邀请时自动同意。全部受邀成员同意后频道才 active；任一成员拒绝则本次创建取消，且不锁定任何人。
- 主持人发起的频道立即 active，受邀成员无需确认。邀请响应、创建与结束都走服务端动作描述并携带 expected_version。
- 私信 active 后由服务器强制其中非主持人成员只能在该频道发言，并拒绝公屏消息；玩家成员的全部游戏行动也被拒绝。行动区只保留“结束私信”。主持人仍可在任意频道发言、执行行动和管理。
- 任一成员点击“结束私信”即结束整个频道，解除所有非主持人成员限制；断线、刷新或换设备都不能绕过限制。频道转为 active 时向全体发送“甲正在与乙、丙私信”，结束时发送“甲与乙、丙已结束私信”，多人名单使用创建时的公开称呼，不泄露私信内容。
- 频道内消息只给成员与主持人查看，结束后只读保留；替补默认不继承旧操作者的私信历史，除主持人明确勾选继承。
- 已结束的私信不再出现在客户端的频道选择列表里（选中的频道结束瞬间回落到公屏），历史消息仍留在消息流中可回看。
- 天黑进入夜间时服务器结束全部私信频道（含只与主持人的私聊）并公告“天黑，全部私信频道已结束；夜间只能与主持人私聊”；夜间只允许与主持人建立私聊，玩家邀请其他参与者会被服务端拒绝（战斗/邀请表单里只剩主持人一个选项），主持人的邀请对象不受限制。旧数据或异常路径遗留的不含主持人的 active 频道在夜间既不能发言，也不算作“私信占用”，因此不会锁住玩家的夜间行动。

views.channels_for() 同时返回频道状态、邀请状态、成员摘要、can_send 与服务端 reason；send_message()、命令分发、历史分页、实时推送与附件读取共用同一套成员检查和私信锁定检查，不能只靠前端禁用按钮。

发送目标有：公聊、本局的私信频道，以及只发给你的系统与私密信息通道；不因为属于魔女就默认获得规则未写出的魔女群聊。发给单个或多个玩家的裁定、线索、私密提示走系统信息通道，只有获准接收者与主持人看得到，刷新或重连后可随时回看。
主持人可查看全部游戏频道。玩家只能接收允许自己查看的消息；观战只见公开频道和获邀私信，但没有任何游戏行动。规则限制发言时输入区说明原因并禁用发送，但输入框始终可写：草稿按对局、身份与频道隔离保存在本机，刷新后恢复，提交成功才清除；登出或离开对局时把该账号本机残留的草稿与已读游标一并清除，不在本机永久留存私密内容；不保存密码、QQ 登录码或令牌副本。不靠颜色表达状态。

允许复制粘贴普通文本，不提供回复引用、跳转到来源消息、来源认证徽标或跨频道原消息卡片。粘贴内容一律是发送者自己的一条文字气泡，不带可验证的来源。玩家当然仍可自行转述真假信息。
不提供防截图、防复制、语音、录屏检测或外部聊天监控。文本按文本渲染，不执行HTML；消息长度上限建议2000字，属于正常输入边界。

桌面 Enter 发送、Shift+Enter 换行；手机用明确的发送按钮。发送后清空输入只发生在收到成功确认时；失败保留草稿，不自动重发成多条消息。
新消息到达时自动切到对话记录（自己发出的消息、在线/掉线通知除外；首次进入不跳转；手机上正开着行动窗口填写时也不跳转，只进记录与悬浮提醒，关掉行动窗口后恢复自动跳转）。两类消息另外以悬浮提醒弹出、可逐条关闭或点开跳到记录：发给你的裁定与私密信息，以及标记为关键的系统公告（技能声明、出局与复活、质疑结果、处决与投票结果、临死开枪、警告超时、主持人代操作）。阶段推进、警告发出、提名记录等常规通知仍只出现在记录里，避免刷屏。
聊天按需加载较早记录，新增消息不在用户向上阅读时强制拉到底部；显示“新消息”入口。

4. 手机与电脑布局

桌面宽度 ≥1024px：三栏，左侧约220px席位列表，中间弹性聊天/公共桌面，右侧约320px自己的牌与行动。主持人的右栏改为裁决面板，可展开全量角色表。
平板768—1023px：双栏，聊天保留主区域，角色和裁决在侧抽屉中切换。
手机 <768px：单栏，底部“聊天 / 桌面 / 我的牌 / 行动”；主持人对应“聊天 / 桌面 / 裁决 / 管理”。重要待办用数量提示，不把桌面三栏强行缩小。

移动端使用动态视口高度和安全区边距；软键盘出现时输入框和发送按钮仍可见。正文/输入不小于16px，操作区域至少44px；普通页面不横向滚动，双牌在窄屏纵向展示。
目标选择、投票、13水使用和主持人死亡确认显示角色/座位、效果与提交按钮，防止触屏误点。确认属于正常操作交互，不增加身份认证步骤。
焦点可见、按钮有文字、头像有替代描述、日夜/死亡/离线均有文字标识。动效轻量，支持减少动态效果；不使用大规模特效或自动播放音乐。

5. 原生客户端（Flutter）

目标平台只有 Android 玩家端与 Windows 主持人端。使用 Material 3 与 Flutter 自带的导航、动画和 HapticFeedback，除 flutter_secure_storage、shared_preferences 外不引入状态框架、路由框架、动态 UI 包或游戏引擎。
应用显示名与窗口标题统一为“魔法裁判”：Android 用 AndroidManifest 的 android:label，Windows 用 runner 的窗口标题与 Runner.rc 的 ProductName/FileDescription；可执行文件名保持 ASCII 的 seven_double_client.exe，避免非 ASCII 文件名带来的工具链问题。
界面字体统一为 HarmonyOS Sans SC（简体中文，随包内置 Regular/Medium/Bold 三档，约 23MB），由 pubspec 声明字体家族并在 ThemeData 的 fontFamily 启用；网页端同样改用该字体，由 public/fonts 同源提供并配 @font-face。字体随包内置是为了让原生客户端在离线或首屏时都能正确显示中文，不依赖系统是否安装。
服务地址只接受无路径、查询和片段的服务根地址；loopback、localhost 与私有网段可以用 HTTP，其他主机必须 HTTPS。HTTP、/api/live 与头像地址都从同一根地址派生；请求超时 25 秒，写失败后只拉取一次状态核对，绝不自动重放。
一个 GameApi 负责 QQ 挑战、me、大厅、主动加入、状态、命令、消息分页与发送、证物和登出；HTTP 请求一律不跟随重定向（ServerEndpoint 只校验根地址，跟随 3xx 会让带令牌的请求降到任意明文主机）。一个 LiveConnection 消费 sync/state/message/ping，65 秒无事件按 1、2、4、8、15 秒退避重连并按消息 ID 补齐；单帧损坏只丢该帧、补齐失败不断线，但握手被 401/403 拒绝属于身份失败，立即停止重连交给登录流程。DTO 只解码服务端裁剪结果，不在 Dart 里重算规则。
玩家“对局”页上方是可分页消息列表，下方固定聊天输入和短行动条；点击 2—4 字短名按钮弹出底部表单，展示完整说明、字段与最终确认。软键盘弹出时隐藏行动列表、只保留紧凑行动入口与未读提示。行动是否“新”按服务端描述的规范化键比较，首次同步只建立基线，不把旧行动伪报为新行动。
行动说明由服务端下发（actions 描述里的 description），客户端只负责渲染，不在 Dart/TS 里重算规则：每个行动 id 都有一条固定说明，随局面变化的行动在服务端按当前状态改写。因此投票行动直接写明正在投谁（短名如“对3号 · 名字投票”，说明给出候选席位、第几轮与所需票数），夜间技能、白天技能和主持人裁决各自给出当下这一步做什么、按什么阈值结算；开闭加入、开枪命中率与剩余子弹同样如此。缺说明的 id 属于后端缺陷，checks 会断言玩家与主持人此刻能拿到的每个行动都带非空说明。
手机底栏固定三项并采用悬浮圆角样式：玩家为“对局 / 状态 / 我的”，主持人为“对局 / 状态 / 管理”。新消息、新行动或警告反馈到“对局”，未查看的阶段/牌桌状态反馈到“状态”，双牌私密状态反馈到“我的”，主持人待办反馈到“管理”；角标同时使用数字和颜色，切到对应内容并实际查看后才清除。
Android 对按钮确认、频道切换、收到需本人处理的新行动或警告分别调用 selectionClick、lightImpact、heavyImpact；Windows 静默。应用在后台、系统关闭触觉或系统开启“减少动态效果”时不做动画和振动。阶段变化时弹出一次全屏阶段动画，显示日数、昼夜和阶段名；首次进入或重连不重复旧动画。
每个席位同时绘制两张圆形头像，左右重叠约 50%，当前使用的牌位于顶层；未获授权的牌显示“?”，已出局的身份头像灰白化。夜间延迟公开期间严格使用服务端现有的 avatar_role_id/previous_role_id/cards/current_card_id，客户端不得从动画顺序猜测隐藏牌；自己的“我的”页始终完整显示两张真实角色卡与状态。
每个行动都配图标：Material 图标为主，语义不贴合的再补自绘 SVG（assets/icons）。映射表在 lib/src/app_icons.dart 里，check 会断言它覆盖后端声明的全部行动 id，新增行动漏配图标会失败。
需要选择时使用自绘选择界面而不是系统下拉框：选玩家显示「头像 + 名字 + 角色名」，出局者灰白化并标注；选行动显示图标、短名、分组与说明；选魔典用 13 张立绘卡片并强制正好 11 名。行动选项的 value 是参与者 id，座位视图因此额外暴露 participant_id，客户端据此把选项关联到席位与角色（玩家视角拿不到别人的牌，会显示“角色未公开”，这是权限正确表现）。
主持人登录后进入独立主持人壳，“管理”按“当前待办 / 流程 / 玩家 / 私密信息 / 纠错”分组，顶部显示阶段、自动推进与真正阻塞项，并列出本局魔典。所有按钮只显示短名，点击后才展开影响、目标、参数和确认；主持人仍通过同一 actions 描述推进、警告、裁决、代操作、替补、踢人/拉黑和胜负确认，席位视角读取后再代操作，不能提交该席当前没有的行动。观战只复用只读牌桌，不挂载管理组件。
新建对局必须先经过魔典选择：Flutter 端 CreateGame 不再静默使用默认名单，主持人先选满 11 名并确认一次后才建局。
对局页的快捷操作：点击消息头像、发送者名字或牌桌里的席位卡，都会打开该参与者的快捷菜单。玩家看到「查看角色技能与状态」「发起私信」；主持人另加「一键禁言/解除禁言」「警告该席位」「移出本局/拉黑」。快捷操作不新开协议：它按 payload 复用服务端 actions 里对应的描述并预填目标，危险动作仍是红色标记，仍然只提交一次。
角色技能详情展示的是公开规则（catalog 的 normal / witch 与角色的公开身份、生死、在线、禁言状态），不展示别人的下层牌、剩余次数等私密信息。角色目录随游戏状态一起读取并缓存，取不到只影响详情文案，不影响对局流程。
自己当前的下层牌换人时自动弹一次角色卡介绍（标题“新角色登场”，内容是该角色的好人方技能与魔女化技能，与点头像看到的详情同源）：发牌、下层登场、复活和换牌都会改动 current_card_id，因此都覆盖。判定只在客户端比较自己 self.current_card_id 的前后值，首次同步/刷新/重连只记基线不弹窗，同一个角色连续两轮不会重复弹；协议不变，服务端不需要新增字段。
主持人登录后进入独立主持人壳，“管理”按“当前待办 / 流程 / 玩家 / 私密信息 / 纠错”分组，顶部显示阶段、自动推进与真正阻塞项，并列出本局魔典。所有按钮只显示短名，点击后才展开影响、目标、参数和确认；主持人仍通过同一 actions 描述推进、警告、裁决、代操作、替补、踢人/拉黑和胜负确认，席位视角读取后再代操作，不能提交该席当前没有的行动。观战只复用只读牌桌，不挂载管理组件。
主持人另在对局页顶部有一条快捷工具栏，直接给出当前真实可用的高频动作（开放/关闭加入、推进、暂停自动、警告、禁言、建私信）——只显示服务端此刻确实给出的动作，缺席的自动隐藏，不必切到“管理”页。

六、七双对局与裁决流程

1. 对局主线

建局建立空席 → 发放共用玩家码和观战码 → 七名玩家入场并首次准备 → 系统私下发放14张牌 → 玩家调整上下牌并第二次准备 → 主持人开局 → 魔女化 → 夜间行动 → 夜间结果与证物 → 自动排定的顺序发言 → 自由发言 → 提名/投票/处决 → 天黑，循环直到主持人确认结局。
魔女化前三天按开局生成的魔女阵营执行：第1天转化 A 的当前牌、第2天转化 B 的当前牌（两席由发牌排除艾玛席与含米莉亚/亚里沙的席位），第3天优先艾玛：艾玛存活则强制转化（不论层数与当前牌状态），艾玛已出局则由 A、B 中仍可转化的一位接替（按席位号取第一个合法者），不退回魔典；第四天起按已随机排列的魔典找第一个合法目标：存活、尚未魔女化、当前在上层，且另一张不是原始米莉亚或亚里沙。另有一个默认关闭的主持人开关「汉娜魔化」，只在第三天入夜前可改：开启后，第三天夜里若汉娜在场上、曾经和雪莉绑定过且当前已解绑、艾玛不在场，则由汉娜覆盖当天魔女人选。命运席位无合法目标、魔典耗尽或其他规则未定情况交主持人处理，不能把整场目标顺序每天重新洗牌。
好人的胜利条件是 A、B 两个魔女阵营席位整席出局（单张魔女牌出局不算）：这样阵营席位可以用另一张牌在第三天再次魔女化，胜负只在两个玩家都出局时结算。
每个阶段展示“当前谁需要做什么”，阶段标题右侧同时给出该阶段的简要提示（谁该行动、点哪个按钮、其他人是否只需等待），主持人面板另列出完整的待办清单与当前行动者。玩家主动确认后提交；可放弃的行动有“放弃并确认”，不以断线代替放弃。夜间开始时，本夜没有任何可执行技能的席位自动按“放弃并确认”处理并私下告知，只有真正还能行动的席位需要提交，因此魔女可可始终是最后行动者。主持人只对当前确实卡住的席位启动30秒倒计时，可逐个警告或一键警告全部；到期按未操作处理。待办列表里属于「警告」的条目（夜间未确认、顺序发言、提名、投票、临刑响应、希罗回溯）直接以「警告30秒」按钮呈现，点一下就对条目里那个席位生效，不再先打开表单再提交；面板上的「警告：30秒后结束该玩家操作」仍保留，用于手工选席位或一键警告全部。倒计时用截止时间，刷新不会重新获得30秒。
系统自己知道做完的阶段（魔女化检测、夜间行动、最后夜间行动、顺序发言、提名、投票、处决前响应）在无人待办时进入5秒倒计时，到点由系统推进到下一阶段，不再等待主持人点击；所有客户端都显示“自动推进 · 剩余N秒”。出现待裁定事项、行动者重新卡住，或主持人暂停自动推进时倒计时立即撤销。主持人面板常驻“暂停自动推进/恢复自动推进”，暂停后该阶段只由主持人手动推进；主持人手动推进同样可以随时打断倒计时。自由发言、夜间预结算、夜间结果、天黑与胜负确认等需要主持人判断或宣布的阶段，仍完全由主持人推进。顺序发言的顺序也由系统直接排定，不再需要主持人先点一次排顺序：本夜出局者最先，其余玩家在顺序与逆序两个环里取让魔女化玩家更早发言的一侧（speech_plan 以出局席之后那一席为锚点、按座位顺/逆序绕圈后把出局者提到前面比较），没有魔女化玩家时取顺序；主持人仍可用「排发言顺序」手工改起点与方向。
顺序发言同样可以预提交。未轮到的席位有两个选择：点「本轮不发言（跳过我的顺序）」表示这轮跳过，轮到其顺序时自动略过并公开记录“X号本轮不发言”；或点「提前写发言（轮到你时公开）」，在弹出的文本框里写下发言内容；内容先私下存好，轮到他/她时系统才自动以其本人身份公开发言消息（与普通发言同一样式，头像与称呼一致），同时其顺序自动略过，写得早的人不会提前曝光。两者都是一次点击直接生效、不需要二次确认；当前发言人另有「结束本次发言」推进顺序，也可以直接用「提前写发言」把内容写完并交给下一位。所有人都提交后发言阶段立即完成，配合自动推进无需主持人点击即可进入自由发言。预提交按天记录，天黑进入下一夜时清空。本夜出局但下层仍能行动的席位照常按顺序发言；两张牌都已出局的席位不再排进发言顺序，自动排定与主持人手工调整都跳过它。
主持人的待办列表始终列出「完成当前阶段 / 推进」这一项（夜间预结算已有同名专属待办，不重复），并标出当前阶段名与“现在可以推进”或“先处理上方待办、等待玩家完成行动”，方便主持人从待办直接推进。
需要人工结论的地方显示待办并等待主持人，不随机猜一个结果，不用“默认无事发生”跳过未决效果。

2. 夜间行动与死亡前预结算

第一步：收集普通夜间行动及放弃确认；艾玛选择寻宝时清空本席其他夜间选择并直接锁定全夜，系统立即抽取1/5地雷结果并公告。
第二步：若魔女可可在本夜可行动，将其他人已确认的夜间行动提供给可可，再允许可可最后提交。普通可可仅在信物受赠者明确授权后看到对应行动。
第三步：系统只为可可的「赠送信物」抽取1/2中毒效果骰（其余技能一律不吃中毒骰），并固定亚里沙左右邻座各自的1/2负伤结果；再预结算魔女刀、额外攻击、全场攻击、庇护、玛格爱人负伤与其他伤害。夜间死亡不抹去死者当晚已正常提交的行动。
第四步：只有伤害处理后仍会死亡，才检查米莉亚替死或希罗回溯；两者都不再掷中毒骰，直接触发。米莉亚每晚必须预选一名玩家换血，该目标一直保留到她下一次有效换血；其换血对象在预结算中出局时，把致其出局的那次普通攻击转移到米莉亚牌并重算（处刑、质疑失败与殉情不走替死）。希罗不再由本人选择：夜间预结算致其出局时系统立即回溯到前一天顺序发言，白天死亡回溯到前一天自由发言，找不到该时点则回到开局；回溯一旦发生就返回“已回溯”信号，调用方不得再写回阶段或快照。
第五步：同一份预结算反复检查受影响的结果，但不重复消耗技能次数或重新抽取已固定的概率（中毒效果骰只存在于信物与信息类，预结算重算不会重复掷骰）。出现规则未说明的冲突才转为主持人待办。
第六步：主持人审阅最终结果、雨夜脚印、四人疑似凶手名单、复活/傀儡及相关连锁，确认后发布允许公开的死亡和证物信息。未揭晓的死亡不先推送再撤回。

夜间出局不在夜间阶段公开：本夜出局公告、头像切换与出局标记压到第二天顺序发言开始时统一公示。白天发生的出局仍当场公示。

寻宝安全者在对应白天不能成为魔女刀、蕾雅长矛或提名目标，但仍会受到全场攻击。亚里沙与玛格明确造成的“负伤一次”不会把已有负伤升级为死亡。

3. 双牌与回溯

席位下保存两张实际角色牌，牌有自己的持有人、层次、生死、魔女化、伤势和技能使用状态；不能只给玩家一个“死/活”字段。
一张牌出局后才能使用下层牌；同一玩家同一半天最多出局一张牌。目标究竟跟随人还是跟随被交换的牌、下层在本阶段的可行动时机等无明确说明的情况，生成具体裁决项让主持人处理。

希罗回溯记录好人与魔女两次独立额度，各最多一次；额度已用不会被自己的回溯恢复。魔女回溯保留自己的魔女化。
回溯由系统在希罗死亡预结算时自动触发，不在行动面板中等待本人选择：夜间回到前一天顺序发言、白天回到前一天自由发言，找不到该时点则回到开局保存的最早快照。
恢复前一天对应游戏时间点的牌、普通技能次数与其他可回溯游戏状态；玩家的记忆及已收到的聊天/线索记录不删除。雪莉对汉娜的绑定、安安大招负面效果等精神系效果单独保留，不被快照覆盖。
回溯不恢复旧邀请码、被撤销的会话、旧操作者或网络连接；这些不是游戏时间。回溯后公开标记“游戏时间已回溯”，真实时间顺序的聊天继续保留；不把已发生消息伪造成从未发生。

4. 投票、死亡批次与胜负

主持人确定提名顺序和本轮候选，对每名候选单独收集同意/不同意/弃票，直到主持人确认整轮完成。其他未定投票细节以主持人本局宣布为准。
提名在白天任意阶段都能提交（玩家可以提前提名，界面标为“可提前”并直接提交、不再二次确认），不要求所有人等到提名阶段才行动；进入提名阶段时先前提名或放弃的玩家自动视为已确认，只有没提交过的席位需要操作。同一张牌可以被多名玩家同时提名，重复提名不是失败，也不会重复投票：计票时按提名先后去重，每张被提名的牌只投一轮。投票阶段开始时，提名过当前候选的玩家按自己的提名自动投下同意票（被强制弃票或雪莉绑定汉娜等规则冲突时除外），其余玩家仍可正常点选同意、不同意或弃票。
每次计票的分母 N 是当时拥有投票权的存活玩家数；强制弃票者仍计入，失去投票权者与不能投票的傀儡不计入。通过门槛为 floor(N/2)+1。不要用实际投票人数替代分母。
所有严格过半候选一起进入本轮处决结果；奈乃香临刑开枪等效果先处理，不在第一名候选处决后提前截断其他已通过处决。
每次死亡检查胜负并形成候选结论。同一半天的多人出局按严格同时处理，主持人确认相关结果齐全后才正式宣判，不按网络消息到达顺序抢先封局。双方同时满足时白好黑魔。
雪莉、质疑失败者等特殊个人结局由角色状态合并计算。交牌不简化为任何一人点击即可结束，照玩家规则收集条件和主持人确认。
若尚未生成魔女或仍有后续转化问题，不把“当前存活魔女数为零”直接等同于好人已经完成胜利条件；结合本局魔典交由主持人确认，避免空集合判断导致开局自动获胜。

5. 13水与信息

13水按夜发放：主持人可在夜间行动、最后夜间行动或预结算阶段把一瓶13水交给一个存活席位，同一夜可发给多个不同席位，每位持有者各自使用一瓶，夜末未用过期收回。只有持有者本人看得到自己持有的13水。持有者在本夜行动期直接指定目标使用，毒杀立即进入本夜预结算，不创建主持人待办；13水死亡的未隐藏死因单列“X号玩家被13水毒杀”，魔女梅露露可勾选隐藏死因，隐藏时按普通夜间死亡处理（走普通死亡公开路径，不生成固定目击名单）。
四人疑似凶手名单按每名夜间死者分别生成：包含技能处理后的显示凶手、汉娜及另外两人；未隐藏死因的13水死亡由系统直接生成一份随机排序的固定四名单（真实凶手、在场的梅露露与在场的汉娜必定包含，余位从未入选角色随机补齐），跳过主持人填写。死者中毒时这份目击是中毒信息：判定出局前掷一次信息骰，各1/2给出含真凶的真名单或把显示真凶换成一名未入选角色的假名单，本人不会得知是哪一种（汉娜始终在名单里，真凶就是汉娜时假名单只能原样保留）。若实际来源是使用替罪凶手的魔女诺亚，名单与雨夜脚印按替代角色显示；雨夜脚印公开显示凶手座位号相对死者较大或较小，实际来源为汉娜时方向反转。魔女穗乃香每次真的进入名单时由本人选择本次显示身份，超时保留穗乃香。名单只发给对应死者。证物仍只在整席最后一张牌出局时发放。
每条夜间死亡、延迟公开通知、目击待办与已发目击都关联同一个 death_id：梅露露复活时按 death_id 一并撤销该次死亡的公告、死因、目击与半天出局记录，因此复活目标不出现在夜终总结里，同夜其他死亡不受影响。
可可的信物不含文字或图像，只记录发送席位、受赠席位、日期和夜间行动授权。证物仍可包含文字或图像；主持人提供的其他材料继续按指定接收范围投影。

6. 主持人工作台

优先呈现本阶段待处理事项，而不是要求主持人去编辑一大段原始数据：
- 看全员双牌、上下层、生死、阵营、伤势、剩余技能次数和在线状态。
- 看魔典、转化候选、夜间意图、概率结果与预结算变化。夜间阶段在主持人操作面板列出每个席位当夜的角色牌、已提交的技能与目标、尚未提交者，玩家之间不共享这些信息，主持人可据此主持。
- 查看动态毒源、中毒骰、夜间概率结果、实际伤害来源与预结算变化；系统明确的概率自动抽取，不产生主持人待裁定项。
- 发13水、排发言顺序、警告并计时、开闭投票、确认处决与胜负。
- 处理替补继承、非同一天同一时点的回溯和规则未定义的特殊操作；穗乃香目击改名、真实/伪装声明和质疑均由对应玩家或系统直接结算。
- 需要纠错时调整指定对象的游戏状态，附裁定说明；同时预览哪些变化公开、哪些只给当事人。

已经明确的概率由系统抽取，默认不要求主持人人工掷骰；没有明确概率才由主持人决定。主持人的裁决记录属于本局游戏记录，不另做审计平台或管理员监控系统。
公开操作必须清楚列出目标和将发布的内容。私密裁定不能仅因为点击了“下一阶段”就自动变成全员公告。

以下是实现覆盖清单，完整规则文本仍从同一个角色目录提供。每项均包含真实角色能力、魔女化后的变化和主持人的裁决入口，不只做选牌而把角色技能留空。

艾玛：每日打断/最后发言；动态邻接中毒；每夜独占寻宝、1/5地雷与安全后的目标保护；前两天不能魔女化，第三天存活即以最高优先级强制魔女化（艾玛已出局则由魔女阵营 A、B 中仍可转化的一位接替）。

玛格：白天爱上/移情，每夜令爱人席当前牌负伤一次，爱人整席出局后转爱自己；魔女学习/抵消洗脑。没有破译或模仿协议。
蕾雅：白天长矛立即进入标准出局预结算，自己同时进入当日处决名单；没有夜间注视或夜间长矛。
穗乃香：开局获知上层牌、公开示人身份；魔女每次进入四人目击名单时由本人选择本次显示角色，超时显示穗乃香。

质疑范围：除信物、爱人选择与处决幻视外，全部开放白天技能声明都可被其他玩家质疑。声明公开字段固定为声明ID、席位、技能名、目标摘要和状态，不包含真假。质疑假声明只停止未完成部分并清除关联的安安延迟处罚；质疑真声明用 eliminate_seat 直接作废质疑者两张牌并个人判负。

伪装结算：当前角色/魔女状态不满足的同角色能力与穗乃香示人身份能力可产生假声明。真假声明都立即进入相同执行分支；假信物和假爱人选择不写状态，其余已执行结果不回滚。处决幻视是处决阶段的临刑技能，不在伪装范围内，只能由奈乃香本人声明；信息类技能只掷信息骰，本人必定收到信息，真假由信息骰决定且不告知本人。效果类里只有「赠送信物」会因中毒骰失败被记为假。所有这些分支都不产生主持人真假裁定待办。

八、状态、保存与实时通信

1. 必要状态

Game：本局ID、状态版本、日数、白天/夜晚标识、阶段、发言顺序、截止时间、魔典、13水、待办裁决与胜负候选。
Seat：稳定座位号、当前操作者、公开称呼/示人身份、双牌引用、准备状态、投票资格；在线连接另行维护。
RoleCard：唯一牌ID、角色种类、原始牌身份、当前持有人及上下层、生死、魔女化、状态和次数。原始身份不能因交换而丢失。
Action：提交者席位、使用的牌、技能/目标、提交阶段与版本、是否确认、已抽定结果和处理状态。
Information：信物授权、四人目击名单、证物、私密提示与状态卡；发送时的获准接收者与内容。
PersistentEffect：不能随希罗回溯消失的绑定、处罚、回溯消耗及其他主持人明确保留的效果。
Snapshot：游戏内时间点、对应牌与技能状态；不包含登录账号、连接、历史聊天或可回溯的鉴权数据。

2. 两个SQLite数据库

对局库 data/seven-double.sqlite3 使用七张表：games（完整领域状态、快照、版本）、participants（参与身份、account_id 关联与历史权限）、channels（私信频道的创建者、状态、成员/邀请/同意名单与结束时间）、messages（聊天、信息、通知及接收范围）、evidence（文字、图片及归属）、invites（定向对局邀请：受邀账号、邀请人、状态、创建与响应时间）；领域快照存在 games.state 内，不另建事件重放或快照数据库。旧的 sessions 表与旧邀请码形状的 invites 表在初始化时删除重建。
鉴权库 data/auth.sqlite3 使用三张表：accounts（qq_id、昵称、头像）、login_challenges（六位挑战码的散列、状态、过期与消费时间、客户端种类）、login_tokens（token_hash、account_id、kind、expires_at、valid）。只保存 SHA-256 后的令牌与挑战码，原始值不落库。
两个库之间不伪造外键：单进程事务边界先校验账号，再写对局参与身份。备份边界也不同——清空对局只删对局库内容，账号与登录令牌保留。`data/` 可用 `GAME_DATA_DIR` 覆盖，验证时请指向独立临时目录。
角色素材继续读现有img目录；证物图像作为SQLite BLOB保存在evidence表并按身份检查权限，不能通过公开静态素材路径访问。信物不保存图像。
游戏命令先在本局锁内校验与计算，事务保存状态及产生的消息，再推送；保存失败则不发布成功结果。小规模对局不需要分布式锁。
提供启动时读回当前状态，避免刷新或服务重启重新发牌；不承诺服务中断自动托管，也不增加房主故障转移方案。

3. 可见视图

玩家/观战响应从公开字段出发，按获准信息补充；不要先把主持人全量状态发给浏览器再用CSS隐藏。HTTP、WebSocket、消息历史、附件访问与重连恢复共用同一可见性规则。
主持人视图含全部游戏信息。玩家视图含自身双牌及合法获得的信息。观战视图含全席双牌、生死、状态、阶段与结果的只读牌桌，但不含玩家/主持人行动、主持人待办、参与者管理或席位代操作，也没有任何游戏命令。替补增加历史权限必须由主持人明确决定，不默认获得其他人的私聊。
所有写命令统一携带 expected_version；旧版本请求返回409，客户端重新取得可见状态并要求确认，不重复执行，也不自动重放。动态行动描述与 GameView 都带顶层 ui_version，当前为 1；未知版本或未知字段类型（只允许 text、textarea、number、select、multiselect、checkbox、drawing 七种）显示“客户端版本不支持此行动，请升级”并禁止提交。engine.validate_command() 始终是唯一权威，客户端输入检查只提供即时提示。
过往消息保留发送时的接收者，后来的换牌不会自动解锁另一席位的历史信息。

4. 更新方式

HTTP承接登录、加入、游戏命令与聊天提交；WebSocket只负责实时状态、消息和在线通知，不维护另一套技能协议。
游戏命令携带 expected_version；旧版本请求返回409，客户端重新取得可见状态并要求确认，不重复执行。客户端不会自动重试扣子弹、投票、发13水等有状态命令；超时先取状态确认结果。聊天另有自己的发送确认，不因游戏版本变动拒收正常发言。
WebSocket使用 sync、state、message、ping 消息，客户端回复pong。持久消息有递增id，消息kind区分聊天、私密信息、在线通知等；对局结束随state同步。所有内容按接收权限生成，不做复杂增量补丁。
连接建立时在同一同步边界注册订阅并取得快照与最近一页获准消息，然后投递后续更新，避免初始化窗口漏消息。重连后重新同步状态，按after游标补充获准历史，客户端按消息id去重。
纯在线状态和聊天不抬高游戏命令版本，避免正常发言让别人选好的夜间行动无故失效。

九、HTTP与实时接口约定

以下接口均已实现。登录身份来自令牌（网页 Cookie 或原生 Bearer），不接受客户端自行指定“我是主持人”或以role_id代替身份。

GET  /api/health                              服务健康状态
POST /api/host/login                          password；正确值114514；设置主持人Cookie
POST /api/native/host/login                   password；返回 session_token 与身份，供原生客户端保存
POST /api/logout                              撤销当前令牌
GET  /api/me                                  当前身份；未加入本局时返回账号身份
GET  /api/catalog                             公共角色规则、头像地址与展示信息
POST /api/auth/challenges                     网页生成六位登录挑战码

POST /api/native/auth/challenges              原生生成六位登录挑战码
GET  /api/native/auth/challenges/{id}         原生轮询；完成后返回 Bearer 长令牌
POST /api/internal/qq/login                   仅网关可调用：用 X-Gateway-Token 绑定QQ号与挑战码
POST /api/internal/qq/members/sync            仅网关可调用：同步群成员昵称与头像

POST /api/games                               主持人创建一局并确认魔典名单，系统建立7个空席

POST /api/games/{game_id}/evidence            提交文本或图片证物；私信锁定或观战身份一律拒绝
GET  /api/games/{game_id}/evidence/{id}       检查权限后返回材料或图片
WS   /api/live                                用Cookie或Bearer建立连接，接收事件并回复心跳

commands统一使用 expected_version、action、payload 信封；房间管理输入由Pydantic校验，游戏动作由后端动作描述和领域函数逐项校验权限、字段、阶段、次数与目标。不接受任意JSON覆盖整个游戏状态。
房间管理动作：room.open_join 开关开放参局；room.kick 使用participant_id和block，既可移出玩家也可移出观战者；room.replace 使用seat_id与participant_id 让观战者接管空席；room.mute 设置或解除禁言。
私信动作：channel.create（name、participant_ids）、channel.accept、channel.reject、channel.end（均带 channel_id）；它们和其余所有行动走同一套确认流程。
所有玩家行动、私信邀请响应和主持人管理都是单次确认：点击 2—4 字短名按钮打开说明与参数弹窗，填好后点一次“确认提交”即发送，不再有第二道确认框，也不再有 instant 绕过语义。校验仍在提交前完成（必填、选项有效性、数值范围），危险动作继续以红色按钮与警告图标双重标记；因为所有写命令都带 expected_version，服务端状态变化会返回 409 并要求重新确认，不存在静默写入。
GET /api/games/{game_id}/messages 的 scope 取 all|public|private|system|host：先按频道成员关系过滤再分页，保证筛选历史不是只过滤本机最近一页。
所有选择席位的人物选项都同时显示玩家名与角色名：默认只显示上层牌的角色名，上层出局后显示“上层→下层”两个名字；主持人始终看到该席位两张牌的角色名。

玩家动作涵盖：选上下牌、准备、确认/放弃夜间行动、白天技能声明、质疑、主动出局、提名、投票、制作/破坏、信息授权、证物公布、13水使用、交牌请求。提名不限轮流：尚未提名或放弃的席位都会同时看到「提名候选/放弃本次提名」，各自提交后立即生效，只有能提名的席位都提交后主持人才推进（当前牌本阶段不能行动的席位没有提名按钮，直接视为跳过，不挡在待办里）；重复提名同一角色由服务器拒绝。每个动作描述自带“是否需要玩家确认”的标记，前端与主持人面板都用它显示“轮到你行动”的提醒与阻塞状态。
主持人动作涵盖：开局、排发言顺序（选起点与方向）、警告、结束超时行动、推进阶段、裁决、确认结算、发放13水、投票控制、纠错、替补、踢人/房内拉黑、结束对局。主持人可用「席位视角」读取某席位自己看到的界面，该界面逐条列出该席位当前可提交的操作并各带「代替操作」按钮；代操作只能使用该席位当时可用的行动，代操作内容不向他人公开，只在公开频道留下“主持人代某席位完成本阶段操作”的提示。
常见失败区分：未登录、无权限、邀请码失效、目标席位已被占用、阶段已结束、状态已变化、输入不合法。错误文本不向无权者透露真实牌面、私密目标或技能真假。
证物图片上传仅接受2MB以内、最大边长4096的PNG/JPEG，后端生成随机证物ID；不执行上传内容，也不接受客户端指定任意磁盘路径。角色立绘是公开静态素材，与私密证物分开。

十、开发与交付顺序

按完整可运行的纵向功能推进，不先铺满空文件或留“稍后实现”的角色按钮：
1. 完成主持人登录 → 新建空席局 → 发共用码 → 七人随机入场/首次准备 → 发牌/私下排序/再次准备 → 主持人开局；验证旧码失效和刷新恢复。
2. 接上真实聊天、头像、消息权限、WebSocket掉线公告、手机/电脑桌面和观战替补。
3. 接上主持人阶段推进、确定概率、技能输入/信息、预结算、投票、13水与结局，覆盖14角色。
4. 处理回溯、精神系保留、同时死亡、伪装/质疑、替补历史，完成全程七双联机验收。

前端开发服务器通过 frontend/vite.config.ts 代理访问本机8000端口的FastAPI；正式使用时同源服务，避免多余的跨域和多后端部署。npm ci按锁文件安装开发与构建依赖。
后端规则检查只保留能防住真实错误的少量回归用例；不要为每个转发函数写测试。浏览器体验以实际手机/桌面视口操作和真实服务联机为准，不用截图假页面替代。

十一、验收标准（实际验证范围见第十二节）

A. 114514可进入主持人入口，其他密码失败；玩家改昵称或提交host字段不能获得主持人权限；QQ 挑战码只能消费一次，原始令牌不落库。
B. 七名玩家首次准备后随机分出14张不重复的牌，7席各2张，米莉亚与亚里沙不在同一席；玩家能私下排上下牌，别人看不到下层牌；主持人能看到全部。
C. 主持人开放参局后，七个不同 QQ 账号无需审核随机占满七席，第八个账号被拒但可选观战，同一账号不能重复分席；发牌后不能新占玩家席。踢出/拉黑只撤销本局参与身份，账号与登录令牌保留，下一局可重新加入；清空对局不登出任何账号。刷新按账号恢复原席位，发牌后的空席只能由观战者接管且不重发牌。
C2. 观战能读全席双牌与状态，但游戏命令、证物提交和管理请求一律拒绝；公屏与私信只按频道权限开放，不能读取未加入频道的历史、实时消息或附件。
C3. 私信覆盖玩家或观战创建、多人逐一同意、拒绝取消、主持人默认同意、主持人免同意发起、单个非主持人同时只有一个 active 频道、开始与结束的全体系统消息；active 期间非主持人成员的公屏发言与玩家成员的游戏行动都被服务端拒绝，主持人不受限制，结束后恢复。进入夜间（魔女化检测起算）时全部私信频道自动结束并公告，夜间只有与主持人的私聊能创建，不含主持人的遗留频道在夜间不能发言也不锁住游戏行动。
C4. 行动协议只接受七种字段类型与 2—4 字 short_label；未知 ui_version 或字段类型被拒绝；所有行动都是单次确认；409 保留草稿并要求重新确认；lobby.order 选定上层后服务器保存的另一张必为下层。每个行动都带非空说明，需随局面变化的行动（投票候选、夜间技能、白天技能、主持人待办裁定、开枪概率、开闭加入）在服务端按当前状态改写；客户端只渲染，不重算规则。
D. 同一席位两条连接断一条不发掉线通知，最后一条断开只通知本局一次；恢复不重抽牌、不清空行动。
E. 私聊与13水持有信息在玩家、观战的状态、实时事件和历史里都只按权限出现；没有前端隐藏的全量主持人数据。
F. 手机360px宽与桌面1440px宽均能入场、查看双牌、发气泡消息、投票和操作主持人待办；软键盘不挡发送按钮，页面不横向滚动。
G. 5名有投票权活人中含1名强制弃票者时，处决仍需3票；傀儡和真正无投票权者不计入分母，多候选通过不漏结算。
H. 米莉亚受庇护而不死时不替死；确会死亡才替死重算；重算不多扣子弹或再次掷骰（替死不掷中毒骰）。可可看到他人行动后才能最后提交。
I. 同一玩家同一半天不能出局两张牌；同一半天同时达成胜利按白好黑魔，不按死亡消息先后判定。
J. 希罗两种身份各限一次，死亡预结算即自动回溯、不产生主持人待办；回溯恢复他人普通技能，不恢复自己的额度，不撤销魔女希罗魔女化、雪莉绑定或安安大招负面效果，也不删除聊天记忆；回溯后调用方不再写回阶段与快照。魔女希罗未攻击艾玛时同样不产生阻塞待办：例外额度耗尽后改为一条可默认裁定的「疯狂」待办。
K. 雪莉/汉娜开局双上层即绑定，否则未共同作为上层过完整白天前不触发；动态中毒来源、信物效果骰与信息假值均按规则结算；四人目击、雨夜脚印与穗乃香逐名单改名相互一致。
L. 13水按夜发放、夜末过期，未隐藏死因的公告与固定目击一致，魔女梅露露的隐藏死因例外保留。
M. 穗乃香伪装和真实技能的公开声明不能被UI区别；质疑只停止未完成部分，失败质疑的个人判负得到体现。
N. 六名不同席位提交「请求结束自由发言」后 10 秒自动进入提名；不足六人、有待办或主持人暂停时不自动推进。夜终公告为「第X夜是平安夜」或列出仍实际出局的当夜角色名。
O. 傀儡被魔女梅露露代操作时，动作与频道都以 `as_seat` 与星号标记区分；星号只进 `label`，`short_label` 保持 2—4 字协议长度；傀儡席本夜的行动与确认也只从控制者的傀儡面板提交（原席位不会既没有行动又占着阻塞待办），原傀儡玩家只能只读旁观，不能发言、上传证物或执行游戏行动；傀儡当前牌出局后原玩家恢复通知与权限。
P. 替补接管后旧操作者不能继续行动，新操作者只继承主持人批准的私密信息；更换操作者不刷新牌或技能次数。
Q. 主持人未裁决的“可能”会明确等待，不被系统偷偷当成失败、成功或跳过；未定玩法不阻塞系统本身的可操作性。
R. Flutter Android 与 Windows 客户端可登录、加入、聊天、执行行动；底栏角标与阶段动画只出现一次，软键盘弹出时隐藏行动列表但保留新行动提醒，双头像 50% 重叠且当前牌置顶、死亡灰白；Windows 主持人端无触觉且管理分组可用。

十二、运行与交付

已提供可运行的七双前后端；玩家规则仍是游戏说明，本文件记录软件结构和运行方式，二者不互相替代。

1. Windows启动
首次安装：双击项目根目录 setup.cmd，或在终端运行 .\setup.cmd。它创建.venv、安装后端与网关依赖、执行npm ci并构建前端。安装期间需要访问Python/npm包源。
日常启动：双击 start.cmd，或在终端运行 .\start.cmd。服务日志出现“Uvicorn running”后，在电脑浏览器打开 http://localhost:8000；主持人选择管理入口，密码114514。
QQ登录：复制 gateway\.env.example 为 gateway\.env 并填写 NapCat 地址、访问令牌、后端地址、网关共享密钥与QQ群号（多个群用英文逗号分隔，网关同时监听并合并群成员），然后运行 run-gateway.cmd。网关共享密钥须与后端环境变量 GAME_GATEWAY_TOKEN 一致；真实密钥、NapCat 登录态与日志都不入库。
手机加入：与电脑连接同一局域网，打开 http://电脑局域网IPv4:8000，先在指定QQ群发送“活动登录 123456”完成验证，再由主持人开放加入后主动选择加入或观战。IPv4可在电脑上运行ipconfig查看；手机不能使用localhost。若Windows防火墙提示，只按实际需要允许专用网络访问8000端口。
更换端口：.\start.cmd --port 8001；只允许本机访问：.\start.cmd --host 127.0.0.1。默认绑定0.0.0.0，必须保持单个worker；按Ctrl+C停止服务。
固定主持人密码是已确认要求，不适合把服务直接暴露到不可信公网；本版本不包含公网域名、TLS证书或外网穿透配置，但可以挂在用户自备的反向代理后面：代理需透传原始 Host 或补 X-Forwarded-Host/X-Forwarded-Proto，转发 Authorization 请求头，并允许 /api/live 的 WebSocket 升级；代理不在本机时用 --trusted-proxies 声明。带有效 Bearer 令牌的写请求跳过浏览器同源校验（原生客户端不发送 Origin），网页 Cookie 写请求与 WebSocket 仍在令牌有效时先放行；没有有效令牌时先看 Origin 是否在显式放行名单（默认 super.tkcloud.online，用 GAME_ALLOWED_ORIGINS 覆盖），再看浏览器自报的 Sec-Fetch-Site，最后才比 Origin 与 Host/转发头。

2. 开局与日常操作
主持人新建对局时确认11角色魔典名单，系统随机排序；点击“开放加入”后，已登录账号自行选择加入或观战，无需审核。玩家随机进入空席，选择上下牌并准备，7人准备后由主持人开局。
按页面提示确认行动，由主持人推进阶段、处理“可能”与未定规则待办。观战账号取得只读全牌桌；需要替补时，主持人从观战者中接管空席，并分别决定是否继承私密历史及保留原行动。
移出/本局拉黑对玩家与观战者均有效；只撤销该参与身份，不重置角色牌，也不删除该账号的QQ登录。没有设备识别或IP封禁，玩家换设备重新登录即恢复参与身份。
不明确或未写明的概率与规则交由主持人裁决；系统自己知道做完的阶段（魔女化、夜间行动、顺序发言、提名、投票、处决前响应）无人待办时5秒后自动推进，主持人可暂停或手动推进。
手机使用底部导航切换聊天、桌面、双牌/管理及行动；需要操作时顶部显示“轮到你行动”，底部导航同步标记数量；聊天可复制粘贴，证物可输入文字或导入PNG/JPEG。原生客户端提供同样栏目，并额外提供触觉反馈与阶段动画；宽屏按既有平板与桌面布局展示。
主持人工作台按“待办”组织：所有需要裁决、警告、推进或宣判的事项集中列出，未处理完不会推进阶段；顶部推进按钮在有待办时禁用并显示剩余项数。夜间可用「本夜全员行动」核对每个席位的实际提交（含目标当前角色、掷骰与猜对数、是否被中毒抵消、是否主持人代提交），并对卡住的席位一键警告；发出去的私密信息在对话记录里以“系统信息”标记出现，玩家侧另有悬浮提醒。

3. 保存与开发
默认数据库为 data/seven-double.sqlite3（对局）与 data/auth.sqlite3（账号与登录令牌），首次启动自动创建。刷新或服务重启会恢复原局；不要在进行中的对局删除数据库。备份前先停止服务，再复制整个data目录；只想保留账号与登录态时可以单独备份 auth.sqlite3。
可用环境变量GAME_DATA_DIR指定独立数据目录，联调曾使用data/verification，交付时清除此测试目录。退出浏览器不会结束对局；须由主持人结算或终止当前局后才能创建下一局。
对局结束后数据仍可只读查看，直到建立下一局为止：建立新对局会自动清除上一局对局库的全部数据（含结算与聊天），主持人也可在管理面板点「一键初始化」立即清空；两种方式都保留QQ账号、玩家登录令牌与主持人登录，下一局重新开放加入即可参局。
前端开发：保持后端8000端口运行，在frontend目录执行npm run dev；正式使用前执行npm run build。开发服务器不是第二套游戏后端。重新构建后无需让玩家清缓存：index.html 每次回源校验，带哈希的资源长期缓存。
发行版本标签：后端 /api/health 下发 GAME_CLIENT_LATEST 与 GAME_CLIENT_MINIMUM（三段数字，未配置则不下发）；客户端把内置的 ReleaseMonitor.currentVersion 与之比较，低于 latest 顶部横幅提示可更新，低于 minimum 横幅要求必须更新后才能继续使用。发版流程是先把 client/lib/src/release.dart 的 currentVersion 与 client/pubspec.yaml 的版本名同步提高，再把 GAME_CLIENT_LATEST 改成新版本、GAME_CLIENT_MINIMUM 留在仍被兼容的旧版本（本次为 latest=1.0.3、minimum=1.0.3：低于 1.0.3 的所有客户端都强制更新）；安卓 versionCode/versionName 不随之变动，更新与否完全由这两个环境变量与内置版本号决定。
原生客户端：在client目录执行flutter pub get、flutter analyze、flutter test；产物用flutter build apk --debug或flutter build windows --debug。Android 构建需要 Android SDK（platform 与 build-tools 36）与 JDK 21；Flutter 3.47 的模板用 AGP 9.1，因此 Gradle wrapper 固定为 9.3.1。Windows 构建需要 Visual Studio 的 C++ 桌面工作负载与 ATL 组件（flutter_secure_storage 依赖 atlstr.h）。
检查依赖：.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
规则/访问检查：.venv\Scripts\python.exe -m unittest discover -s checks -v
Python静态检查：.venv\Scripts\python.exe -m ruff check backend checks run.py gateway
生产构建：在frontend目录执行npm run build（包括TypeScript检查）。
