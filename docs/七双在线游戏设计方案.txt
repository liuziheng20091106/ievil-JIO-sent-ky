七双在线游戏设计方案

一、目标与设计边界

本方案用于制作“魔法裁判·七双”在线游戏，玩法以《七双模式游戏介绍与完整规则.txt》及之后确认的规则为依据。七名玩家各持两张角色牌，一名固定主持人管理对局。确定的规则由程序执行，没有明确规定的情况交给主持人裁决，不再以补齐全部自动裁决规则为开工前提。

本文记录产品、交互及已实现的软件结构，并提供启动说明。前后端应用、角色图片及回归检查均已落地；不沿用 docs/old 中已被后续回复推翻的要求。实际验证范围见第十二节。

本次落实的要求：
- 后端 Python + FastAPI，业务按职责分模块，不使用微服务或通用规则引擎。
- 玩家对局走 Flutter 原生 Android / Windows 客户端；网页只保留公告、游戏规则介绍与游戏下载链接的静态首页。
- 玩家用 QQ 群验证登录；账号与对局参与身份分离，长令牌保存在独立鉴权数据库。
- 新对局暂不可加入；主持人“开放加入”后，已登录账号自行选择加入或观战，无需审核。
- 玩家掉线后不发系统通知；在线状态只体现在席位与账号在线名单的在线标记上。
- 聊天区分公屏与私信，各自独立列表、已读游标与生命周期；私信有邀请、同意、拒绝、结束。
- 不设计反作弊、设备指纹、IP封禁、行为风控、举报审核、竞技排名等系统。
- 保留正常身份验证、房间权限、输入校验和私密信息隔离；这些是游戏正常运行的要求，不是反作弊功能。

首发运行范围：一个服务实例供一名主持人管理一局七双；结束后可新建下一局。保留观战和替补入口。不做13人模式、公开匹配大厅、多个并行对局或语音聊天。原游戏规则没有成就设计：成就只是本服的独立附加功能，由主持人手工授权、存在独立成就库（见第八节第5小节），不参与任何对局判定，也不改变「疯狂」裁定的后果。

二、技术方案与模块边界

1. 技术选择

后端：FastAPI + Uvicorn；Pydantic 校验传输输入；JSON兼容字典保存领域状态，标准库 sqlite3 保存本地数据，secrets 生成登录挑战、令牌与随机洗牌种子，random.SystemRandom 处理游戏内洗牌与已注明概率的效果。
前端网页：无框架的静态单页（frontend/index.html + build.mjs），由 Node.js 脚本把 rules.md 的规则数据注入页面后复制进 dist；提供公告、游戏规则介绍与下载链接，不做登录与对局界面。无需 Next.js、SSR、Redux、Socket.IO 或大型组件库。
原生客户端：Flutter + Material 3，直接依赖只有 flutter_secure_storage、shared_preferences、flutter_svg（画图标）、flutter_markdown_plus（渲染公告的 markdown）与 clock/path/path_provider；使用 Dart 自带的 HTTP、WebSocket 与 JSON，不引入状态框架、路由框架或动态 UI 包。
存储：三个 SQLite 文件。对局库保存对局数据，鉴权库保存账号与登录令牌，成就库保存成就定义、授权与佩戴。无需 PostgreSQL、Redis、消息队列或 ORM。
部署：前端构建后由 FastAPI 同源提供网页、API 和图片；Node.js 只用于构建静态首页，不再另设一套 Node 游戏后端。Uvicorn 首发只运行一个 worker；QQ 登录另有一个独立的 NapCat 网关进程。
已在 Python 3.14.3、Node.js v24.13.0 环境安装依赖并完成生产构建；源码使用Python 3.14语法，Node.js最低要求22.12.0。依赖分别记录在 backend/requirements.txt、gateway/requirements.txt、requirements-dev.txt 与 frontend/package-lock.json。

依赖方向：页面 → API/实时连接 → FastAPI路由 → 领域函数 → 状态结果；存储和消息推送在领域函数之外完成。
领域模块不得导入 FastAPI、WebSocket 或浏览器类型；实时连接模块不得判断角色技能；客户端不得自行判定命中、死亡、魔女化或胜利。角色规则只维护一份，由后端提供目录给客户端显示。
领域事件在开局、阶段入口、夜间行动生效、真实白天声明、攻击意图、预结算、投票资格/计票与死亡落地等确定边界依注册顺序投递。可选补丁只能通过明确事件修改意图或投票上下文，核心继续负责最终伤害优先级、胜负、服务端行动白名单、主持进入确认与版本冲突。攻击意图最多重算一次并记录主持日志。
14 个角色规则在 backend/app/game/roles/ 下按魔典目录静态登记；服务端启动时按文件名扫描 backend/app/game/external_plugins/ 中服务器管理员部署的 Python 模块、按依赖排序并一次性导入，不接受用户上传插件、不会从客户端传来的 ID 动态导入。外置模块必须提供唯一 ID、版本、独立的管理名称 NAME、说明 DESCRIPTION、分类 CATEGORY（external_required、external_default_on、external_default_off）、依赖 DEPENDS、处理器 HANDLERS 和命令 COMMANDS；内置角色全部为 builtin_required。外置必选不能依赖可选模块，缺依赖、重复 ID、环或无效元数据使后端启动失败。部署模块是受信代码，更改后重启服务；存档仍只按 ID/版本锁定，删除或变更已有版本会阻止旧局读写。
可选模块 hiro_forgery（希罗·伪证，默认关闭）依赖希罗角色：建局时勾选才生效；希罗当前牌在场且可使用技能时，每个游戏日可使用一次，填写最多4000字的自定义全场系统消息（例如伪造遗物），可勾选「加入证物」让该消息进入全体可见的证物目录。技能使用提示仅希罗本人和已确认进入本局的主持人可见，不向其他人披露伪证来源。
可选模块 codex_disabled（禁用魔典转化，默认启用）：第四天及之后的魔女化检测直接进入夜间，不再通过魔典产生新的魔女，也不产生魔典转化待裁定；前三天原有转化规则、已经产生的魔女与可可读取魔典信息均保持不变。主持人建局时可取消勾选恢复原规则，已有存档不自动启用此模块。witch_conversion 事件的 day 为当前游戏日，skip 默认为 false，已启用模块可设为 true 跳过当日转化。
可选模块 emma_treasure（艾玛·寻宝，默认禁用）依赖艾玛角色：仅建局勾选后提供夜间寻宝入口，旧局不自动启用。寻宝沿用1/5地雷、提交后本席不可修改或放弃、安全时当天的目标保护和地雷不替死；骰值与保护保存在 plugin_state["emma_treasure"]，随时间回溯恢复，结果仅本人及已确认进入的主持人可见。未启用时没有寻宝行动、地雷或寻宝保护，普通艾玛本夜无其他技能时自动确认；打断发言、中毒光环和魔女化全场攻击仍属于内置艾玛模块。
可选模块 start_announcement（开局公告，默认启用）：主持人正式开局时通过 game_started 事件向全场插播一条公告（kind=alert），正文默认“欢迎来到魔法裁判，祝各位游戏愉快！”。主持人建局可取消勾选；旧局不自动启用，重复开局被拒绝，不重复播报。正文在 backend/app/game/external_plugins/start_announcement.py 的 ANNOUNCEMENT 常量中修改，部署或修改后重启后端即可，客户端无需更新。
可选模块 leia_gaze_fix（蕾雅·视线固定，默认关闭）依赖蕾雅角色：建局勾选后，普通或魔女蕾雅当前牌可使用技能时，每天白天可发动一次「视线固定」。只向全场发布技能公告和30秒动画，无伤害、决斗、投票或其它规则效果，不生成可质疑的技能声明。动画按顺序每10秒展示 leia/full/1.png、2.png、3.png，五段专属文案各显示6秒并逐条滑入，配霓虹文字扫光、漂浮星芒与每3秒旋转一圈的背景光束；所有收件人播放相同素材，不披露魔女状态。每日次数保存在 plugin_state["leia_gaze_fix"]，替补不重置，随时间回溯恢复；旧局不自动启用。部署后重启后端，客户端更新动画资源包即可，不需更新App。

三、身份、登录与生命周期

1. 登录入口

登录入口只在原生客户端：玩家页与主持人页都是 QQ 群验证码，没有主持人密码。玩家入口用 /api/native/auth/challenges，主持人入口用 /api/native/auth/host/challenges：两次登录各发一张令牌，主持人令牌的 kind 为 host，同一个 QQ 账号可以既当玩家又当主持。主持入口在核销登录码时就检查授权，没被授权的账号拿不到令牌。
QQ 登录沿用已运行的 NapCat OneBot 流程：客户端调用 POST /api/native/auth/challenges 取得六位挑战码，用户在指定 QQ 群发送“活动登录 123456”，网关用 X-Gateway-Token 调用 POST /api/internal/qq/login 绑定 QQ 号、群昵称与头像。挑战码一次性消费，过期或重放一律拒绝；网关共享密钥用 secrets.compare_digest 校验，真实密钥只从环境变量读取，不写入客户端资源或仓库。登录页始终给出整句“活动登录 123456”：原生客户端提供一键复制到剪切板，玩家不必自己补上“活动登录”前缀或手抄六位码。
挑战完成后，原生客户端取得 Bearer 长令牌并由 flutter_secure_storage 持久保存；查 login_tokens 表，共用账号、过期与撤销语义。客户端启动时调用 /api/me 核对，只有 401 才清除本地令牌。玩家退出只撤销当前令牌，不删除账号。
网关对失败的登录尝试一律在玩家发言的那个群里回一句，不让群里只有沉默：绑定被拒时把后端 HTTPException 的原因转述成「某某，登录失败：登录码无效、过期或已经使用」这类文案（后端不可达则回「服务端暂时不可用」）；「活动登录」写了但码不是 6 位数字时回格式提示。回复只发回来源群，多群同时监听时不会串群；非登录内容的群消息保持不回应。

2. 账号、参与身份与开放参局

账号（accounts）与对局参与身份（participants）分离：账号记录 QQ 号、群昵称与头像，长期有效；参与身份属于单局，记录玩家或观战、席位、禁言与本局拉黑状态，通过 account_id 关联账号。
新对局建立时为不可加入状态。主持人管理动作 room.open_join（短名“开放加入”）宣布对局可用并产生全体系统消息；已登录账号通过 GET /api/lobby 看到当前开放对局，用 POST /api/games/{game_id}/participations 选择 player 或 spectator，无需主持人审核。
选择玩家时，仅在首次发牌前随机占用空席；七席已满或已发牌则拒绝并保留“观战”选择。选择观战不占席位。以 (game_id, account_id) 唯一约束保证同一账号不能重复加入或重抽席位。
替换旧的统一邀请码：不再有邀请码 /join 与客户端邀请码文案。入场靠主持人「开放加入」+ 账号主动参局，或对局内非观战身份从「在线玩家」名单向某个在线账号发定向邀请（受邀者仍须等开放加入后才能接受入席，可拒绝；同一局同一账号只保留一条待处理邀请，10 分钟未响应即失效）。刷新、换设备登录和重连都按 QQ 账号恢复原参与身份，不重新分席或重发牌。

创建一局时：
- 主持人先确认本局11名魔典角色（系统随机排列），再在客户端查看已部署插件的名称、版本、说明、分类与依赖并选择可选插件；内置和外置必选不能关闭，外置默认启用/默认禁用按类别初选，缺少依赖不能启用。服务端在建局前复核所有依赖并锁定本局 ID/版本清单；没有明确魔典名单不由程序臆测。
- 系统先建立7个空席，不在创建时发放角色牌。
- 七名玩家各自主动加入后随机入席。七名玩家首次全部准备后，系统一次性随机分配14张牌到7个席位，每席2张，确保可可与雪莉、米莉亚与希罗不在同一席位，且艾玛、米莉亚、亚里沙三张牌分别落在三个不同席位的下层。发牌同时生成魔女阵营：随机选定两个不同席位作为 A、B，且不选持有艾玛、米莉亚、亚里沙或雪莉的席位，无论雪莉在上层还是下层；私下告知这两人「你是魔女阵营」（第1天 A 当值、第2天 B 当值），并常驻“我的”页状态卡。
- 发牌后玩家只能看到自己的两张牌，私下选择上下顺序并再次准备；七席都完成第二次准备后主持人只需「开局」，不再二次选择插件。开局即向所有参局者公告全部已启用插件的名称、版本与介绍。正式外置插件「梅露露傀儡平衡性调整」默认禁用；启用后真正被梅露露控制的傀儡不占投票席位也不能代投，投票开始时冻结其数目，结算用公开的原有席位数与门槛，3/6（1傀儡）公开为4/7、2/6公开为2/7，不发布傀儡身份。清单及各模块版本随本局存档保存，不随希罗回溯改变；插件私有机械状态随回溯还原。旧局自动补齐当时的内置角色，不自动启用可选模块；存档模块版本、依赖或顺序与服务端不符时仅该局读写返回409并暂停计时，部署匹配版本或编写显式迁移后恢复。
  对局内插件公告使用与技能公告同款卡片，卡面只显示名称和版本；点击打开详情后才显示具体规则介绍。
- 两轮准备和排序期间，公开席位与聊天均不显示角色头像；玩家自己的牌和明确授权给主持人的信息仍按权限可见。

发牌后凭证丢失或玩家被移出时，由主持人让观战者接管空席；接管不重抽角色，也不重置技能次数与既有裁定状态。角色牌、技能次数和既有裁定状态不因换操作者而重置。

对局数据只保留到下一局建立为止：主持人建立新对局或点击「一键初始化」时，清空对局库中的参与身份、进度、聊天与证物；QQ 账号、玩家登录令牌和主持人登录都保留，下一局重新开放加入即可参局。账号与令牌保存在独立的 auth.sqlite3，不受清空对局影响。

3. 观战与替补

观战账号不占7个玩家席位，不获得角色牌，也拿不到玩家或主持人的游戏行动。观战取得与主持人相近的只读牌桌：能看到全席双牌、生死、状态、阶段和结果，但不返回玩家/主持人行动、主持人待办、参与者管理或席位代操作；所有游戏命令、证物提交和管理请求都在服务端拒绝。
玩家可在客户端「我的」页选择「离开房间」，确认后通过 POST /api/games/{game_id}/leave 离开并返回大厅，不退出 QQ 登录。玩家请求必须带 expected_version，状态变化时返回409，刷新后重新确认，不自动重试。离开与主持人 room.kick（不拉黑）共用移出逻辑：解除本局参与身份、腾空席位，候场时清除准备状态；角色牌、技能次数、裁定状态与已提交行动保留，不重抽、不重置。开局后回席仍需主持人安排观战者替补接管。观战者保留「退出观战」入口：仅解除观战参与身份，不影响席位，之后仍可再次观战。两种离开都会记录系统消息。
观战者只读访问本局所有频道：公开讨论、全部玩家与主持人私信（含待接受与已结束频道）、观战频道（channel_id=spectator）及系统与定向私密消息；历史分页、重连同步和实时推送使用相同权限，公屏筛选始终表示真正的公开讨论。所有频道均不能发送文字、图片或表情，不能广播输入状态、撤回消息、创建、接受、拒绝或结束私信，私信邀请名单不包含观战者。主持人仍可在观战频道发言，玩家仍看不到观战频道或他人私信。观战者接管席位成为玩家后，立即恢复该席位原有的公屏与私信资格。
观战的全牌面视角不扩展证物授权：观战不能提交证物，也不能读取未获准的证物附件。
替补由主持人从观战者中选择，并指定一个待接管席位。操作前展示将继承的牌、状态、剩余次数、已提交行动和可见历史，由主持人确认私密信息范围。
接管不重抽角色、不重置技能；是否保留已提交行动、是否继承原操作者私密历史都由主持人确认。原玩家对该席位的参与身份失效，新的操作者接管原席位。公开通知只说明某席位更换操作者，不公开双牌或私密信息。
本局拉黑只让该账号在本局的参与身份失效，不删除其全局 QQ 登录，也不影响其在下一局重新加入；踢人同理。不使用IP或设备指纹。

4. 掉线与在线状态

对局内每个参与身份记录在线连接数；同一人开两个标签页，关闭其中一个不算掉线。最后一条连接正常关闭或心跳判定断开后，该身份只标记为离线，不再广播“已掉线”；恢复连接也不再广播“已重新连接”。掉线与重连只改变席位与在线名单上的在线标记，不产生聊天记录里的系统消息。
应用心跳建议每20秒一次，连续60秒未收到响应判定连接失效；正常关闭可立即识别。重连后重新下发当前获准查看的状态与消息。
掉线不是死亡、弃票、投降或技能放弃，不自动结算。主持人可以等候、按规则警告并在30秒后结束该行动，或邀请替补。状态与已确认行动不因网络断开丢失。
不设计房主转移、选举或自动换主持人；固定主持人的身份和权限不会因浏览器刷新改变。

账号级在线名单独立于对局在线状态：大厅里没有 WebSocket 的账号靠定时轮询 /api/lobby、/api/online 续期，对局内连接由 pong 续期，最近 60 秒内有活动即视为在线（realtime.presence）。这份名单只用于大厅与「状态」页展示和定向邀请，不参与任何规则判定；不展示 QQ 号或令牌。
Android 玩家端收到新的定向对局邀请时额外发一条系统通知（通知栏“收到对局邀请：某某邀请你加入对局”），因为大厅轮询在应用切到后台时用户看不到界面横幅。判定沿用同一次 /api/lobby 轮询：客户端比较这次与上次的邀请 id 集合，首次刷新只记基线，登录后已堆着的旧邀请不重复提醒；同一账号只保留一条通知，点开进入应用。通知走已有的原生 MethodChannel（与保活同一个通道），Android 之外的平台是空操作，不引入本地通知插件；用户名与通知权限由系统设置决定，用户关闭通知不影响大厅里的邀请本身。

5. 主持分级与授权

主持权限不再来自共享密码，而是与 QQ 账号绑定：
- 内置管理员由环境变量 GAME_ADMIN_QQ 指定（英文逗号分隔多个 QQ 号），恒为 5 级；没有配置它时没有任何账号能登录主持人端，服务端启动时会打一条警告日志。
- 其余账号的等级存在 auth.sqlite3 的 host_authorizations 表（账号 id、等级、授权人、授权时间、该账号建立的对局 id、作废时间）。4 级可以授权/取消 1-3 级，5 级可以授权/取消 1-5 级；改级等于重新授权（会清掉「一局已用完」）。
- 等级含义：1 级主持 1 局；2 级永久组织权；3 级另有稀有度 1-3 的成就；4 级另有稀有度 4 的成就与 1-3 级授权权；5 级是系统管理员（公告、全等级成就、1-5 级授权）。1-2 级不能碰成就。
- 1 级的「一局」在他建立的对局结束时算用掉：对局落幕、被一键初始化或被下一局取代，都会立刻作废该授权，列表里标成「已用完」，需要重新授权才能再建局。
- 等级每次请求都重新核对：授权被取消或用完时，旧令牌立即不再给出主持人身份（接口回「主持授权已失效或已被取消，请重新登录」）。
- 内置管理员的等级来自配置，界面既不能改也不能取消（409）；4 级看不到也管不了比自己高的授权。授权页显示 QQ 号以便区分同名账号，其余名单仍不含 QQ 号。
- 一个服务实例仍只主持一局，但持主持授权（或内置管理员）的账号不止一个，所以建立对局时把主持身份写进对局状态（账号 id + QQ 昵称快照，字段 host）：对局内一律显示「主持人(昵称)」，玩家分得清当前主持的是哪个账号。
- 主持人不是参与身份，所以对局内的「主持人」是固定 id host：频道成员、私信标题与发给玩家的 channel.create 选项都用本局记录的展示名。
- 主持授权只说明「有资格主持」：持授权（或内置管理员）的账号进入某一局还要先确认一次。POST /api/games/{game_id}/host/enter 把这个账号记进对局状态（字段 host_entries），服务端从这一刻起才按主持人放行；未确认时任何主持账号拿到的都只是最窄的观察者投影。
- 未确认进入时拿不到：全席上下牌与 current_card_id、主持人面板（待办/夜间行动/投票/日志/魔典）、本局私聊频道与消息历史、挂在自己名下的私密情报；也执行不了任何命令，禁言、移人、替补、席位代操作、终止对局全部拒绝（403「请先确认进入本局管理界面」），客户端因此也不会显示禁言等房间管理入口。玩家与观战者的可见范围不受影响。
- 判据只有一处：game.state.host_capable(actor) 读身份上的 host_entered（auth.actor_for_token 每个请求重算），投影（game/views、app/views）、消息可见性（storage）、证物（evidence）、成就佩戴（achievements_api）与命令授权（api.command/room_command/authorized_as_seat）都走它，避免漏掉某条路径。
- 确认成功时服务端立刻把升级后的完整主持投影推给这一局的连接，所以原生客户端确认后无需刷新。
- 不是建立这一局的主持人确认进入时，另外在本局发一条系统公告（全场可见的 alert：谁进了谁建立的对局的管理界面）；同一账号在同一局只发一次，建局主持人自己进入不发，没有记录主持身份的旧局不做越权判定。它只写在这一局的消息记录里（在场的人当场都能看到），不写大厅的全服公告库。
- 原生客户端启动或进入对局后不直接展开管理界面，先给一页「进入对局管理界面」的确认；确认要等服务端登记成功才放行，所以公告与放行一定早于主持人看到任何私密内容。确认页另有「退出登录（改用玩家身份）」，方便误入主持端时切换。确认状态记在服务端（字段 host_entries，按账号+对局），所以同一账号换令牌、重新登录或重开应用都不再要求确认，只有新一局才重新要求。
- 主持人可随时返回大厅：对局标题栏、入局加载页保留入口，管理确认页在「确认进入管理界面」「退出登录」下方另加「返回大厅」。返回仅断开本设备视图，不结束对局或退出登录，后续大厅轮询不自动拉回；主动入局才重新绑定。大厅当前对局只显示「进入主持人视角」，直接读取主持人投影，不调用玩家加入或观战接口，管理权限仍需服务端确认。
- 每次进入对局时，「正在进入对局」页先请求客户端版本信息，有新版本或强制更新要求就弹现有更新窗口；关闭后继续检查资源包，再显示对局。恢复登录、返回大厅后再次入局与换局均检查，普通刷新和断线重连不重复弹窗；版本检查失败不阻塞后续资源检查，过旧版本的玩家加入限制仍由服务端执行。
- 主持人与玩家共用同一个 QQ 账号，成就（含佩戴）本来就是账号级的：对局内主持人头像旁也显示佩戴徽章，点开头像能看同一个账号的成就摘要。

四、玩家页面与聊天

1. 页面清单

入口页：游戏名称、简短玩法、邀请码输入、主持人登录。
候场页：7个席位与准备情况、自己的双角色卡、上下交换按钮、公开称呼、准备按钮；穗乃香另可在开局前私下记录一次示人角色。公开头像由上层牌决定，玩家不能自行指定。准备进度只公布已准备人数，玩家看不到具体谁已准备（会发现上层牌锁定时机）；主持人仍看得到每个席位的准备状态；穗乃香在排序阶段能看到已准备玩家的上层角色名（仅文字，不带头像）。
玩家桌面：顶部日夜与阶段，中部公开席位/聊天，自己的角色与私密信息，当前可操作的行动面板。
主持人桌面：相同公开桌面，加全量角色状态、所有行动、裁决待办、魔典、13水、投票、阶段推进、替补管理。
结算页：获胜方、特殊胜负、主持人裁定说明。已结束或清空终止的对局自动留档到独立历史库，任何已登录身份均可查看全部身份、私聊、观战聊天、定向情报与主持人日志；进行中对局仍按原权限裁剪。消息与有效日志不再截断为最后400条。历史列表与详情右侧提供可拖动滚动条；详情右上角可通过 Windows/Android 系统保存窗口导出 UTF-8 BOM 的可读 TXT，包含结果/个人失败、规则模块、全部参与者、最终上下牌与状态、有效行动和裁定、证物文字及完整消息的时间/频道/原接收对象。TXT中的图片只记录存在说明，不包含图像像素；撤回内容不恢复。旧档在原结束局仍在时补回现存资料，已丢失的内容明确标为不完整，不伪造。
大厅：对局入口、在线玩家、按等级出现的入口（我的成就 / 成就管理 / 主持授权 / 公告管理）与公告列表。

2. 头像与身份不混用

登录席位、真实角色牌、公开示人身份是三个不同概念。
自己的角色卡和主持人私密面板使用真实角色头像。公开聊天只使用已公开或依规则示人的角色头像；不因为后台换牌、魔女化或下层仍隐藏，就自动向其他人换成真实头像。
尚无公开角色时使用中性的座位号头像，不借某张角色图暗示其真实身份。公开头像始终等于该席当前上层牌的角色：开局时由上层牌决定，下层登场或复活后随当前角色更新，主持人可在席位视图中核对同一结果。穗乃香只能在自己于上层时示人一次，之后公开头像使用被示人角色的图，但这不授予其真实技能；系统不向全场广播“某号示人为某角色”，该记录与开局前的私下选择都只给主持人。对局中主持人始终使用月代雪立绘（原生客户端为 assets/logo.png）；只有大厅里主持人自己那一行按需求随机挑一张角色立绘，进入对局后固定回月代雪。
旧聊天消息保存当时的公开称呼和头像；换牌或回溯不把旧消息重新渲染成现在的秘密身份。

本机标记：长按任意玩家的头像（牌桌席位或聊天里的头像）可标记「魔女 / 好人 / 疑似魔女 / 疑似好人」或清除，五种状态各对应一种颜色，对局中该玩家的名字按标记着色。标记只是玩家自己的笔记：只存在于客户端内存，不上传、不落盘、不参与任何规则判定，退出应用或离开对局即清空，服务端与其他玩家都看不到。首个非平安夜结束后，客户端按服务端自己的夜终公告（「第X夜：<当夜出局的角色牌>」）固定展示一次「如何标记他人」的教程；平安夜公告、聊天与私密信息都不触发。

3. 聊天交互

他人消息：左侧头像 + 公开称呼/座位号 + 左对齐气泡。
自己消息：右对齐气泡，可显示自己的公开头像。
主持人公告、阶段变化：居中系统消息，不伪装成玩家发言。
公屏与私信分开：公屏讨论、私信频道、系统与私密信息各自独立列表和已读游标，不再把所有可见消息混成一条时间线。原生客户端在消息页顶部提供“全部 / 公屏 / 私信 / 系统 / 主持人”分段筛选。GET /api/games/{game_id}/messages 增加封闭 scope 查询参数，先按频道权限过滤再分页，因此筛选历史不是只过滤本机最近一页。
“主持人”筛选指包含主持人的私信频道，不是旧版单人主持频道的残留；旧的 host:<参与身份> 频道已随邀请码入口一并删除。
聊天正文长按可复制；本人发送的聊天可不限时撤回，消息保留原 id、发送者和时间，所有获准查看者在原位置看到撤回占位。输入 @ 时可从当前频道可见的占席玩家选择，写入稳定的 `@N号 ` 标签，正文与输入框高亮；服务端按实际频道受众解析提及，仅被提及的玩家收到应用内 @ 未读角标与前台提醒，不发系统通知。
对局内可点击「发送图片」选择本机图片：Android 使用系统文档选择器，Windows 使用系统文件选择器，不申请整库照片权限。原图不超过20MB，客户端自动缩小为100KB（102400字节）以内的PNG，先预览并确认目标频道再发送；动图取首帧。图片以base64保存在消息载荷中，沿用该频道的发言权限、实时推送、历史可见性与撤回规则；点击图片可放大，长按本人图片可撤回。后端只接受100KB以内且尺寸受限的有效PNG/JPEG。
聊天输入区的「证人」「证物」快捷入口只在软键盘展开时出现，并固定在行动入口左侧；其他人输入状态出现或消失时不改变这两个入口的位置。
情报行动（day.intelligence）：运行中的每个玩家席位每天白天可发布一次，整席出局后仍可用；通过统一行动表单填写最多4000字、非空的文字，提交后立即以独立情报卡片向全员公告，不等待主持人裁定。卡片沿用技能播报的边框与布局，显示游戏日、席位、公开称呼和完整正文，不公开角色，也没有技能质疑入口；公告同时加入「证物」的公开事件目录，聊天输入 # 可引用并查看全文。次数按席位与游戏日保存，换上下牌、替补、刷新和回溯到已使用的同一天均不会恢复，新的未使用白天可再次发布；夜间、候场、结束和观战身份不能发布，私信占用及傀儡代操作沿用现有行动权限。

私信频道的生命周期：
- 玩家或观战可以创建一对一或多人私信，创建表单从本局有效参与身份和主持人中多选邀请对象并填写频道名，不经过主持人审核。
- 频道保存 creator_id、status（pending/active/ended）、邀请名单、已同意名单和结束时间。同一非主持人账号同时至多参加一个 active 私信，主持人不受此限制。
- 非主持人发起时，受邀非主持人成员逐人看到“同意 / 拒绝”；主持人被邀请时自动同意。全部受邀成员同意后频道才 active；任一成员拒绝则本次创建取消，且不锁定任何人。
- 主持人发起的频道立即 active，受邀成员无需确认。邀请响应、创建与结束都走服务端动作描述并携带 expected_version。
- 私信 active 后由服务器强制其中非主持人成员只能在该频道发言，并拒绝公屏消息；玩家成员的全部游戏行动也被拒绝。行动区只保留“结束私信”。主持人仍可在任意频道发言、执行行动和管理。
- 任一成员点击“结束私信”即结束整个频道，解除所有非主持人成员限制；断线、刷新或换设备都不能绕过限制。频道转为 active 时向全体发送“甲正在与乙、丙私信”，结束时发送“甲与乙、丙已结束私信”，多人名单使用创建时的公开称呼，不泄露私信内容。
- 频道内消息只给成员与主持人查看，结束后只读保留；替补默认不继承旧操作者的私信历史，除主持人明确勾选继承。
- 已结束的私信不再出现在客户端的频道选择列表里（选中的频道结束瞬间回落到公屏），历史消息仍留在消息流中可回看。
- 天黑进入夜间时服务器结束全部私信频道（含只与主持人的私聊）并公告“天黑，全部私信频道已结束；夜间只能与主持人私聊”；夜间只允许与主持人建立私聊，玩家邀请其他参与者会被服务端拒绝（战斗/邀请表单里只剩主持人一个选项），主持人的邀请对象不受限制。旧数据或异常路径遗留的不含主持人的 active 频道在夜间既不能发言，也不算作“私信占用”，因此不会锁住玩家的夜间行动。
- 整席出局（两张牌都不在场）的玩家与夜间同一条限制：只能与主持人私信。出局者自己不能邀请其他玩家（表单里只剩主持人一个选项），普通玩家的邀请名单里也不再出现出局者，出局者接受非主持人私信、以及他与玩家的旧频道发消息都由服务端拒绝（reason「出局后只能与主持人私信」），主持人不受限；旧频道仍可自行结束以腾出私信占用。出局一律按当前牌现场判定，不单独记账，因此希罗回溯、梅露露复活与主持人回溯让角色牌重新登场后，交牌申请与多人私信资格一并恢复。

views.channels_for() 同时返回频道状态、邀请状态、成员摘要、can_send 与服务端 reason；send_message()、命令分发、历史分页、实时推送与附件读取共用同一套成员检查和私信锁定检查，不能只靠客户端禁用按钮。

发送目标有：公聊、本局的私信频道，以及系统与私密信息通道；不因为属于魔女就默认获得规则未写出的魔女群聊。发给单个或多个玩家的裁定、线索、私密提示走系统信息通道，获准接收者与主持人可读，观战者只读可见，刷新或重连后可随时回看；角色私密状态与证物附件仍按各自授权裁剪。
主持人可查看全部游戏频道。玩家只能接收允许自己查看的消息；观战可只读查看所有频道，但没有任何游戏或频道行动。观战频道选择器允许选中只读、待接受与已结束频道，状态更新不会把已结束频道的选择强制切回公屏；普通玩家的频道切换行为不变。规则限制发言时输入区说明原因并禁用发送，但输入框始终可写：草稿按对局、身份与频道隔离保存在本机，刷新后恢复，提交成功才清除；登出或离开对局时把该账号本机残留的草稿与已读游标一并清除，不在本机永久留存私密内容；不保存密码、QQ 登录码或令牌副本。不靠颜色表达状态。

允许复制粘贴普通文本，不提供回复引用、跳转到来源消息、来源认证徽标或跨频道原消息卡片。粘贴内容一律是发送者自己的一条文字气泡，不带可验证的来源。玩家当然仍可自行转述真假信息。
不提供防截图、防复制、语音、录屏检测或外部聊天监控。文本按文本渲染，不执行HTML；消息长度上限建议2000字，属于正常输入边界。

桌面 Enter 发送、Shift+Enter 换行；手机用明确的发送按钮。发送后清空输入只发生在收到成功确认时；失败保留草稿，不自动重发成多条消息。

原生客户端的发送按钮左侧有表情入口，顺序发言等多行字段同样带表情入口。面板提供 QFace 的静态 QQ 表情（经典 275 张 + 超级 50 张合并为 QQ 表情组），QQ 最近记录固定在上方且最多3行，支持按名称与拼音搜索；QQ 图片随客户端打包，不联网取图。QQ 表情在文本里就是 `[/名字]`（如 `[/微笑]`）这样的纯文本 token：输入框与消息气泡把它画成内联图片，因此草稿隔离、2000 字上限、服务端校验、实时推送与顺序发言的公开流程都不需要改动；只有名字能在表情总表里查到的 token 才会变成图片，正文里恰好写成方括号的内容不受影响。中文输入法组词期间输入框退回纯文本，组词结束后再显示表情。下载表情独立分目录，发送 MD5 单独消息且不加入最近，详见下方独立资源包说明。
新消息到达时自动切到对话记录（自己发出的消息除外；首次进入不跳转；手机上正开着行动窗口填写时也不跳转，只进记录与悬浮提醒，关掉行动窗口后恢复自动跳转）。两类消息另外以悬浮提醒弹出、可逐条关闭或点开跳到记录：发给你的裁定与私密信息（含只发给被警告席位的「主持人警告」与「警告超时」），以及标记为关键的全场公告（技能声明、出局与复活、质疑结果、处决与投票结果、临死开枪、主持人代操作）。常规进度不再发系统消息：阶段推进靠两端的阶段标题与阶段动画表示，自由发言进度靠「已有 n/所需人数 人请求结束」进度条与 10 秒倒计时表示，提名、顺序发言与私信开合等只进主持人日志或只发给相关成员，避免刷屏。私密信息在客户端是金色卡片：聊天记录里带「私密信息 · 仅你与主持人可见」标签，新到一条时页面顶部另弹一条可关闭的横幅，可一键跳到对局记录；「我的」页常驻「私密情报记录」。客户端顶部常驻一个由服务端下发的横幅（与催办框同一条 action_prompt 通道，文案与时机都由服务端决定）：自己的行动卡住流程时是红色「请求操作」催办（准备、提名、夜间行动、投票、临刑响应等），该玩家正在私聊里时框里额外提示先结束私聊才能操作；没有待办时同一位置向全场通报阶段进度——顺序发言显示「当前轮到 x 号玩家发言」，提名与投票显示「正在等待 x 号、x 号玩家提名／投票」，玩家都做完、流程只等主持人时显示「等待主持人进行操作」，自由发言阶段不提示等主持人（进度由 n/所需人数 进度条表示）；顺序发言时横幅再加一条全场公开的30秒倒计时（剩余秒数 + 细进度条，文案标明「发言或继续输入会重新计时」），本人发言或继续输入后跳回满格，到点由系统自动轮到下一位；夜间只显示「仍有玩家未完成行动」，绝不列出席位，否则等于公开谁有夜间技能。
聊天按需加载较早记录，新增消息不在用户向上阅读时强制拉到底部；显示“新消息”入口。

4. 手机与电脑布局

桌面宽度 ≥1024px：三栏，左侧约220px席位列表，中间弹性聊天/公共桌面，右侧约320px自己的牌与行动。主持人的右栏改为裁决面板，可展开全量角色表。
平板768—1023px：双栏，聊天保留主区域，角色和裁决在侧抽屉中切换。
手机 <768px：单栏，底部“聊天 / 桌面 / 我的牌 / 行动”；主持人对应“聊天 / 桌面 / 裁决 / 管理”。重要待办用数量提示，不把桌面三栏强行缩小。

移动端使用动态视口高度和安全区边距；软键盘出现时输入框和发送按钮仍可见。正文/输入不小于16px，操作区域至少44px；普通页面不横向滚动，双牌在窄屏纵向展示。
目标选择、投票、13水使用和主持人死亡确认显示角色/座位、效果与提交按钮，防止触屏误点。确认属于正常操作交互，不增加身份认证步骤。
焦点可见、按钮有文字、头像有替代描述、日夜/死亡/离线均有文字标识。动效轻量，支持减少动态效果；不使用大规模特效或自动播放音乐。

5. 原生客户端（Flutter）

目标平台只有 Android 玩家端与 Windows 主持人端。使用 Material 3 与 Flutter 自带的导航、动画和 HapticFeedback，除 flutter_secure_storage、shared_preferences 外不引入状态框架、路由框架、动态 UI 包或游戏引擎。
应用显示名与窗口标题统一为“魔法裁判”：Android 用 AndroidManifest 的 android:label，Windows 用 runner 的窗口标题与 Runner.rc 的 ProductName/FileDescription；可执行文件名保持 ASCII 的 seven_double_client.exe，避免非 ASCII 文件名带来的工具链问题。
界面字体统一为 HarmonyOS Sans SC（简体中文，随包内置 Regular/Medium/Bold 三档，约 23MB），由 pubspec 声明字体家族并在 ThemeData 的 fontFamily 启用；网页首页同样使用该字体，由 public/fonts 同源提供并配 @font-face。字体随包内置是为了让原生客户端在离线或首屏时都能正确显示中文，不依赖系统是否安装。
服务地址只接受无路径、查询和片段的服务根地址；loopback、localhost 与私有网段可以用 HTTP，其他主机必须 HTTPS。HTTP、/api/live 与头像地址都从同一根地址派生；请求超时 25 秒，写失败后只拉取一次状态核对，绝不自动重放。
一个 GameApi 负责 QQ 挑战、me、大厅、主动加入、状态、命令、消息分页与发送、证物和登出；HTTP 请求一律不跟随重定向（ServerEndpoint 只校验根地址，跟随 3xx 会让带令牌的请求降到任意明文主机）。一个 LiveConnection 消费 sync/state/message/ping，65 秒无事件按 1、2、4、8、15 秒退避重连并按消息 ID 补齐；单帧损坏只丢该帧、补齐失败不断线，但握手被 401/403 拒绝属于身份失败，立即停止重连交给登录流程。DTO 只解码服务端裁剪结果，不在 Dart 里重算规则。
玩家“对局”页上方是可分页消息列表，下方固定聊天输入和短行动条；点击 2—4 字短名按钮弹出底部表单，展示完整说明、字段与最终确认。软键盘弹出时隐藏行动列表、只保留紧凑行动入口与未读提示。行动是否“新”按服务端描述的规范化键比较，首次同步只建立基线，不把旧行动伪报为新行动。
顺序发言阶段按服务端公开 speech_order 横向展示席位顺序、头像和角色名；每次发言权开始时，服务端先持久保存并推送 speech_turn 消息，客户端在该位置以两段横线包住座号、当时的公开头像和角色名，第一句之前即显示。预提交正文同样放在其起点之后；阶段结束、重连或重启后历史位置不变，也不受换牌或替补影响。旧局已过去且未记录起点的轮次不猜测补造；仍在发言的旧局从下一次引擎同步开始记录。候场及未授权角色不补全显示。新行动仅在首次同步/重连基线之后按服务端 action description 弹出预览教程；同批多个新技能或行动合并在一个可滚动窗口中展示，关闭一次即可，取走教程不清除原有新行动角标。同一局已看过的行动 id 再次出现或说明变化时不重弹，准备/取消准备、开放/关闭加入、自动推进开关不弹。
行动说明由服务端下发（actions 描述里的 description），客户端只负责渲染，不在 Dart/TS 里重算规则：每个行动 id 都有一条固定说明，随局面变化的行动在服务端按当前状态改写。因此投票行动直接写明本轮有几名候选、分别是谁与所需票数（说明给出候选清单、分母与门槛），表单里每个候选一行，行上带该席的座位号与角色卡，客户端据此画头像与角色名；夜间技能、白天技能和主持人裁决各自给出当下这一步做什么、按什么阈值结算；开闭加入、开枪命中率与剩余子弹同样如此。缺说明的 id 属于后端缺陷，checks 会断言玩家与主持人此刻能拿到的每个行动都带非空说明。
行动表单恢复草稿时，只保留当前字段与固定 payload 允许的键；回溯后候选减少不会带上已消失的选票字段，仍有效的选择继续保留。已打开表单提交前按本人、主持人代操作或傀儡身份核对当前行动描述；候选、选项或权限变化时保留草稿并要求关闭后重新打开确认，不借刷新后的版本号提交旧表单，不自动重试。
质疑行动说明逐条写明被质疑的座位号、技能名与失败判负风险。点击技能公告打开详情后，仅在服务端当前提供该声明的质疑行动时显示「质疑此技能」；按公告的声明编号打开对应的统一确认表单，不按座位或技能名猜测、不退回其它声明。声明结束或权限失效时，详情中的快捷入口随状态更新收回。
主持人收到私密情报时，新消息横幅与记录中的私密信息卡片都标明「发给几号玩家」；多人接收逐一列出座位号。接收身份仅由服务端向已确认进入本局的主持人下发，按完整参与者名单解析（含已替换身份），不把旧情报标给替补后的新身份；普通玩家不取得接收名单，仍显示原来的本人私密提示。
手机底栏固定三项并采用悬浮圆角样式：玩家为“对局 / 状态 / 我的”，主持人为“对局 / 状态 / 管理”。新消息、新行动或警告反馈到“对局”，未查看的阶段/牌桌状态反馈到“状态”，双牌私密状态反馈到“我的”，主持人待办反馈到“管理”；角标同时使用数字和颜色，切到对应内容并实际查看后才清除。
Android 对按钮确认、频道切换、收到需本人处理的新行动或警告分别调用 selectionClick、lightImpact、heavyImpact；Windows 静默。应用在后台、系统关闭触觉或系统开启“减少动态效果”时不做动画和振动。阶段变化时弹出一次全屏阶段动画，显示日数、昼夜和阶段名；首次进入或重连不重复旧动画。
每个席位同时绘制两张圆形头像，左右重叠约 50%，当前使用的牌位于顶层；未获授权的牌显示“?”，已出局的身份头像灰白化。夜间延迟公开期间严格使用服务端现有的 avatar_role_id/previous_role_id/cards/current_card_id，客户端不得从动画顺序猜测隐藏牌；自己的“我的”页始终完整显示两张真实角色卡与状态。
每个行动都配图标：Material 图标为主，语义不贴合的再补自绘 SVG（assets/icons）。映射表在 lib/src/app_icons.dart 里，check 会断言它覆盖后端声明的全部行动 id，新增行动漏配图标会失败。
需要选择时使用自绘选择界面而不是系统下拉框：选玩家显示「头像 + 名字 + 角色名」，出局者灰白化并标注；选行动显示图标、短名、分组与说明；选魔典用 13 张立绘卡片并强制正好 11 名。行动选项的 value 是参与者 id，座位视图因此额外暴露 participant_id，客户端据此把选项关联到席位与角色（玩家视角拿不到别人的牌，会显示“角色未公开”，这是权限正确表现）。
主持人登录后进入独立主持人壳，“管理”按“当前待办 / 流程 / 玩家 / 私密信息 / 纠错”分组，顶部显示阶段、自动推进与真正阻塞项，并列出本局魔典。所有按钮只显示短名，点击后才展开影响、目标、参数和确认；主持人仍通过同一 actions 描述推进、警告、裁决、代操作、替补、踢人/拉黑和胜负确认，席位视角读取后再代操作，不能提交该席当前没有的行动。观战只复用只读牌桌，不挂载管理组件。
新建对局必须先经过魔典选择：Flutter 端 CreateGame 不再静默使用默认名单，主持人先选满 11 名并确认一次后才建局。
对局页的快捷操作：点击消息头像、发送者名字或牌桌里的席位卡，都会打开该参与者的快捷菜单。玩家看到「查看角色技能与状态」「发起私信」；主持人另加「一键禁言/解除禁言」「警告该席位」「移出本局/拉黑」。快捷操作不新开协议：它按 payload 复用服务端 actions 里对应的描述并预填目标，危险动作仍是红色标记，仍然只提交一次。
角色技能详情展示的是公开规则（catalog 的 normal / witch 与角色的公开身份、生死、在线、禁言状态），不展示别人的下层牌、剩余次数等私密信息。角色目录随游戏状态一起读取并缓存，取不到只影响详情文案，不影响对局流程。
自己当前使用的牌换人、或开局锁定上下牌时自动弹一次角色卡介绍（内容是该角色的好人方技能与魔女化技能，与点头像看到的详情同源）：候场转入进行中（status 由 lobby 变 playing）时弹「开局 · 上层牌」，说明开局起使用上层牌、上层牌出局后才使用下层牌；下层登场、复活和换牌都改动 current_card_id，因此都覆盖。判定只在客户端比较自己 self.current_card_id 的前后值与对局状态，首次同步/刷新/重连只记基线不弹窗，同一个角色连续两轮不会重复弹；协议不变，服务端不需要新增字段。
主持人登录后进入独立主持人壳，“管理”按“当前待办 / 流程 / 玩家 / 私密信息 / 纠错”分组，顶部显示阶段、自动推进与真正阻塞项，并列出本局魔典。所有按钮只显示短名，点击后才展开影响、目标、参数和确认；主持人仍通过同一 actions 描述推进、警告、裁决、代操作、替补、踢人/拉黑和胜负确认，席位视角读取后再代操作，不能提交该席当前没有的行动。观战只复用只读牌桌，不挂载管理组件。
主持人另在对局页顶部有一条快捷工具栏，直接给出当前真实可用的高频动作（开放/关闭加入、推进、暂停自动、警告、禁言、建私信）——只显示服务端此刻确实给出的动作，缺席的自动隐藏，不必切到“管理”页。

六、七双对局与裁决流程

1. 对局主线

建局建立空席 → 发放共用玩家码和观战码 → 七名玩家入场并首次准备 → 系统私下发放14张牌 → 玩家调整上下牌并第二次准备 → 主持人开局 → 魔女化 → 夜间行动 → 夜间结果与证物 → 自动排定的顺序发言 → 自由发言 → 提名/投票/处决 → 天黑，循环直到主持人确认结局。
魔女化前三天按开局生成的魔女阵营执行：第1天转化 A 的当前牌、第2天转化 B 的当前牌（两席由发牌排除持有艾玛、米莉亚、亚里沙或雪莉的席位），第3天优先艾玛：艾玛存活则强制转化（不论层数与当前牌状态），艾玛已出局则由 A、B 中仍可转化的一位接替（按席位号取第一个合法者），不退回魔典；第四天起按已随机排列的魔典找第一个合法目标：存活、尚未魔女化、当前在上层，且另一张不是原始米莉亚或亚里沙。另有一个默认关闭的主持人开关「汉娜魔化」，只在第三天入夜前可改：开启后，第三天夜里若汉娜在场上、曾经绑定过雪莉且当前已解绑、艾玛不在场，则由汉娜覆盖当天魔女人选。命运席位无合法目标、魔典耗尽或其他规则未定情况交主持人处理，不能把整场目标顺序每天重新洗牌。
好人的胜利条件是 A、B 两个魔女阵营席位整席出局（单张魔女牌出局不算）：这样阵营席位可以用另一张牌在第三天再次魔女化，胜负只在两个玩家都出局时结算。
每个阶段展示“当前谁需要做什么”，阶段标题右侧同时给出该阶段的简要提示（谁该行动、点哪个按钮、其他人是否只需等待），主持人面板另列出完整的待办清单与当前行动者。玩家主动确认后提交；可放弃的行动有“放弃并确认”，不以断线代替放弃。夜间开始时，本夜没有任何可执行技能的席位自动按“放弃并确认”处理并私下告知，只有真正还能行动的席位需要提交，因此魔女可可始终是最后行动者。主持人只对当前确实卡住的席位启动30秒倒计时，可逐个警告或一键警告全部；到期按未操作处理。待办列表里属于「警告」的条目（夜间未确认、顺序发言、提名、投票、临刑响应、希罗回溯）直接以「警告30秒」按钮呈现，点一下就对条目里那个席位生效，不再先打开表单再提交；面板上的「警告：30秒后结束该玩家操作」仍保留，用于手工选席位或一键警告全部。倒计时用截止时间，刷新不会重新获得30秒。
系统自己知道做完的阶段（魔女化检测、夜间行动、最后夜间行动、顺序发言、提名、投票、处决前响应）在无人待办时进入5秒倒计时，到点由系统推进到下一阶段，不再等待主持人点击；所有客户端都显示“自动推进 · 剩余N秒”。出现待裁定事项、行动者重新卡住，或主持人暂停自动推进时倒计时立即撤销。主持人面板常驻“暂停自动推进/恢复自动推进”，暂停后该阶段只由主持人手动推进；主持人手动推进同样可以随时打断倒计时，并且是强制推进：阶段开始满45秒后，未完成的玩家行动按超时（视为放弃）处理，提前写好的发言照常公开；玩家已经完成时无需等待45秒。自由发言、夜间预结算、夜间结果、天黑与胜负确认等需要主持人判断或宣布的阶段，仍由主持人推进。顺序发言的顺序也由系统直接排定，不再需要主持人先点一次排顺序：本夜出局者最先，其余玩家在顺序与逆序两个环里取让魔女化玩家更早发言的一侧（speech_plan 以出局席之后那一席为锚点、按座位顺/逆序绕圈后把出局者提到前面比较），没有魔女化玩家时取顺序；主持人仍可用「排发言顺序」手工改起点与方向。
顺序发言同样可以预提交。未轮到的席位有两个选择：点「本轮不发言（跳过我的顺序）」表示这轮跳过，轮到其顺序时自动略过并公开记录“X号本轮不发言”；或点「提前写发言（轮到你时公开）」，在弹出的文本框里写下发言内容；内容先私下存好，轮到他/她时系统才自动以其本人身份公开发言消息（与普通发言同一样式，头像与称呼一致），同时其顺序自动略过，写得早的人不会提前曝光。两者都是一次点击直接生效、不需要二次确认；这两个入口只提供给还没轮到的席位——当前发言人自己直接在公屏发言、再点「结束本次发言」推进顺序，讲完的席位在本轮结束时即记为已处理，行动表里不会再出现这两个预提交入口。所有人都提交后发言阶段立即完成，配合自动推进无需主持人点击即可进入自由发言。预提交按天记录，天黑进入下一夜时清空。本夜出局但下层仍能行动的席位照常按顺序发言；两张牌都已出局的席位不再排进发言顺序，自动排定与主持人手工调整都跳过它。顺序发言还有一份对全场公开的30秒计时（`public.speech_deadline` / `speech_deadline_seat`）：轮到的席位一确定就开始计时，横幅对所有人显示还剩几秒；当前发言人在公屏发言、或继续输入（「正在输入」帧）都会把计时重新拨满30秒，30秒到点由时钟任务自动把发言权顺延到下一位并为下一位重新计时，主持人不必逐个警告。它挂在 `public` 里随状态下发，本地按截止时间逐秒刷新，所以不依赖服务端每秒推状态；计时重置只改这一份公开倒计时、不抬版本号（输入是瞬态信号，抬版本号会把别人正在提交的行动频繁判成冲突），但会补推一帧状态让全场看到新截止时间。离开顺序发言阶段、整轮结束或希罗回溯恢复时间线时，这份计时立即清除。
主持人的待办列表始终列出「完成当前阶段 / 推进」这一项（夜间预结算已有同名专属待办，不重复），并标出当前阶段名与当前是否可以推进。夜间行动、可可最后行动、顺序发言、提名、投票、临刑响应、夜间结果玩家待办等阶段，只要仍有玩家未完成且阶段开始不足45秒，服务端就在任何超时结算之前拒绝强制推进；自由发言以已有结束请求标准判断完成（满编至少6席，不足6席则全员）。真正进入新阶段或回溯（包括同阶段）重新计时，普通行动、换发言人、保存快照与重读已有存档不重置。阶段起点以 public.phase_started_at 持久保存，旧局缺字段时首次读取补齐一次安全起点。已完成的阶段立即可推进，30秒警告与无人待办后的自动推进不受45秒限制；待裁定事项、胜负宣判与交牌审阅仍拒绝推进。「夜间结果与证物」阶段还没决定的梅露露复活同样受45秒保护，允许强制推进后按超时放弃，game["night"]["revive_declined"] 记住本夜已放弃并关闭入口。强制确认其它夜间行动刚解锁可可时止于新阶段，不在同一次推进里跳过她的行动窗口。
需要人工结论的地方显示待办并等待主持人，不随机猜一个结果，不用“默认无事发生”跳过未决效果。

2. 夜间行动与死亡前预结算

第一步：收集普通夜间行动及放弃确认；仅启用「艾玛·寻宝」外置插件时，未魔女化艾玛可选择寻宝，清空本席其他夜间选择并锁定本席当夜选择（不锁全场），系统立即抽取1/5地雷结果并私下通知本人和已确认主持人。
第二步：在场的魔女可可每晚开始时自动获取魔典与全员阵营两条私密信息。阵营复用 state.witch_faction：A、B命运席位为魔女阵营，其余为好人阵营，包含已出局席位，不按当前牌是否魔女化判定；信息分别沿用中毒信息骰，失败时阵营名单错移一席，不向本人披露真假。仅本人及已确认进入本局的主持人可见。其他人确认后将夜间行动提供给可可，再允许可可最后提交；普通可可仅在信物受赠者明确授权后看到对应行动。
第三步：系统只为可可的「赠送信物」抽取1/2中毒效果骰（其余技能一律不吃中毒骰），并固定亚里沙左右邻座各自的1/2负伤结果；再预结算魔女刀、额外攻击、全场攻击、庇护、玛格爱人负伤与其他伤害。夜间死亡不抹去死者当晚已正常提交的行动。
第四步：只有伤害处理后仍会死亡，才检查米莉亚替死或希罗回溯；两者都不再掷中毒骰，直接触发，但全场攻击一经锁定生效，该夜任何死因或主动出局均不触发希罗普通或魔女死亡回溯，也不消耗对应额度。米莉亚每晚必须预选一名玩家换血，该目标一直保留到她下一次有效换血；其换血对象在预结算中出局时，把致其出局的那次普通攻击转移到米莉亚牌并重算（处刑、质疑失败与殉情不走替死）。希罗普通身份即将死亡时自动回溯一次；魔女身份另有一次独立额度，可主动出局，回溯不撤销自身魔女化。锁定前及非清场夜的回溯保持原样：夜间预结算致其出局时系统立即回溯到前一天顺序发言，白天死亡回溯到前一天自由发言，找不到该时点则回到开局；回溯一旦发生就返回“已回溯”信号，调用方不得再写回阶段或快照。
第五步：同一份预结算反复检查受影响的结果，但不重复消耗技能次数或重新抽取已固定的概率（中毒效果骰只存在于信物与信息类，预结算重算不会重复掷骰）。出现规则未说明的冲突才转为主持人待办。
第六步：主持人审阅最终结果、雨夜脚印、四人疑似凶手名单、复活/傀儡及相关连锁，确认后发布允许公开的死亡和证物信息。未揭晓的死亡不先推送再撤回。
魔女化艾玛的全场攻击正常结算后进入夜间结果阶段，即判艾玛单独获胜、其余玩家落败；她当夜被魔女刀打出局、攻击被庇护挡住或已有席位出局都不改变结果。提交或预结算尚未完成时不提前判胜；全场攻击一经锁定生效，希罗普通或魔女死亡回溯均不能撤销整个夜晚及全场攻击标记，同夜其它伤害或主动出局也不能绕过限制，且不消耗对应额度。上述限制仅针对希罗技能，不改变主持人的特殊手动回溯裁定。胜负仍由主持人处理完待裁定事项后宣判。

夜间出局不在夜间阶段公开：本夜出局公告、头像切换与出局标记压到第二天顺序发言开始时统一公示。白天发生的出局仍当场公示。
死亡公告由服务端统一写明“座位号 · 出局角色名”；夜间排队到天亮公示，白天即时公示，两条路径不由客户端猜测身份。这里的角色名取该席的**公开头像**而不是真实牌：示人的穗乃香出局时公告与死亡卡片都只写她示人的角色，示人身份不得由公告说破。

启用「艾玛·寻宝」插件时，寻宝安全者在对应白天不能成为魔女刀、蕾雅长矛或提名目标，但仍会受到全场攻击。亚里沙与玛格写明的“负伤一次”只限制该技能当次造成的负伤次数；负伤状态照常累积，已有负伤时再次负伤即无条件死亡。

3. 双牌与回溯

席位下保存两张实际角色牌，牌有自己的持有人、层次、生死、魔女化、伤势和技能使用状态；不能只给玩家一个“死/活”字段。
一张牌出局后才能使用下层牌；同一玩家同一半天最多出局一张牌。目标究竟跟随人还是跟随被交换的牌、下层在本阶段的可行动时机等无明确说明的情况，生成具体裁决项让主持人处理。

希罗回溯记录好人与魔女两次独立额度，各最多一次；额度已用不会被自己的回溯恢复。魔女回溯保留自己的魔女化。
回溯由系统在希罗死亡预结算时自动触发，不在行动面板中等待本人选择：夜间回到前一天顺序发言、白天回到前一天自由发言，找不到该时点则回到开局保存的最早快照。
恢复前一天对应游戏时间点的牌、普通技能次数与其他可回溯游戏状态；玩家的记忆及已收到的聊天/线索记录不删除。雪莉对汉娜的绑定、安安大招负面效果等精神系效果单独保留，不被快照覆盖。
回溯不恢复旧邀请码、被撤销的会话、旧操作者或网络连接；这些不是游戏时间。回溯后公开标记“游戏时间已回溯”，真实时间顺序的聊天继续保留；不把已发生消息伪造成从未发生。

4. 投票、死亡批次与胜负

主持人确定本轮候选（所有被提名的牌，加上蕾雅决斗强制入围的两张牌），把全部候选一次性列给每名有投票权的玩家：每人一张表，逐行选定同意/不同意/弃票，一次提交。全部提交后主持人的一次推进（或无人待办 5 秒后的自动推进）同时结算全部候选并依次公布结果；不再逐个候选轮流收集、也不按轮次分批公布。其他未定投票细节以主持人本局宣布为准。
提名在白天任意阶段都能提交（玩家可以提前提名，界面标为“可提前”并直接提交、不再二次确认），不要求所有人等到提名阶段才行动；进入提名阶段时先前提名或放弃的玩家自动视为已确认，只有没提交过的席位需要操作。同一张牌可以被多名玩家同时提名，重复提名不是失败，也不会重复投票：计票时按提名先后去重，每张被提名的牌只投一轮。提名不代表投票：提名者仍需为每个候选自行选择同意、不同意或弃票，选项继续遵守雪莉绑定汉娜、蕾雅决斗等角色规则。玩家一次提交全部候选的选票，提交后本轮不能再改；此时若又有人新增提名，只把新候选补进还没交卷的席位那张表。
每次计票的分母 N 在**投票开始时冻结**（那一刻拥有投票权的存活玩家数）；之后即使有人整席出局也不再改变门槛，否则已经下发到玩家表单上的票数会悄悄变掉。强制弃票者仍计入，失去投票权者与不能投票的傀儡不计入。普通候选的通过门槛为 floor(N/2)+1，蕾雅决斗的两张牌为 floor(N/2)（7 人局 3 票）。不要用实际投票人数替代分母。
所有严格过半候选一起进入本轮处决结果；奈乃香临刑开枪等效果先处理，不在第一名候选处决后提前截断其他已通过处决。
每次死亡检查胜负并形成候选结论。同一半天的多人出局按严格同时处理，主持人确认相关结果齐全后才正式宣判，不按网络消息到达顺序抢先封局。双方同时满足时白好黑魔。
雪莉、质疑失败者等特殊个人结局由角色状态合并计算。交牌不简化为任何一人点击即可结束，照玩家规则收集条件和主持人确认。
若尚未生成魔女或仍有后续转化问题，不把“当前存活魔女数为零”直接等同于好人已经完成胜利条件；结合本局魔典交由主持人确认，避免空集合判断导致开局自动获胜。

5. 13水与信息

13水按夜发放：主持人可在夜间行动、最后夜间行动或预结算阶段把一瓶13水交给一个存活席位，同一夜可发给多个不同席位，每位持有者各自使用一瓶，夜末未用过期收回。只有持有者本人看得到自己持有的13水。持有者在本夜行动期直接指定目标使用，毒杀立即进入本夜预结算，不创建主持人待办；13水死亡的未隐藏死因单列“X号玩家被13水毒杀”，魔女梅露露可勾选隐藏死因，隐藏时按普通夜间死亡处理（走普通死亡公开路径，不生成固定目击名单）。
疑似凶手名单按每名夜间死者分别生成：主持人表单预填基础三人，汉娜在场时四人，优先含技能处理后的显示凶手与在场的汉娜，余位补齐。主持人可自由修改角色与人数或留空，不要求包含真凶或汉娜，实际真凶也可不补选；仅显示常规规则警告，不阻止提交。未隐藏死因的13水死亡仍由系统直接生成名单，按基础三人、汉娜在场时四人的原规则包含显示真凶与在场的汉娜，余位随机补齐，跳过主持人填写。死者中毒时这份目击是中毒信息：判定出局前掷一次信息骰，失败时把入选的显示真凶换成一名未入选角色；主持人已省略真凶的名单保持原样，本人不会得知判定结果（真凶就是汉娜时自动假名单仍原样保留）。若实际来源是使用替罪凶手的魔女诺亚，自动名单与雨夜脚印按替代角色显示；雨夜脚印公开显示凶手座位号相对死者较大或较小，实际来源为汉娜时方向反转。魔女穗乃香每次真的进入名单时由本人选择本次显示身份，超时保留穗乃香。名单只发给对应的当事人。证物仍只在整席最后一张牌出局时发放。
名单的触发条件是「被魔女的袭击指到」而不是「因此出局」：魔女刀、额外攻击与全场攻击的目标按本夜提交的意图记账（在米莉亚替死改写目标之前落账），庇护把它降级成负伤、玛格的爱免疫、米莉亚替死把致死一击转走都不改变这条记录，被指到的席位照发一份给主持人填写的名单（当事人中毒时同样按信息骰结算）；真正出局的席位仍走普通死亡路径，同一席位不会重复发。13水毒杀不是魔女袭击：没出局就不发名单。
每条夜间死亡、延迟公开通知、目击待办与已发目击都关联同一个 death_id：梅露露复活时按 death_id 一并撤销该次死亡的公告、死因与半天出局记录，因此复活目标不出现在夜终总结里，同夜其他死亡不受影响；被魔女袭击击中的死者例外——目击看的是「被指到」，复活只把待办标题改成当事人还在场，名单照发（13水等其他死因仍连目击一起撤销）。
可可的信物不含文字或图像，只记录发送席位、受赠席位、日期和夜间行动授权。证物仍可包含文字或图像；主持人提供的其他材料继续按指定接收范围投影。

6. 主持人工作台

优先呈现本阶段待处理事项，而不是要求主持人去编辑一大段原始数据：
- 看全员双牌、上下层、生死、阵营、伤势、剩余技能次数和在线状态。
- 看魔典、转化候选、夜间意图、概率结果与预结算变化。夜间阶段在主持人操作面板列出每个席位当夜的角色牌、已提交的技能与目标、尚未提交者，玩家之间不共享这些信息，主持人可据此主持。
- 查看动态毒源、中毒骰、夜间概率结果、实际伤害来源与预结算变化；系统明确的概率自动抽取，不产生主持人待裁定项。
- 发13水、排发言顺序、警告并计时、开闭投票、确认处决与胜负。
- 处理替补继承、非同一天同一时点的回溯和规则未定义的特殊操作；穗乃香目击改名、真实/伪装声明和质疑均由对应玩家或系统直接结算。
- 需要纠错时调整指定对象的游戏状态，附裁定说明；同时预览哪些变化公开、哪些只给当事人。

已经明确的概率由系统抽取，默认不要求主持人人工掷骰；没有明确概率才由主持人决定。主持人的裁决记录属于本局游戏记录，不另做审计平台或管理员监控系统。
公开操作必须清楚列出目标和将发布的内容。私密裁定不能仅因为点击了“下一阶段”就自动变成全员公告。

七、十四个角色的操作入口

以下是实现覆盖清单，完整规则文本仍从同一个角色目录提供。每项均包含真实角色能力、魔女化后的变化和主持人的裁决入口，不只做选牌而把角色技能留空。

艾玛：每日打断/最后发言；动态邻接中毒；前两天不能魔女化，第三天**当前牌是艾玛**（即她已经登场）时以最高优先级强制魔女化，否则由魔女阵营 A、B 中仍可转化的一位接替。寻宝、1/5地雷与安全后的目标保护已拆至默认禁用的 emma_treasure 外置插件，须在建局时启用。
希罗：死亡预结算时自动回溯（夜间回前一天顺序发言、白天回前一天自由发言，缺快照则回开局）、好人/魔女独立额度、主动出局、精神系保留与魔女化保留；回溯不吃中毒骰，死亡预结算即触发。魔女希罗「必须疯狂地使艾玛出局」不做硬性拦截：第一夜未攻击艾玛消耗唯一一次例外额度，之后再未攻击由系统生成「疯狂裁定」待办交主持人按规则第六条「疯狂」警告或执行不利裁定，不阻塞当夜结算。
汉娜：每份疑似凶手名单固定包含且由三人扩为四人（含未隐藏死因的13水致死）；魔女一次额外攻击；可选开关「汉娜魔化」（默认关闭，只在第三天入夜前可改）在汉娜在场、曾经绑定过雪莉且当前已解绑、艾玛不在场时覆盖第三天夜的魔女人选。
雪莉：雪莉与汉娜均为上层即绑定（否则需两牌同时为当前牌并共同度过完整白天）；绑定后的投票、殉情与胜负。
梅露露：每晚庇护目标；魔女只可复活当夜由自己造成死亡的角色（不要求曾受庇护），复活只能在当夜完成——天亮（下层登场、死讯公示）后入口关闭，避免把已经公开的死亡悄悄回滚；傀儡无投票权、不能发动角色特有技能，但**被动效果保留**（艾玛毒素光环、米莉亚替死、汉娜的目击名额、玛格之爱、希罗回溯、雪莉绑定、奈乃香的被动幻视），手里的13水与魔女刀也由主人代用；该次死亡的公告与死因按 death_id 一并撤销（被魔女袭击击中的目击照发）；保留13水隐藏死因。**主人出局时傀儡当前牌立即跟着出局**（下层牌还在就由原玩家恢复自主操作，没有就是整席出局，死亡公告与别的出局同一口径），且不会因为主人后来被复活而再次被拉成傀儡。
诺亚：每局一次下雨；有来源的死亡自动公开方向脚印，汉娜来源反转；魔女一次指定之后死亡显示的替罪凶手。
安安：诺亚为同席下层牌或诺亚席相邻时中毒；魔女全场洗脑的次日处罚带声明ID，若假声明被质疑则只撤销其尚未发生的处罚。
米莉亚：每夜预选交换对象并一直保留到下一次有效换血，普通死亡（不含处刑、质疑失败、殉情）自动替死重算，换血与替死都不吃中毒骰，不产生主持人待办。
可可：赠送无图像信物及受赠者授权查看夜间行动；魔女每晚开始时得到魔典与所有玩家的阵营（包括已出局席位；按A、B命运阵营，不按当前牌魔女化状态），并在其他行动锁定后最后行动。
奈乃香：6颗临刑子弹，命中率从1/6按连续未命中逐次增至6/6、命中后重置；处决幻视是被动技能（处决名单一定稿就自动查看本日名单是否含魔女，结果只发给本人；不可声明、不可伪装、不可质疑，中毒时必定收到一条结果，由信息骰决定真话或假话）；魔女夜间主动查看全员魔女化状态。
亚里沙：禁止魔女化；每夜对环形左右邻座分别抽1/2负伤一次（“一次”只限制本次，已有负伤时照常升级为死亡）。
玛格：白天爱上/移情，每夜令爱人席当前牌负伤一次，爱人整席出局后转爱自己。没有破译或模仿协议。
蕾雅：白天长矛立即进入标准出局预结算，自己同时进入当日处决名单；没有夜间注视或夜间长矛。
穗乃香：开局获知上层牌（普通技能，恒为真、不吃中毒/信息骰；排序阶段预览与开局信息同源，只列已准备席位）、公开示人身份；魔女每次进入四人目击名单时由本人选择本次显示角色，超时显示穗乃香。

质疑范围：除信物与爱人选择外，全部开放白天技能声明都可被其他仍有存活角色牌的玩家质疑；只失去一张牌不影响资格，两张牌均出局后不再下发质疑行动，服务端拒绝直接提交与主持人代操作。声明公开字段固定为声明ID、席位、技能名、目标摘要和状态，不包含真假。质疑假声明只停止未完成部分并清除关联的安安延迟处罚，且被拆穿的技能该席位本局不能再发动（真实或伪装声明都被拒绝，行动表单也不再出现该技能）；质疑真声明用 eliminate_seat 直接作废质疑者两张牌并个人判负。

伪装结算：当前角色/魔女状态不满足的同角色能力与穗乃香示人身份能力可产生假声明。真假声明都立即进入相同执行分支；假信物和假爱人选择不写状态，其余已执行结果不回滚。处决幻视是被动技能（处决名单一定稿就自动生效），没有声明与伪装入口；信息类技能只掷信息骰，本人必定收到信息，真假由信息骰决定且不告知本人（穗乃香「开局前获知上层牌」不属于声明类技能，恒为真、不掷骰）。效果类里只有「赠送信物」会因中毒骰失败被记为假。所有这些分支都不产生主持人真假裁定待办。

八、状态、保存与实时通信

1. 必要状态

Game：本局ID、状态版本、日数、白天/夜晚标识、阶段、发言顺序、截止时间、魔典、13水、待办裁决与胜负候选。
Seat：稳定座位号、当前操作者、公开称呼/示人身份、双牌引用、准备状态、投票资格；在线连接另行维护。
RoleCard：唯一牌ID、角色种类、原始牌身份、当前持有人及上下层、生死、魔女化、状态和次数。原始身份不能因交换而丢失。
Action：提交者席位、使用的牌、技能/目标、提交阶段与版本、是否确认、已抽定结果和处理状态。
Information：信物授权、四人目击名单、证物、私密提示与状态卡；发送时的获准接收者与内容。状态卡不包含中毒：中毒对玩家完全隐藏，只写主持人日志。
Prompt：只在本人行动卡住流程时下发的催办（标题、说明、可选的「先结束私聊」提示）；时机与文案都由服务端决定，客户端只负责醒目展示。
PersistentEffect：不能随希罗回溯消失的绑定、处罚、回溯消耗及其他主持人明确保留的效果。
Snapshot：游戏内时间点、对应牌与技能状态；不包含登录账号、连接、历史聊天或可回溯的鉴权数据。

2. 三个SQLite数据库

对局库 data/seven-double.sqlite3 使用七张表：games（完整领域状态、快照、版本）、participants（参与身份、account_id 关联与历史权限）、channels（私信频道的创建者、状态、成员/邀请/同意名单与结束时间）、messages（聊天、信息、通知及接收范围）、evidence（文字、图片及归属）、invites（定向对局邀请：受邀账号、邀请人、状态、创建与响应时间）；领域快照存在 games.state 内，不另建事件重放或快照数据库。旧的 sessions 表与旧邀请码形状的 invites 表在初始化时删除重建。
鉴权库 data/auth.sqlite3 使用四张表：accounts（qq_id、昵称、头像）、login_challenges（六位挑战码的散列、状态、过期与消费时间、客户端种类 web/native/web_host/native_host）、login_tokens（token_hash、account_id、kind、expires_at、valid）、host_authorizations（主持等级与授权人）。只保存 SHA-256 后的令牌与挑战码，原始值不落库。
成就库 data/achievements.sqlite3 使用三张表：achievements（名称、内容、稀有度 1-10、创建与更新时间）、grants（account_id、achievement_id、获得时间、可空的 priority_position 优先展示顺序，同一玩家同一个成就只记一次）、players（昵称快照、佩戴的授权 id、最近一次以玩家身份参赛的时间）。旧库启动时补充 priority_position 列；成就、授权与优先展示选择跨局保留——建局清空对局库不会碰它。
公告库 data/announcements.sqlite3 使用一张表 announcements（标题、markdown 正文、作者、创建与修改时间）；它同样不属于任何一局，一键初始化与建下一局都不影响公告。发布与修改只有 5 级主持能做。
四个库之间不伪造外键：单进程事务边界先校验账号，再写对局参与身份。备份边界也不同——清空对局只删对局库内容，账号、登录令牌、主持授权、成就记录与公告全部保留。`data/` 可用 `GAME_DATA_DIR` 覆盖，验证时请指向独立临时目录。
角色素材继续读现有img目录；证物图像作为SQLite BLOB保存在evidence表并按身份检查权限，不能通过公开静态素材路径访问。信物不保存图像。
游戏命令先在本局锁内校验与计算，事务保存状态及产生的消息，再推送；保存失败则不发布成功结果。小规模对局不需要分布式锁。
提供启动时读回当前状态，避免刷新或服务重启重新发牌；不承诺服务中断自动托管，也不增加房主故障转移方案。

3. 可见视图

玩家/观战响应从公开字段出发，按获准信息补充；不要先把主持人全量状态发给客户端再用客户端逻辑隐藏。HTTP、WebSocket、消息历史、附件访问与重连恢复共用同一可见性规则。
主持人视图含全部游戏信息。玩家视图含自身双牌及合法获得的信息。观战视图含全席双牌、生死、状态、阶段与结果的只读牌桌，但不含玩家/主持人行动、主持人待办、参与者管理或席位代操作，也没有任何游戏命令。替补增加历史权限必须由主持人明确决定，不默认获得其他人的私聊。
所有写命令统一携带 expected_version；旧版本请求返回409，客户端重新取得可见状态并要求确认，不重复执行，也不自动重放。动态行动描述与 GameView 都带顶层 ui_version，当前为 1；未知版本或未知字段类型（只允许 text、textarea、number、select、multiselect、checkbox、drawing 七种）显示“客户端版本不支持此行动，请升级”并禁止提交。engine.validate_command() 始终是唯一权威，客户端输入检查只提供即时提示。
过往消息保留发送时的接收者，后来的换牌不会自动解锁另一席位的历史信息。

4. 更新方式

HTTP承接登录、加入、游戏命令与聊天提交；WebSocket只负责实时状态、消息和在线通知，不维护另一套技能协议。
游戏命令携带 expected_version；旧版本请求返回409，客户端重新取得可见状态并要求确认，不重复执行。客户端不会自动重试扣子弹、投票、发13水等有状态命令；超时先取状态确认结果。聊天另有自己的发送确认，不因游戏版本变动拒收正常发言。
WebSocket使用 sync、state、message、ping 消息，客户端回复pong。持久消息有递增id，消息kind区分聊天、私密信息、在线通知等；对局结束随state同步。所有内容按接收权限生成，不做复杂增量补丁。
连接建立时在同一同步边界注册订阅并取得快照与最近一页获准消息，然后投递后续更新，避免初始化窗口漏消息。重连后重新同步状态，按after游标补充获准历史，客户端按消息id去重。
纯在线状态和聊天不抬高游戏命令版本，避免正常发言让别人选好的夜间行动无故失效。

5. 成就系统

成就由主持人授权，所有成就都可以自定义：名称（不超过24字）、内容（不超过200字）、稀有度1-10（数字越大越稀有，客户端按档位取十种不同的明亮底色：1灰、2紫、3蓝、4青、5浅绿、6土黄、7橘、8红、9银、10亮金；文字统一为白色，带薄深色轮廓保持可读）。青、银、金徽章及对应的等级选项带金属渐变、亮边与循环斜向反光，系统关闭动画时保留静态质感；聊天昵称旁的紧凑徽章、成就列表、头像摘要与主持预览共用此样式，长名称保持单行省略。玩家界面不显示5-10级的实际稀有度，5-8级显示「特殊」，9-10级显示「专属」；主持管理界面保留原始等级。新建、修改、删除定义，以及给谁授权、撤销哪条授权，都只有主持人令牌能做；玩家只能读公开的成就目录（全部定义）与自己名下的授权记录，并且只能佩戴、优先展示自己名下的记录——这些边界在服务端判定，界面隐藏不能代替授权。

删除定义会连同授权一起删除并清空对应佩戴与优先展示项（界面先提示已授予多少人），撤销单条授权同样清空对应佩戴与优先展示项；同一玩家同一个成就只记一次，重复授权返回冲突。玩家列表取自成就库的 players 表：以玩家身份参局或获得过成就的账号才在其中，按最近一次参赛时间倒序、从未参赛的排在最后（观战不计入参赛）。头像摘要是公开展示数据（总成就数 + 最多5个成就），任何已登录身份可读：玩家选最多5个优先项，按勾选顺序展示，不足5个时用未选择的成就按真实稀有度倒序、同档获得时间倒序补齐，不重复；未选择时仍展示最稀有的5个。修改选择时原子验证全部授权归属，拒绝重复或超过5个，失败保留原选择。对局内的佩戴信息只发给该局的主持人、参与者与观战者。

界面上：大厅一张卡片进入「我的成就」（玩家）或「成就管理」（主持人，分成就定义与玩家授权两页）；「我的成就」可独立选择佩戴与勾选优先展示，优先项选满5个后只能取消已选项，取消后可继续选择。自己获得的成就下方还有一份「成就一览」，把服务器上的全部成就都列出来——没获得的用淡色徽章标「未获得」，已获得的一行可以直接佩戴；对局内发言时昵称右边显示佩戴成就（底色即稀有度颜色），点击头像在快捷菜单下方展开成就摘要。

6. 公告

公告是系统管理员（5 级主持）向所有端发布的通知，正文是 markdown。存取在独立的 data/announcements.sqlite3：标题不超过 60 字、正文不超过 4000 字；服务端只给每条公告算一个 sha256 内容哈希与一个整体版本号，不解析正文。

分发走大厅轮询：GET /api/lobby 的响应里带 announcements（最新的若干条，含正文）与 announcements_version，客户端每 5 秒轮询时顺带检查版本号，变了才重建列表——不必为公告单独开一条轮询。客户端把读过的公告哈希存进本机偏好（shared_preferences，只存哈希不存正文）：哈希不在本机集合里就是未读，公告被改过内容（哈希变了）会重新算作未读，重启不丢已读状态。大厅卡片显示最新几条与未读数，公告页列出全部并可以一键全部已读。

渲染在客户端：原生客户端用 flutter_markdown_plus 渲染（标题、列表、引用、代码块、表格、链接），样式跟随应用主题；发布页也带实时预览。网页首页的公告栏调用 GET /api/announcements/public，按纯文本段落展示正文。

commands统一使用 expected_version、action、payload 信封；房间管理输入由Pydantic校验，游戏动作由后端动作描述和领域函数逐项校验权限、字段、阶段、次数与目标。不接受任意JSON覆盖整个游戏状态。
房间管理动作：room.open_join 开关开放参局；room.kick 使用participant_id和block，既可移出玩家也可移出观战者；room.replace 使用seat_id与participant_id 让观战者接管空席；room.mute 设置或解除禁言。
私信动作：channel.create（name、participant_ids）、channel.accept、channel.reject、channel.end（均带 channel_id）；它们和其余所有行动走同一套确认流程。
所有玩家行动、私信邀请响应和主持人管理都是单次确认：点击 2—4 字短名按钮打开说明与参数弹窗，填好后点一次“确认提交”即发送，不再有第二道确认框，也不再有 instant 绕过语义。校验仍在提交前完成（必填、选项有效性、数值范围），危险动作继续以红色按钮与警告图标双重标记；因为所有写命令都带 expected_version，服务端状态变化会返回 409 并要求重新确认，不存在静默写入。
GET /api/games/{game_id}/messages 的 scope 取 all|public|private|system|host：先按频道成员关系过滤再分页，保证筛选历史不是只过滤本机最近一页。
所有选择席位的人物选项都同时显示玩家名与角色名：默认只显示上层牌的角色名，上层出局后显示“上层→下层”两个名字；主持人始终看到该席位两张牌的角色名。

玩家动作涵盖：选上下牌、准备、确认/放弃夜间行动、白天技能声明、质疑、主动出局、提名、投票、制作/破坏、信息授权、证物公布、13水使用、交牌请求。提名不限轮流：尚未提名或放弃的席位都会同时看到「提名候选/放弃本次提名」，各自提交后立即生效，只有能提名的席位都提交后主持人才推进（当前牌本阶段不能行动的席位没有提名按钮，直接视为跳过，不挡在待办里）；重复提名同一角色由服务器拒绝。每个动作描述自带“是否需要玩家确认”的标记，客户端与主持人面板都用它显示“轮到你行动”的提醒与阻塞状态。
主持人动作涵盖：开局、排发言顺序（选起点与方向）、警告、结束超时行动、推进阶段、裁决、确认结算、发放13水、投票控制、纠错、替补、踢人/房内拉黑、结束对局。主持人可用「席位视角」读取某席位自己看到的界面，该界面逐条列出该席位当前可提交的操作并各带「代替操作」按钮；代操作只能使用该席位当时可用的行动，代操作内容不向他人公开，完成提示作为私密系统消息仅发给对应席位当前玩家与已确认进入本局的主持人，不再向公屏发布；原本公开的技能声明与结算结果仍按规则公开。
常见失败区分：未登录、无权限、邀请码失效、目标席位已被占用、阶段已结束、状态已变化、输入不合法。错误文本不向无权者透露真实牌面、私密目标或技能真假。
证物图片上传仅接受2MB以内、最大边长4096的PNG/JPEG，后端生成随机证物ID；不执行上传内容，也不接受客户端指定任意磁盘路径。角色立绘是公开静态素材，与私密证物分开。

十、开发与交付顺序

按完整可运行的纵向功能推进，不先铺满空文件或留“稍后实现”的角色按钮：
1. 完成主持人登录 → 新建空席局 → 发共用码 → 七人随机入场/首次准备 → 发牌/私下排序/再次准备 → 主持人开局；验证旧码失效和刷新恢复。
2. 接上真实聊天、头像、消息权限、WebSocket 在线状态、手机/电脑桌面和观战替补。
3. 接上主持人阶段推进、确定概率、技能输入/信息、预结算、投票、13水与结局，覆盖14角色。
4. 处理回溯、精神系保留、同时死亡、伪装/质疑、替补历史，完成全程七双联机验收。

前端开发服务器：无。前端已改为无框架静态单页，没有 vite.config.ts；正式使用时同源服务，避免多余的跨域和多后端部署。
后端规则检查只保留能防住真实错误的少量回归用例；不要为每个转发函数写测试。浏览器体验以实际手机/桌面视口操作和真实服务联机为准，不用截图假页面替代。

十一、验收标准（实际验证范围见第十二节）

A. 只有 GAME_ADMIN_QQ 指定的账号（或已被 4/5 级授权的主持账号）能登录主持人入口；未授权账号走主持人入口被拒；玩家改昵称或提交host字段不能获得主持人权限；1 级主持用完那一局后授权与旧令牌一起失效；4 级授不出 4 级、也取消不了 5 级；QQ 挑战码只能消费一次，原始令牌不落库。
B. 七名玩家首次准备后随机分出14张不重复的牌，7席各2张，米莉亚与亚里沙不在同一席；玩家能私下排上下牌，别人看不到下层牌；主持人能看到全部。
C. 主持人开放参局后，七个不同 QQ 账号无需审核随机占满七席，第八个账号被拒但可选观战，同一账号不能重复分席；发牌后不能新占玩家席。踢出/拉黑只撤销本局参与身份，账号与登录令牌保留，下一局可重新加入；清空对局不登出任何账号。刷新按账号恢复原席位，发牌后的空席只能由观战者接管且不重发牌。
C2. 观战能读全席双牌与状态，并只读访问全部公屏、玩家与主持人私信、观战频道、系统与定向私密消息；历史、重连和实时权限一致，所有发言、撤回、输入状态、私信操作、游戏命令、证物提交和管理请求均拒绝。玩家与未确认主持人的原有私密边界不变，观战不因此获得角色私密状态或未授权证物附件。
C3. 私信覆盖玩家创建、多人逐一同意、拒绝取消、主持人默认同意、主持人免同意发起、单个非主持人同时只有一个 active 频道、开始与结束的频道内系统消息（只发给频道成员，不占全场记录）；邀请名单只含玩家与主持人；active 期间非主持人成员的公屏发言与玩家成员的游戏行动都被服务端拒绝，主持人不受限制，结束后恢复。进入夜间（魔女化检测起算）时全部私信频道自动结束并公告，夜间只有与主持人的私聊能创建，不含主持人的遗留频道在夜间不能发言也不锁住游戏行动。
C4. 行动协议只接受七种字段类型与 2—4 字 short_label；未知 ui_version 或字段类型被拒绝；所有行动都是单次确认；409 保留草稿并要求重新确认；lobby.order 选定上层后服务器保存的另一张必为下层。每个行动都带非空说明，需随局面变化的行动（投票候选、夜间技能、白天技能、主持人待办裁定、开枪概率、开闭加入）在服务端按当前状态改写；客户端只渲染，不重算规则。
C5. 卡住流程的席位在客户端看到服务端下发的红色「请求操作」催办（准备、再次准备、提名、夜间行动、投票、临刑响应），完成操作后立即消失；该席位正在 active 私信里时催办额外提示先结束私聊，此时服务端只下发私信行动。
C6. 全场阶段横幅同样只由服务端下发：顺序发言与提名、投票阶段，所有玩家都能看到「当前轮到 x 号玩家发言」或「正在等待 x 号、x 号玩家提名／投票」；玩家都做完、流程只等主持人（待裁定、宣判、预结算发布、夜间结果、天黑结算，或自动推进被暂停）时看到「等待主持人进行操作」，自由发言阶段不提示等主持人；夜间只显示「仍有玩家未完成行动」，任何端都拿不到未完成行动的席位名单。
D. 同一席位两条连接断一条不算掉线，最后一条断开只改变在线标记、不发任何系统通知；恢复不重抽牌、不清空行动。
E. 私聊与13水持有信息在玩家、观战的状态、实时事件和历史里都只按权限出现；没有前端隐藏的全量主持人数据。
F. 手机360px宽与桌面1440px宽均能入场、查看双牌、发气泡消息、投票和操作主持人待办；软键盘不挡发送按钮，页面不横向滚动。
G. 5名有投票权活人中含1名强制弃票者时，处决仍需3票；傀儡和真正无投票权者不计入分母，多候选通过不漏结算。
H. 米莉亚受庇护而不死时不替死；确会死亡才替死重算；重算不多扣子弹或再次掷骰（替死不掷中毒骰）。可可看到他人行动后才能最后提交。
I. 同一玩家同一半天不能出局两张牌；同一半天同时达成胜利按白好黑魔，不按死亡消息先后判定。
J. 希罗两种身份各限一次，死亡预结算即自动回溯、不产生主持人待办；回溯恢复他人普通技能，不恢复自己的额度，不撤销魔女希罗魔女化、雪莉绑定或安安大招负面效果，也不删除聊天记忆；回溯后调用方不再写回阶段与快照。魔女希罗未攻击艾玛时同样不产生阻塞待办：例外额度耗尽后改为一条可默认裁定的「疯狂」待办。
K. 雪莉/汉娜开局双上层即绑定，否则未共同作为上层过完整白天前不触发；动态中毒来源、信物效果骰与信息假值均按规则结算；四人目击、雨夜脚印与穗乃香逐名单改名相互一致。
L. 13水按夜发放、夜末过期，未隐藏死因的公告与固定目击一致，魔女梅露露的隐藏死因例外保留。
M. 穗乃香伪装和真实技能的公开声明不能被UI区别；质疑只停止未完成部分，失败质疑的个人判负得到体现。
N. 六名不同席位提交「请求结束自由发言」后 10 秒自动进入提名；在场可行动席位不足六人时改为全员提交即可（进度条分母随之下发，不写死 6），有待办或主持人暂停时不自动推进。夜终公告为「第X夜是平安夜」或列出仍实际出局的当夜角色名。
O. 傀儡被魔女梅露露代操作时，动作与频道都以 `as_seat` 与星号标记区分；星号只进 `label`，`short_label` 保持 2—4 字协议长度；傀儡席本夜的行动与确认也只从控制者的傀儡面板提交（原席位不会既没有行动又占着阻塞待办），原傀儡玩家只能只读旁观：行动、证物、公屏与私信全部收回（投影里所有频道一并禁言，悬浮框与频道动作也不下发），不能发言、上传证物或执行游戏行动；控制者按该席身份代读代发它的私信（`as_seat` 同时用在消息读与写上，频道里的回话实时推给控制者，但不代读它的系统情报与证物）。傀儡只能发动通用行动——手里的13水与（魔女时的）魔女刀由控制者代用，其余角色特有技能一律不给；被动效果照旧自动结算（毒素光环、替死、目击名额、爱、回溯、绑定、被动幻视），死亡或主人出局时解除控制：傀儡当前牌出局、或主人出局时那张牌立即跟着出局，原玩家恢复通知与权限（下层牌还在时）。
P. 替补接管后旧操作者不能继续行动，新操作者只继承主持人批准的私密信息；更换操作者不刷新牌或技能次数。
Q. 主持人未裁决的“可能”会明确等待，不被系统偷偷当成失败、成功或跳过；未定玩法不阻塞系统本身的可操作性。
R. Flutter Android 与 Windows 客户端可登录、加入、聊天、执行行动；底栏角标与阶段动画只出现一次，软键盘弹出时隐藏行动列表但保留新行动提醒，双头像 50% 重叠且当前牌置顶、死亡灰白；Windows 主持人端无触觉且管理分组可用。

十二、运行与交付

已提供可运行的七双前后端；玩家规则仍是游戏说明，本文件记录软件结构和运行方式，二者不互相替代。

1. Windows启动
首次安装：双击项目根目录 setup.cmd，或在终端运行 .\setup.cmd。它创建.venv、安装后端与网关依赖、构建前端静态页。安装期间需要访问Python/npm包源。
日常启动：双击 start.cmd，或在终端运行 .\start.cmd。服务日志出现“Uvicorn running”后，在电脑浏览器打开 http://localhost:8000 查看公告、规则与下载；游戏对局在 Flutter 原生客户端进行，主持人用被授权的 QQ 账号登录客户端。
管理员配置：主机环境变量 GAME_ADMIN_QQ 必须是系统管理员的 QQ 号（多个用英文逗号分隔），否则没有任何账号能登录主持人端（启动日志会给出警告，登录时也会提示未配置）。start.cmd.local.cmd 里已经留了填写位置。其余主持等级在界面里由 4/5 级主持授权。
QQ登录：复制 gateway\.env.example 为 gateway\.env 并填写 NapCat 地址、访问令牌、后端地址、网关共享密钥与QQ群号（多个群用英文逗号分隔，网关同时监听并合并群成员），然后运行 run-gateway.cmd。网关共享密钥须与后端环境变量 GAME_GATEWAY_TOKEN 一致；真实密钥、NapCat 登录态与日志都不入库。
手机加入：与电脑连接同一局域网，在原生客户端填写 http://电脑局域网IPv4:8000，先在指定QQ群发送“活动登录 123456”完成验证，再由主持人开放加入后主动选择加入或观战。IPv4可在电脑上运行ipconfig查看；客户端不能使用localhost。若Windows防火墙提示，只按实际需要允许专用网络访问8000端口。
更换端口：.\start.cmd --port 8001；只允许本机访问：.\start.cmd --host 127.0.0.1。默认绑定0.0.0.0，必须保持单个worker；按Ctrl+C停止服务。
主持人权限与 QQ 账号绑定、按等级划分，不适合把服务直接暴露到不可信公网；本版本不包含公网域名、TLS证书或外网穿透配置，但可以挂在用户自备的反向代理后面：代理需透传原始 Host 或补 X-Forwarded-Host/X-Forwarded-Proto，转发 Authorization 请求头，并允许 /api/live 的 WebSocket 升级；代理不在本机时用 --trusted-proxies 声明。带有效 Bearer 令牌的写请求跳过浏览器同源校验（原生客户端不发送 Origin），WebSocket 仍在令牌有效时先放行；没有有效令牌时先看 Origin 是否在显式放行名单（默认 super.tkcloud.online，用 GAME_ALLOWED_ORIGINS 覆盖），再看浏览器自报的 Sec-Fetch-Site，最后才比 Origin 与 Host/转发头。

2. 开局与日常操作
主持人新建对局时确认11角色魔典名单，系统随机排序；点击“开放加入”后，已登录账号自行选择加入或观战，无需审核。玩家随机进入空席，选择上下牌并准备，7人准备后由主持人开局。
按页面提示确认行动，由主持人推进阶段、处理“可能”与未定规则待办。观战账号取得只读全牌桌；需要替补时，主持人从观战者中接管空席，并分别决定是否继承私密历史及保留原行动。
移出/本局拉黑对玩家与观战者均有效；只撤销该参与身份，不重置角色牌，也不删除该账号的QQ登录。没有设备识别或IP封禁，玩家换设备重新登录即恢复参与身份。
不明确或未写明的概率与规则交由主持人裁决；系统自己知道做完的阶段（魔女化、夜间行动、顺序发言、提名、投票、处决前响应）无人待办时5秒后自动推进，主持人可暂停或手动推进。
手机使用底部导航切换聊天、桌面、双牌/管理及行动；需要操作时顶部显示“轮到你行动”，底部导航同步标记数量；聊天可复制粘贴，证物可输入文字或导入PNG/JPEG。原生客户端提供同样栏目，并额外提供触觉反馈与阶段动画；宽屏按既有平板与桌面布局展示。
主持人工作台按“待办”组织：所有需要裁决、警告、推进或宣判的事项集中列出；未完成的玩家行动不再挡住推进，顶部推进按钮只在有待裁定、胜负宣判或交牌审阅时禁用并显示剩余项数（「夜间结果与证物」阶段还没决定的梅露露复活也算一条阻塞待办、计入剩余项数，但推进按钮仍然可用——按下即视为放弃这次复活），其余时候按下即为强制推进（未完成的玩家行动立刻按超时处理，提前写好的发言照常公开），也可以先对卡住的席位「警告30秒」再等它自己完成。夜间可用「本夜全员行动」核对每个席位的实际提交（含目标当前角色、掷骰与猜对数、是否被中毒抵消、是否主持人代提交），并对卡住的席位一键警告；发出去的私密信息在对话记录里以“系统信息”标记出现，玩家侧另有悬浮提醒。

3. 保存与开发
默认数据库为 data/seven-double.sqlite3（对局）与 data/auth.sqlite3（账号与登录令牌），首次启动自动创建。刷新或服务重启会恢复原局；不要在进行中的对局删除数据库。备份前先停止服务，再复制整个data目录；只想保留账号与登录态时可以单独备份 auth.sqlite3。
可用环境变量GAME_DATA_DIR指定独立数据目录，联调曾使用data/verification，交付时清除此测试目录。游戏内不会结束对局；须由主持人结算或终止当前局后才能创建下一局。
对局结束后数据仍可只读查看，直到建立下一局为止：建立新对局会自动清除上一局对局库的全部数据（含结算与聊天），主持人也可在管理面板点「一键初始化」立即清空；两种方式都保留QQ账号、玩家登录令牌与主持人登录，下一局重新开放加入即可参局。
前端开发：无框架静态页，改 frontend/index.html 或 rules.md 后在 frontend 目录执行 npm run build（Node 脚本组装，无依赖安装）。重新构建后无需让玩家清缓存：index.html 每次回源校验。
部署端更新标签由 data/updates.json 下发（按「平台 + 版本区间」，格式见 README「客户端更新」；后端不读 GAME_CLIENT_LATEST / GAME_CLIENT_MINIMUM 等版本环境变量，清单缺失或没有匹配区间时什么都不下发，文件每次请求现读、改完不用重启）。完整发行版本的唯一源码是 client/lib/src/client_version.dart 的 kClientVersion，当前为 1.1.0；客户端 UA 与 client_latest / client_minimum 的更新比较都用它，低于 latest 顶部横幅提示可更新，低于 minimum 横幅要求必须更新后才能继续使用。这两条提示与安卓保活提示都只在大厅显示，对局中不打断牌局；可更新与保活提示能按「知道了 / 忽略」关掉，关闭结果记在 shared_preferences（版本提示按被关掉的 latest 标签记忆，服务端下发更新的版本才重新提示）。Windows 更新器/安装程序（UA magicjudge-updater/<版本> (windows)）是例外：它不问自己旧不旧，永远拿该平台兜底区间那份当前发布包（否则刚发布的那一版更新器会拿不到自己的包）。从 1.1.0 起正常补丁发版只改 kClientVersion；client/pubspec.yaml 固定 version: 1.1.0+1，仅跨 x.y 系列才改 x.y，+1 不变。APK output-metadata.json 的 versionName 为 1.1.0、versionCode 为 1，Windows runner 系统文件版本来自该固定包基线；不使用 --build-name/--build-number 补丁同步、不做 flutter clean，改 Dart 常量仍需正常重编 Dart AOT。实际发版由 package-release.cmd 以完整 kClientVersion 刷新 data/updates.json 的兜底区间（latest/url/size/sha256 自动刷新，title/notes/minimum/guide_url 手工维护），三条上传名保留「原stem-完整发行版本.扩展名」（如 app-release-1.1.0.apk），本地输出名不变。本次为迁移而非发布，不动 data/ 的线上配置。更新日志从上一条真正改 kClientVersion 数值的提交之后，逐个查看 client/（含更新器）diff；pubspec 依赖调整不算发版提交。普通后续发版只 stage Dart 版本行，不带入其它用户修改；跨系列才选中 pubspec 的版本行。 Flutter 要求三段合法 SemVer，跨系列使用 x.y.0+1；这是固定包基线，并非跟随补丁发行版本同步。
原生客户端：在client目录执行flutter pub get、flutter analyze、flutter test；产物用flutter build apk --debug或flutter build windows --debug。Android 构建需要 Android SDK（platform 与 build-tools 36）与 JDK 21；Flutter 3.47 的模板用 AGP 9.1，因此 Gradle wrapper 固定为 9.3.1。Windows 构建需要 Visual Studio 的 C++ 桌面工作负载与 ATL 组件（flutter_secure_storage 依赖 atlstr.h）。
Windows 更新器从 client/lib/src/client_version.dart 读取 kClientVersion 的完整三段发行版本，CMake 将该文件登记到 CMAKE_CONFIGURE_DEPENDS；版本宏仍 source scoped，只刷新使用版本宏的原生源文件。构建后运行 Updater.exe --version，应输出 magicjudge-updater 与相同的完整发行版本，不能留空；checks/test_updater_cli.py 会对照 Dart 常量核验。
检查依赖：.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
规则/访问检查：.venv\Scripts\python.exe -m unittest discover -s checks -v
Python静态检查：.venv\Scripts\python.exe -m ruff check backend checks run.py gateway
生产构建：在frontend目录执行npm run build。

独立资源包（animation / memes）：素材分别放 resources/animation/ 与 resources/memes/，不编译进客户端。动画角色目录使用项目角色 id，每个 normal/、EX/ 内按 1.png、2.png 等编号；EX 为魔女化半身立绘，根目录 warden-portrait.png 暂作系统立绘。
添加、替换或删除素材后，在项目根目录运行 .venv\Scripts\python.exe -X utf8 tools\update-resource-manifests.py；只刷新一包可加 --pack animation 或 --pack memes。脚本递归列出媒体文件的相对路径、大小和 MD5，分别写入各包根目录 manifest.json；包版本由文件列表生成，同样的素材不会因执行时间而改变版本。说明文件不进入清单，MD5 只用于完整性与变更判断，不替代 HTTPS 或服务端身份认证。
后端通过 GET /api/resources/{pack}/manifest 下发清单、GET /api/resources/{pack}/files/{path} 下发清单中的文件；新清单每次请求现读，不需要为素材更新重启后端。首次部署这些新接口需正常重启后端。部署资源目录时需复制本机素材与对应清单，resources/ 的图片及生成清单仍不纳入 Git。
资源R2加速：data/resource-downloads.json配置base_url后，资源文件与全量ZIP共享3个后端下载名额；按响应实际发送期计数，前3个并发始终本地直传且不探测CF，第4个及以后才尝试302，完成、失败或断开立即释放名额。仅有匹配完整URL、大小与MD5的成功上传记录才允许CDN检查；无记录、记录损坏或不匹配直接本地发送。高并发下未确认URL以带MagicJudgeReleaseCheck/1.0 UA的Range GET检查（最多5秒），仅200/206进入进程成功集合；HTTP错误或连接失败直接本地发送，不缓存失败。低并发即使URL曾确认成功也本地发送，保留Range206。data/resource-uploads.json与下载配置每请求现读，重启只清进程成功集合；本次后端代码改动需重启生效。无效下载配置返回503，移除配置恢复纯本地。1.1.2起客户端下载器支持最多5次HTTP(S)跳转、不带Bearer/Cookie；旧客户端不做兼容分支。
上传记录部署：上传工具与后端都使用GAME_DATA_DIR（未设时为项目data目录），不写对局数据库。不同机器上传/运行时，部署素材与清单的同时复制resource-uploads.json到后端数据目录；不得手工把未上传对象填成成功。已有资源在首次生成记录前走本地，下次正常上传自动生成记录；已经清理CF错误缓存时可继续使用当前前缀，无需为本次改动再换前缀。后端只对当前清单发布且本地路径、脚本及文件大小校验通过的资源开放下载。
当前资源前缀为resources/skill-cutins-31f4ad6f（base_url=https://s3.tkcloud.online/resources/skill-cutins-31f4ad6f），运行 .venv\Scripts\python.exe -X utf8 tools\upload-resources.py --prefix resources/skill-cutins-31f4ad6f。工具先构建animation与memes两份ZIP到GAME_DATA_DIR/resource-archives，再按MD5去重六线程上传媒体与ZIP；8MiB以下单PUT，较大对象复用发行工具8MiB分片上传，保持MIME、immutable缓存与ZIP下载文件名。每项按上传→存储校验→指定URL清缓存（配置时）→公网GET校验→原子成功记录顺序完成，部分失败保留成功记录，不因已有日志跳过上传。开始校验、成功、每次重试与最终失败均打印原始文件名；公网日志包含URL与可用的CF缓存头。
CF自动清缓存：在不入Git的package-release.env填写CF_API_TOKEN与CF_ZONE_ID（不是Account ID），Token仅需该域名Zone的Cache Purge权限；环境变量可覆盖文件。每次对象上传与存储校验成功后POST /zones/{zone}/purge_cache，body只含files:[该完整公网URL]，不清整站。要求HTTP200且success=true，否则该项报错且不新增成功记录；不输出密钥或API响应体。两项均空时明确提示未清缓存仍可上传，只填一项联网前拒绝。清缓存成功后仍校验真实公网URL，不能用查询参数绕过缓存假称可用；此前旧404缓存可直接清对应URL，无需不断换前缀。
反向代理必须原样透传外站Location，不得把CDN跳转改成自身代理路径。Lucky对应站点规则需关闭“自动反代重定向”；否则会返回lucky_auto_reverseproxy_...地址，下载流量仍经过Lucky，达不到直连R2的效果。
客户端每次进入对局界面前检查两包版本，不同或未下载时先询问；用户可只选 animation、只选 memes、两者都选或跳过，选择继续后才显示对局界面，跳过与下载失败都不阻止对局。恢复登录与换局同样先检查，普通刷新与断线重连不重复询问。大厅和对局标题栏的“资源包”入口可再次手动检查与下载。资源缓存在客户端应用数据目录的 resources/ 下，以每个文件的 MD5 直接作为文件名，不按服务器或包名分目录；animation.json、memes.json 各自保存原始路径到 MD5 的映射，相同内容跨路径、跨包只保存一份，增量更新复用已校验的文件。完整下载通过大小与 MD5 校验后才替换所选包的映射，失败或取消不切换；每次更新后按服务器两份清单的 MD5 并集删除无效文件，不保留已被服务器移除的旧资源。只下载一包不会安装另一包，但清理仍读取两份服务端清单；网络故障或清单损坏时停止清理并报告，不把失败当空清单。
客户端1.1.3资源管理可选增量下载或全量ZIP，并可分别导入本机动画/表情ZIP。全量接口GET /api/resources/{pack}/archive返回包名、快照版本、ZIP大小/MD5及下载URL；ZIP存于data/resource-archives/<MD5>.zip，<pack>.json原子选择当前快照，根manifest.json与原始相对路径文件，旧ZIP快照可落后当前清单。上传工具将ZIP托管到同一CF前缀/<ZIP-MD5>并记录archives/<pack>.zip；异机部署复制resource-archives目录与上传记录。全量下载先校验整ZIP大小/MD5，下载或本地导入均验证包名、清单指纹、路径、成员大小/CRC/MD5；拒绝穿越、重复、链接、目录成员、未列出成员、加密、ZIP64和多卷。上限ZIP1GiB、解压2GiB、单文件256MiB、清单8MiB、资源项20000。完整校验才替换映射，取消或坏ZIP不覆盖旧缓存。
全量/导入完成后默认重新读取最新清单，复用已校验MD5缓存执行一次增量下载补差异，不沿用点击前的旧清单。增量网络失败或取消保留已成功安装的ZIP，明确“ZIP已安装、未确认最新”，不误报最新且不清理未能确认的资源；后续可重试增量。原生选择器只取本地路径而不把整个ZIP加载到Dart内存。此客户端功能需更新App一次，后续资源及ZIP发布不需要重新编译客户端。
下载表情按 memes 中的目录分组，目录第一张图片作为分组图标；内置 QQ 经典与超级表情合并，仅 QQ 最近记录固定在列表上方且最多3行。下载表情不加入最近，加载时清除旧下载表情最近记录。下载表情即点即发，POST /api/games/{id}/messages 只带 channel_id、sticker_md5 与必要的 as_seat；表情单独一条消息，不与文字、图片或引用混发。服务端仅允许当前 memes 清单中发布的 MD5，沿用聊天权限、私聊与观战隔离、撤回及广播，不上传图片字节、不创建证物、不改变 kind=chat。客户端直接按 MD5 校验并读取本地缓存（不要求安装 memes 清单），用受限宽高的图片显示，文件缺失或损坏时显示占位符，不自动下载整包；QQ token 插入与文本表单仍沿用原语义。
最近 QQ 表情与完整 QQ 列表共用正常格子尺寸，不放大；最多显示3行。下载表情仅在目录组中显示与发送，不进入最近，也不恢复旧下载表情最近记录。
动画引擎采用标准 Lottie 数据：Web 使用 lottie-web 5.13.0 的无表达式 SVG light 构建以正确显示可替换字体文字，Flutter 使用 lottie 3.6.1（纯 Dart，支持 Windows/Android）。首次接入播放器需要更新一次 App，之后替换资源包中的 JSON 与图片、刷新资源清单即可改变图层、时间线、遮罩和样式，不再更新 App。播放器不执行下发 JavaScript，不接受 AE 表达式、外部 URL、内嵌图片或外部字体；音频、视频及 AE 的3D碎片/插件滤镜不属于此播放协议，发光、扫光与复杂纹理需要烘焙或用兼容图层近似。MD5 只用于完整性，部署仍须可信 HTTPS。
Lottie 脚本放 resources/animation/scripts/*.json，图片相对 JSON 目录引用，例如 u="images/"、p="title.png"；依赖图必须与脚本一起进入 animation 清单。只对 animation 包增加该 JSON 类型，根目录及任意名为 manifest.json 的文件不作为动画下发，memes 仍仅媒体。工具 tools/update-resource-manifests.py --pack animation 会验证脚本与依赖后生成清单；错误拒绝发布且保留原清单。后端现有资源接口每次现读脚本并校验 MD5；客户端沿用共享 MD5 文件缓存，读取完整已校验脚本后由 AnimationPlayer(resources: ..., scriptPath: ...) 播放，资源管理中可选已下载动画预览。游戏事件只附加表现配置，不改变技能结算、发言计时或任何游戏规则。
早期 Web 预览位于 temp/animation-preview，仅用于最初确认样式；按用户当前要求停止该服务，后续动画效果与验收只以原生客户端为准，不维护 Web 表现一致性。
