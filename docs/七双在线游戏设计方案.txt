七双在线游戏设计方案

一、目标与设计边界

本方案用于制作“魔法裁判·七双”在线游戏，玩法以《七双模式游戏介绍与完整规则.txt》及之后确认的规则为依据。七名玩家各持两张角色牌，一名固定主持人管理对局。确定的规则由程序执行，没有明确规定的情况交给主持人裁决，不再以补齐全部自动裁决规则为开工前提。

本文记录产品、交互及已实现的软件结构，并提供启动说明。前后端应用、角色图片及回归检查均已落地；不沿用 docs/old 中已被后续回复推翻的要求。实际验证范围见第十二节。

本次落实的要求：
- 后端 Python + FastAPI，业务按职责分模块，不使用微服务或通用规则引擎。
- 前端使用 Node.js 工具链，实现手机和电脑浏览器共用的网页。
- 主持人生成本局可重复使用的玩家邀请码和观战邀请码；玩家凭玩家码随机加入空席。
- 玩家掉线后通知本局所有人，包括主持人、玩家和观战者。
- 聊天采用角色头像与消息气泡；允许复制粘贴，不提供可验证的引用消息。
- 不设计反作弊、设备指纹、IP封禁、行为风控、举报审核、竞技排名等系统。
- 保留正常身份验证、房间权限、输入校验和私密信息隔离；这些是游戏正常运行的要求，不是反作弊功能。

首发运行范围：一个服务实例供一名主持人管理一局七双；结束后可新建下一局。保留观战和替补入口。不做13人模式、公开匹配大厅、多个并行对局、语音聊天或独立成就系统。规则提到的“本局禁用成就”只保留局内标记。

二、技术方案与模块边界

1. 技术选择

后端：FastAPI + Uvicorn；Pydantic 校验传输输入；JSON兼容字典保存领域状态，标准库 sqlite3 保存本地数据，secrets 生成邀请码和会话凭证，random.SystemRandom 处理游戏内洗牌与已注明概率的效果。
前端：Node.js + npm + Vite + React + TypeScript；CSS Grid/Flex 实现响应布局；使用浏览器原生 fetch、WebSocket、Canvas。无需 Next.js、SSR、Redux、Socket.IO 或大型组件库。
存储：单个 SQLite 文件。无需 PostgreSQL、Redis、消息队列或 ORM。
部署：前端构建后由 FastAPI 同源提供网页、API 和图片；Node.js 用于前端开发与构建，不再另设一套 Node 游戏后端。Uvicorn 首发只运行一个 worker。
已在 Python 3.14.3、Node.js v24.13.0 环境安装依赖并完成生产构建；源码使用Python 3.14语法，Node.js最低要求22.12.0。依赖分别记录在 backend/requirements.txt、requirements-dev.txt 与 frontend/package-lock.json。

2. 实际目录与职责

backend/app/
  main.py                 创建应用、挂载路由与静态资源；不写游戏规则
  api.py                  HTTP路由、请求校验、命令分发
  schemas.py              传输输入结构；不复制领域规则
  auth.py                 主持人登录、邀请码、会话与权限
  realtime.py             WebSocket连接、在线人数、事件投递
  storage.py              SQLite读写与事务
  views.py                按身份生成可见视图；所有出口共用
  evidence.py             私密文字/画作的校验、保存与访问权限
  game/
    state.py              双牌状态、快照/回溯与共享规则
    catalog.py            14个角色的名称、规则说明、头像、技能标识
    engine.py             命令校验、阶段推进、玩家行动与主持人裁决
    resolution.py         夜间预结算、伤害、换牌、死亡与裁决待办
    actions.py            按身份/阶段生成可用动作及字段；兼作后端输入约束
    views.py              游戏状态的公开、玩家及主持人投影
    __init__.py           领域API导出

frontend/src/
  api.ts                  HTTP请求与错误处理
  live.ts                 实时连接和断线恢复
  types.ts                前端实际使用的协议类型
  state.tsx               一个对局状态入口；不保存第二套游戏真相
  App.tsx                 登录、候场、玩家桌面、主持人桌面、结算页切换
  Chat.tsx                频道、消息气泡与历史记录
  components.tsx          共用角色卡、弹窗与记录展示
  Actions.tsx             统一动作表单、版本冲突重确认
  Drawing.tsx             原生Canvas手绘与图片导入
  styles.css              共用主题、桌面布局、手机布局
  main.tsx                React挂载入口

img/                      复用现有角色图片，不重复拷贝素材

docs/                     保留玩家规则和本设计
checks/                   规则边界与访问撤销回归检查
data/                     运行时SQLite数据；不随源码分发测试对局
setup.cmd                 Windows首次安装依赖并构建前端
start.cmd / run.py        单进程启动入口

依赖方向：页面 → API/实时连接 → FastAPI路由 → 领域函数 → 状态结果；存储和消息推送在领域函数之外完成。
领域模块不得导入 FastAPI、WebSocket 或浏览器类型；实时连接模块不得判断角色技能；前端不得自行判定命中、死亡、魔女化或胜利。角色规则只维护一份，由后端提供目录给前端显示。

不为每个角色建立继承体系，不引入插件注册框架或抽象仓储。按白天、夜晚、触发效果分组的普通函数足够；模块拆分用于隔离职责，而不是增加转发层。

三、身份、邀请码与生命周期

1. 主持人登录

首页提供“主持人登录”和“邀请码加入”两个入口。主持人输入固定密码 114514，后端核对后发放随机会话凭证；不以昵称或前端变量判断管理员身份。
会话用 HttpOnly、SameSite=Lax Cookie 保存；HTTPS部署时启用 Secure。密码不写进前端资源、链接或聊天消息，不设计改密码页面。主持人主动退出后当前会话失效。
固定密码意味着任何知道密码的人都能获得主持人权限和全部对局信息；按用户指定采用这一机制，不额外加入验证码或风控。

2. 本局统一邀请码

玩家邀请码属于本局，不绑定具体席位或角色牌。一个玩家码可供七名玩家在候场阶段重复使用；系统为每次加入随机分配空席，满席后拒绝继续加入。
同一玩家仍可决定两张牌的上下顺序。换牌、下层登场、魔女化和回溯改变游戏角色状态，不改变登录席位，也不要求重新输入邀请码。

创建一局时：
- 主持人确认本局11名魔典角色，系统随机排列；没有明确的魔典名单不由程序臆测。
- 系统先建立7个空席，不在创建时发放角色牌；主持人生成玩家码和观战码。
- 邀请码由随机字符组成，不从角色名、座位号或密码推算；重新生成同类邀请码时旧码失效。
- 七名玩家使用同一个玩家码随机入席。七名玩家首次全部准备后，系统一次性随机分配14张牌到7个席位，每席2张，确保米莉亚与亚里沙不在同一席位。
- 发牌后玩家只能看到自己的两张牌，私下选择上下顺序并再次准备；主持人确认七席都完成第二次准备后才能开局。
- 两轮准备和排序期间，公开席位与聊天均不显示角色头像；玩家自己的牌和明确授权给主持人的信息仍按权限可见。

玩家码只负责候场入席，可被七名玩家重复使用但不能在发牌后重新占据空席。刷新和短暂掉线用已有会话恢复，不重复分席、不重新发牌。发牌后凭证丢失或玩家被移出时，由主持人让观战者使用观战码加入，再指定其接管原空席；接管不重抽角色。
主持人可在发牌前重新生成玩家码、在本局结束前重新生成观战码，同类旧码立即失效，已入场会话不受影响；本局结束时两类邀请码全部失效。邀请二维码不是必需功能，先使用文字码与可复制链接。

本局从创建到结束是一个邀请码有效期：正常结算、主持人终止或新开一局时，所有旧邀请码立即失效，旧玩家/观战会话不再具有对局操作权限。结算页可以保留最后一次获准看到的结果；下一局必须使用新码加入。主持人会话不随一局结束而注销。
对局数据只保留到下一局建立为止：主持人建立新对局时自动清除上一局的邀请码、参与身份与会话、进度、聊天与证物，旧会话被登出后须用新码重新入场。主持人也可在管理面板「一键初始化」随时清空当前对局，效果相同且立即生效，主持人登录保留。
不保留旧“公开房无需凭证/私密房另输密码”的加入方式；统一使用邀请码。

3. 观战与替补

主持人另发观战邀请码，观战不占7个玩家席位，不获得角色牌。观战也需要本局会话，只接收公开信息。
替补由主持人从观战者中选择，并指定一个待接管席位。操作前展示将继承的牌、状态、剩余次数、已提交行动和可见历史，由主持人确认私密信息范围。
接管不重抽角色、不重置技能；继承已提交行动是否保留由主持人裁定。原玩家对该席位的参与身份及全部会话撤销，新的操作者接管原席位，统一邀请码不受影响。公开通知只说明某席位更换操作者，不公开双牌或私密信息。
房内拉黑针对本局参与身份及其全部会话，不声称识别现实中的同一个人；不使用IP或设备指纹。拉黑不撤销共用邀请码；主持人可另行撤销或重新生成同类统一邀请码，其他已入场会话不受影响。

4. 掉线全局通知

“全局”指本局全体在线成员，而不是其他对局或所有访问网站的人。
每个参与身份记录在线连接数；同一人开两个标签页，关闭其中一个不算掉线。最后一条连接正常关闭或心跳判定断开后，状态变为离线，只广播一次“3号玩家【公开称呼】已掉线”。
应用心跳建议每20秒一次，连续60秒未收到响应判定连接失效；正常关闭可立即识别。恢复连接后广播一次“已重新连接”，并重新下发当前获准查看的状态。
掉线不是死亡、弃票、投降或技能放弃，不自动结算。主持人可以等候、按规则警告并在30秒后结束该行动，或邀请替补。状态与已确认行动不因网络断开丢失。
不设计房主转移、选举或自动换主持人；固定主持人的身份和权限不会因浏览器刷新改变。

四、玩家页面与聊天

1. 页面清单

入口页：游戏名称、简短玩法、邀请码输入、主持人登录。
候场页：7个席位与准备情况、自己的双角色卡、上下交换按钮、公开称呼/示人头像、准备按钮；主持人另见邀请码和魔典设置。准备进度只公布已准备人数，玩家看不到具体谁已准备（会发现上层牌锁定时机）；主持人仍看得到每个席位的准备状态。
玩家桌面：顶部日夜与阶段，中部公开席位/聊天，自己的角色与私密信息，当前可操作的行动面板。
主持人桌面：相同公开桌面，加全量角色状态、所有行动、裁决待办、魔典、13水、投票、阶段推进、替补管理。
结算页：获胜方、特殊胜负、主持人裁定说明；是否公开全部身份和历史由主持人决定，不默认披露全部私聊。

2. 头像与身份不混用

登录席位、真实角色牌、公开示人身份是三个不同概念。
自己的角色卡和主持人私密面板使用真实角色头像。公开聊天只使用已公开或依规则示人的角色头像；不因为后台换牌、魔女化或下层仍隐藏，就自动向其他人换成真实头像。
尚无公开角色时使用中性的座位号头像，不借某张角色图暗示其真实身份。穗乃香示人后可使用被示人角色的图，但这不授予其真实技能；示人只改变公开头像本身，系统不向全场广播“某号示人为某角色”，该记录只给主持人。主持人始终使用 img/月代雪.png。
旧聊天消息保存当时的公开称呼和头像；换牌或回溯不把旧消息重新渲染成现在的秘密身份。

3. 聊天交互

他人消息：左侧头像 + 公开称呼/座位号 + 左对齐气泡。
自己消息：右对齐气泡，可显示自己的公开头像。
主持人公告、阶段变化、掉线/重连通知：居中系统消息，不伪装成玩家发言。
顶部始终显示当前频道名称；私密频道使用醒目标识，发送前能看清接收范围。

默认频道是公聊和玩家与主持人的私聊。其他私聊、死者频道、观战讨论或角色授予的查看权限，由主持人在本局明确开启；不因为属于魔女就默认获得规则未写出的魔女群聊。
主持人可查看全部游戏频道。玩家只能接收允许自己查看的消息；观战只见公开频道。规则限制发言时输入区说明原因，不靠颜色表达状态。

允许复制粘贴普通文本，不提供回复引用、跳转到来源消息、来源认证徽标或跨频道原消息卡片。粘贴内容一律是发送者自己的一条文字气泡，不带可验证的来源。玩家当然仍可自行转述真假信息。
不提供防截图、防复制、语音、录屏检测或外部聊天监控。文本按文本渲染，不执行HTML；消息长度上限建议2000字，属于正常输入边界。

桌面 Enter 发送、Shift+Enter 换行；手机用明确的发送按钮。发送后清空输入只发生在收到成功确认时；失败保留草稿，不自动重发成多条消息。
聊天按需加载较早记录，新增消息不在用户向上阅读时强制拉到底部；显示“新消息”入口。

4. 手机与电脑布局

桌面宽度 ≥1024px：三栏，左侧约220px席位列表，中间弹性聊天/公共桌面，右侧约320px自己的牌与行动。主持人的右栏改为裁决面板，可展开全量角色表。
平板768—1023px：双栏，聊天保留主区域，角色和裁决在侧抽屉中切换。
手机 <768px：单栏，底部“聊天 / 桌面 / 我的牌 / 行动”；主持人对应“聊天 / 桌面 / 裁决 / 管理”。重要待办用数量提示，不把桌面三栏强行缩小。

移动端使用动态视口高度和安全区边距；软键盘出现时输入框和发送按钮仍可见。正文/输入不小于16px，操作区域至少44px；普通页面不横向滚动，双牌在窄屏纵向展示。
目标选择、投票、13水使用和主持人死亡确认显示角色/座位、效果与提交按钮，防止触屏误点。确认属于正常操作交互，不增加身份认证步骤。
焦点可见、按钮有文字、头像有替代描述、日夜/死亡/离线均有文字标识。动效轻量，支持减少动态效果；不使用大规模特效或自动播放音乐。

5. 视觉基调

深紫灰底色、浅色正文，紫色用于阶段和行动，暖金用于主持人提示，红色只用于死亡/不可逆确认。角色卡使用现有PNG立绘；聊天头像统一圆形裁切，点击后查看该公开身份的角色说明。
手机优先保留聊天和本阶段行动，不让装饰立绘挤占输入区。候场和规则页可以展示完整角色图；穗乃香缺图时用“穗”字标识，不借用主持人的月代雪图片。

六、七双对局与裁决流程

1. 对局主线

建局建立空席 → 发放共用玩家码和观战码 → 七名玩家入场并首次准备 → 系统私下发放14张牌 → 玩家调整上下牌并第二次准备 → 主持人开局 → 魔女化 → 夜间行动 → 夜间结果与证物 → 主持人安排的顺序发言 → 自由发言 → 热气球 → 提名/投票/处决 → 天黑，循环直到主持人确认结局。
魔女化按已随机排列的魔典找第一个合法目标：存活、尚未魔女化、当前在上层，且另一张不是原始米莉亚或亚里沙。法典耗尽、没有合法目标或其他规则未定情况交主持人处理，不能把整场目标顺序每天重新洗牌。
每个阶段展示“当前谁需要做什么”。玩家主动确认后提交；可放弃的行动有“放弃并确认”，不以断线代替放弃。主持人只对已警告玩家启动30秒倒计时；到期按未操作处理。倒计时用截止时间，刷新不会重新获得30秒。
需要人工结论的地方显示待办并等待主持人，不随机猜一个结果，不用“默认无事发生”跳过未决效果。

2. 夜间行动与死亡前预结算

第一步：收集其他玩家的夜间选择及放弃确认。诺亚在完成作画/放弃前，不通过消息、按钮消失或死亡图标获知自己本夜是否死亡。
第二步：若魔女可可在本夜可行动，将其他人已确认的夜间行动提供给可可，再允许可可最后提交。普通可可仅在照片受赠者明确授权后看到对应行动。
第三步：固定本夜已提交意图、已注明概率的抽签结果、主持人已裁定的随机结果，再预结算伤害、庇护和负伤。夜间死亡不抹去该玩家当晚已正常提交的行动。
第四步：只有伤害处理后仍会死亡，才检查米莉亚换牌或希罗回溯。米莉亚先按不交换预结算，确认会死才交换并重新结算；已被庇护救下就不消耗换牌。希罗同样只在不回溯就会死亡时触发。
第五步：在同一份预结算中重复检查受影响的结果，但不因重算重复消耗子弹、技能次数、13水或重新抽命中概率。出现规则未说明的互相触发时转为主持人待办，不无限自动重算。
第六步：主持人审阅最终结果、复活/傀儡及相关连锁，确认后一次发布允许公开的死亡和证物信息。未揭晓的死亡不先推送给玩家再尝试撤回。

蕾雅注视先限制合法目标，再满足“疯狂使人出局”的攻击要求；不能为了疯狂而选择注视范围之外的目标。疯狂程度和规则未定的冲突仍由主持人判断，不分析聊天或自动判定玩家是否努力。

3. 双牌与回溯

席位下保存两张实际角色牌，牌有自己的持有人、层次、生死、魔女化、伤势和技能使用状态；不能只给玩家一个“死/活”字段。
一张牌出局后才能使用下层牌；同一玩家同一半天最多出局一张牌。目标究竟跟随人还是跟随被交换的牌、下层在本阶段的可行动时机等无明确说明的情况，生成具体裁决项让主持人处理。

希罗回溯记录好人与魔女两次独立额度，各最多一次；额度已用不会被自己的回溯恢复。魔女回溯保留自己的魔女化。
恢复前一天对应游戏时间点的牌、普通技能次数与其他可回溯游戏状态；玩家的记忆及已收到的聊天/线索记录不删除。雪莉对汉娜的绑定、安安大招负面效果等精神系效果单独保留，不被快照覆盖。
回溯不恢复旧邀请码、被撤销的会话、旧操作者或网络连接；这些不是游戏时间。没有对应时间点或特殊效果归属不明时，展示可选快照及差异，由主持人裁定目标和保留项。
回溯后公开标记“游戏时间已回溯”，真实时间顺序的聊天继续保留；不把已发生消息伪造成从未发生。

4. 投票、死亡批次与胜负

主持人确定提名顺序和本轮候选，对每名候选单独收集同意/不同意/弃票，直到主持人确认整轮完成。其他未定投票细节以主持人本局宣布为准。
每次计票的分母 N 是当时拥有投票权的存活玩家数；强制弃票者仍计入，失去投票权者与不能投票的傀儡不计入。通过门槛为 floor(N/2)+1。不要用实际投票人数替代分母。
所有严格过半候选一起进入本轮处决结果；奈乃香临刑开枪等效果先处理，不在第一名候选处决后提前截断其他已通过处决。
每次死亡检查胜负并形成候选结论。同一半天的多人出局按严格同时处理，主持人确认相关结果齐全后才正式宣判，不按网络消息到达顺序抢先封局。双方同时满足时白好黑魔。
热气球达到规则要求的即时胜利单独检查；安安、雪莉、质疑失败者等特殊个人结局由角色状态合并计算。交牌不简化为任何一人点击即可结束，照玩家规则收集条件和主持人确认。
若尚未生成魔女或仍有后续转化问题，不把“当前存活魔女数为零”直接等同于好人已经完成胜利条件；结合本局魔典交由主持人确认，避免空集合判断导致开局自动获胜。

5. 热气球、13水与信息

热气球面板显示当日组织者、至多4名参与者、公共进度；制作/破坏选择私密提交。只有满足身份条件者可选破坏；任一破坏清零，否则每次制作加1。到13时按亚里沙在场、存活魔女等条件检查胜利，安安强制落败。
13水由主持人私下发放，全局只保留一瓶的持有/使用状态；玩家私密行动栏显示拥有的13水。使用由主持人处理时机和互动，不把持有者广播出去。13水死亡通常单列死因，魔女梅露露隐藏死因的明确例外仍保留。
三人疑似凶手名单由主持人编辑：正常包含真凶，其余指定；汉娜、诺亚、蕾雅、穗乃香等影响名单的技能先提示主持人。名单只发给对应死者，之后才按规则公开证物。
照片、证物和画作都是可指定可见对象的信息项，不混入公共状态。诺亚作画提供轻量Canvas画板和保存/放弃按钮；可附文字，不引入绘图框架。照片及主持人提供的其他材料由主持人确定内容，不能用临时任意字符串冒充已经定义好的技能结果。

6. 主持人工作台

优先呈现本阶段待处理事项，而不是要求主持人去编辑一大段原始数据：
- 看全员双牌、上下层、生死、阵营、伤势、剩余技能次数和在线状态。
- 看魔典、转化候选、夜间意图、概率结果与预结算变化。夜间阶段在主持人操作面板列出每个席位当夜的角色牌、已提交的技能与目标、尚未提交者，玩家之间不共享这些信息，主持人可据此主持。
- 对“可能”、中毒信息、疯狂、证物和未知互动选择结果与接收者。
- 发13水、排发言顺序、警告并计时、开闭投票、确认处决与胜负。
- 处理穗乃香声明/质疑、替补继承、复活、回溯和规则允许的特殊操作。
- 需要纠错时调整指定对象的游戏状态，附裁定说明；同时预览哪些变化公开、哪些只给当事人。

已经明确的概率由系统抽取，默认不要求主持人人工掷骰；没有明确概率才由主持人决定。主持人的裁决记录属于本局游戏记录，不另做审计平台或管理员监控系统。
公开操作必须清楚列出目标和将发布的内容。私密裁定不能仅因为点击了“下一阶段”就自动变成全员公告。

七、十四个角色的操作入口

以下是实现覆盖清单，完整规则文本仍从同一个角色目录提供。每项均包含真实角色能力、魔女化后的变化和主持人的裁决入口，不只做选牌而把角色技能留空。

艾玛：打断发言、排到最后；记录每日次数。魔女第三天起的全场攻击纳入夜间意图及统一死亡结算。
希罗：死亡前触发、好人/魔女独立回溯额度、主动出局声明、精神系保留与魔女化保留；记录疯狂目标及允许例外的一夜。
汉娜：疑似凶手名单固定包含的提醒；魔女一次额外攻击及使用状态。
雪莉：追踪她与汉娜作为上层牌共同经过的完整白天。达成前只有不能魔女化；绑定后的投票、殉情、胜负、魔典移位及回溯保留均有记录。
梅露露：每晚庇护目标、伤害转负伤；魔女当日所杀者复活为无投票权傀儡的一次能力、主人关系、13水隐藏死因。
诺亚：每晚画作或放弃、公开死亡前的信息屏蔽、死后选择已画作品作证物；魔女一次替代凶手名单目标。
安安：秘密强制弃票；魔女全场洗脑目标、次日无投票权并必须被处刑的持续负面状态；玛格学习/抵消洗脑联动。
米莉亚：每夜预选交换对象、临死预结算、换上层牌及一次额度。登录席位与卡牌交换互不影响。
可可：送照片及受赠者查看夜间行动授权；魔女可见魔典/艾玛魔女化信息并在其他行动锁定后最后行动。
奈乃香：6发子弹、夜间或临刑射击、普通1/6和魔女1/3命中、幻视信息与魔女每夜状态信息。白天公开规则要求的射击概率信息，其他信息不随之公开。
亚里沙：禁止魔女化、组织和起飞热气球；不在场时主持人处理好人的组织投票。
玛格：白天爱上/移情及疯狂目标；整局两次夜间解典与猜对数量；魔女学习洗脑和同时洗脑互相抵消。
蕾雅：白天注视对象、夜间硬性目标范围、疯狂引人注目的主持人裁定；魔女1/2长矛和可能不入名单。
穗乃香：开局获知上层牌、公开示人身份、魔女修改名单显示；白天伪装技能与质疑必须走统一声明流程，不提前向公众标出真假。

伪装特别要求：真实白天技能和伪装技能在公共桌面上使用相同的声明样式。质疑由主持人结算，成功则停止未完成部分，已执行部分不撤销；失败者出局并个人判负。不能允许通过按钮样式、公共事件类型或错误提示证明技能真假。

八、状态、保存与实时通信

1. 必要状态

Game：本局ID、状态版本、日数、白天/夜晚标识、阶段、发言顺序、截止时间、魔典、热气球、13水、待办裁决与胜负候选。
Seat：稳定座位号、当前操作者、公开称呼/示人身份、双牌引用、准备状态、投票资格；在线连接另行维护。
RoleCard：唯一牌ID、角色种类、原始牌身份、当前持有人及上下层、生死、魔女化、状态和次数。原始身份不能因交换而丢失。
Action：提交者席位、使用的牌、技能/目标、提交阶段与版本、是否确认、已抽定结果和处理状态。
Information：照片/画作/名单/证物/私密提示，发送时的获准接收者与内容。
PersistentEffect：不能随希罗回溯消失的绑定、处罚、回溯消耗及其他主持人明确保留的效果。
Snapshot：游戏内时间点、对应牌与技能状态；不包含邀请码、连接、历史聊天或可回溯的鉴权数据。

2. SQLite保存范围

已使用七张表：games（完整领域状态、快照、版本）、participants（参与身份及历史权限）、sessions（会话）、invites（本局统一码、种类与有效状态）、channels（私密频道成员）、messages（聊天、信息、通知及接收范围）、evidence（文字、图片及归属）。领域快照存在 games.state 内，不另建事件重放或快照数据库。
角色素材继续读现有img目录；玩家画作作为SQLite BLOB保存于evidence表，按身份检查权限，不能通过公开静态素材路径访问。
游戏命令先在本局锁内校验与计算，事务保存状态及产生的消息，再推送；保存失败则不发布成功结果。小规模对局不需要分布式锁。
提供启动时读回当前状态，避免刷新或服务重启重新发牌；不承诺服务中断自动托管，也不增加房主故障转移方案。

3. 可见视图

玩家/观战响应从公开字段出发，按获准信息补充；不要先把主持人全量状态发给浏览器再用CSS隐藏。HTTP、WebSocket、消息历史、附件访问与重连恢复共用同一可见性规则。
主持人视图含全部游戏信息。玩家视图含自身双牌及合法获得的信息。观战视图仅含公开信息。替补增加历史权限必须由主持人明确决定，不默认获得其他人的私聊。
过往消息保留发送时的接收者，后来的换牌不会自动解锁另一席位的历史信息。

4. 更新方式

HTTP承接登录、加入、游戏命令与聊天提交；WebSocket只负责实时状态、消息和在线通知，不维护另一套技能协议。
游戏命令携带 expected_version；旧版本请求返回409，客户端重新取得可见状态并要求确认，不重复执行。客户端不会自动重试扣子弹、投票、发13水等有状态命令；超时先取状态确认结果。聊天另有自己的发送确认，不因游戏版本变动拒收正常发言。
WebSocket使用 sync、state、message、ping 消息，客户端回复pong。持久消息有递增id，消息kind区分聊天、私密信息、在线通知等；对局结束随state同步。所有内容按接收权限生成，不做复杂增量补丁。
连接建立时在同一同步边界注册订阅并取得快照与最近一页获准消息，然后投递后续更新，避免初始化窗口漏消息。重连后重新同步状态，按after游标补充获准历史，客户端按消息id去重。
纯在线状态和聊天不抬高游戏命令版本，避免正常发言让别人选好的夜间行动无故失效。

九、HTTP与实时接口约定

以下接口均已实现。登录身份来自会话，不接受客户端自行指定“我是主持人”或以role_id代替身份。

GET  /api/health                        服务健康状态
POST /api/host/login                    password；正确值114514；设置主持人Cookie
POST /api/logout                        撤销当前会话
GET  /api/me                            当前身份、本局和席位；不返回别人的牌
GET  /api/catalog                       公共角色规则、头像地址与展示信息
POST /api/games                         主持人创建一局并确认魔典名单，系统建立7个空席
POST /api/games/{game_id}/invites        主持人为玩家或观战生成本局可重复使用的邀请码
GET  /api/games/{game_id}/state          按当前会话返回可见状态
POST /api/games/{game_id}/commands       expected_version、action、payload
POST /api/games/{game_id}/messages       channel_id、text；返回发送成功的消息
GET  /api/games/{game_id}/messages        按游标分页读取获准记录
POST /api/games/{game_id}/evidence       提交文本材料或画作；由规则决定谁能看
GET  /api/games/{game_id}/evidence/{id}  检查权限后返回材料或图片
WS   /api/live                          用Cookie建立连接，接收事件并回复心跳

commands统一使用 expected_version、action、payload 信封；房间管理输入由Pydantic校验，游戏动作由后端动作描述和领域函数逐项校验权限、字段、阶段、次数与目标。不接受任意JSON覆盖整个游戏状态。room.kick使用participant_id和block，既可移出玩家也可移出观战者；替补仍使用seat_id与participant_id。
玩家动作涵盖：选上下牌、准备、确认/放弃夜间行动、白天技能声明、质疑、提名、投票、制作/破坏、信息授权、证物公布、13水使用、交牌请求。
主持人动作涵盖：开局、排发言顺序、警告、结束超时行动、推进阶段、裁决、确认结算、发放13水、投票控制、纠错、替补、踢人/房内拉黑、结束对局。
常见失败区分：未登录、无权限、邀请码失效、目标席位已被占用、阶段已结束、状态已变化、输入不合法。错误文本不向无权者透露真实牌面、私密目标或技能真假。
画作上传仅接受2MB以内、最大边长4096的PNG/JPEG，后端生成随机证物ID；不执行上传内容，也不接受客户端指定任意磁盘路径。角色立绘是公开静态素材，与私密画作分开。

十、开发与交付顺序

按完整可运行的纵向功能推进，不先铺满空文件或留“稍后实现”的角色按钮：
1. 完成主持人登录 → 新建空席局 → 发共用码 → 七人随机入场/首次准备 → 发牌/私下排序/再次准备 → 主持人开局；验证旧码失效和刷新恢复。
2. 接上真实聊天、头像、消息权限、WebSocket掉线公告、手机/电脑桌面和观战替补。
3. 接上主持人阶段推进、确定概率、技能输入/信息、预结算、投票、热气球、13水与结局，覆盖14角色。
4. 处理回溯、精神系保留、同时死亡、伪装/质疑、替补历史，完成全程七双联机验收。

前端开发服务器通过 frontend/vite.config.ts 代理访问本机8000端口的FastAPI；正式使用时同源服务，避免多余的跨域和多后端部署。npm ci按锁文件安装开发与构建依赖。
后端规则检查只保留能防住真实错误的少量回归用例；不要为每个转发函数写测试。浏览器体验以实际手机/桌面视口操作和真实服务联机为准，不用截图假页面替代。

十一、验收标准（实际验证范围见第十二节）

A. 114514可进入主持人入口，其他密码失败；玩家改昵称或提交host字段不能获得主持人权限。
B. 七名玩家首次准备后随机分出14张不重复的牌，7席各2张，米莉亚与亚里沙不在同一席；玩家能私下排上下牌，别人看不到下层牌；主持人能看到全部。
C. 玩家邀请码在发牌前可供七人共用但不能超过七席；重新生成或撤销同类邀请码只使该类旧码失效，踢出/拉黑只撤销对应参与身份及全部会话，本局结束后旧码不能入场且旧会话不可操作。刷新恢复原席位，换牌不换登录；发牌后的空席只能由观战者接管且不重发牌。

十二、运行与交付

已提供可运行的七双前后端；玩家规则仍是游戏说明，本文件记录软件结构和运行方式，二者不互相替代。

1. Windows启动
首次安装：双击项目根目录 setup.cmd，或在终端运行 .\setup.cmd。它创建.venv、安装后端依赖、执行npm ci并构建前端。安装期间需要访问Python/npm包源。
日常启动：双击 start.cmd，或在终端运行 .\start.cmd。服务日志出现“Uvicorn running”后，在电脑浏览器打开 http://localhost:8000；主持人选择管理入口，密码114514。
手机加入：与电脑连接同一局域网，打开 http://电脑局域网IPv4:8000，再填写主持人发来的邀请码。IPv4可在电脑上运行ipconfig查看；手机不能使用localhost。若Windows防火墙提示，只按实际需要允许专用网络访问8000端口。
更换端口：.\start.cmd --port 8001；只允许本机访问：.\start.cmd --host 127.0.0.1。默认绑定0.0.0.0，必须保持单个worker；按Ctrl+C停止服务。
固定主持人密码是已确认要求，不适合把服务直接暴露到不可信公网；本版本不包含公网域名、TLS证书或外网穿透配置。

2. 开局与日常操作
主持人新建对局时确认11角色魔典名单，系统随机排序并发出14张双牌；在管理面板为7席分别生成邀请码。玩家输入昵称与本局码，选择上下牌并准备，7人准备后由主持人开局。
按页面提示确认行动，由主持人推进阶段、处理“可能”与未定规则待办。观战码用于只读入场；主持人可让观战者接管席位，并分别决定是否继承私密历史及保留原行动。
移出/本局拉黑对玩家与观战者均有效；只撤销该参与身份和相关凭证，不重置角色牌。没有设备识别或IP封禁，新发给他人的码代表新的获准参与身份。
手机使用底部导航切换聊天、桌面、双牌/管理及行动；聊天可复制粘贴，画作可手绘或导入PNG/JPEG。

3. 保存与开发
默认数据库为 data/seven-double.sqlite3，首次启动自动创建。刷新或服务重启会恢复原局；不要在进行中的对局删除数据库。备份前先停止服务，再复制整个data目录。
可用环境变量GAME_DATA_DIR指定独立数据目录，联调曾使用data/verification，交付时清除此测试目录。退出浏览器不会结束对局；须由主持人结算或终止当前局后才能创建下一局。
对局结束后数据仍可只读查看，直到建立下一局为止：建立新对局会自动清除上一局全部数据（含结算与聊天），主持人也可在管理面板点「一键初始化」立即清空；两种方式都保留主持人登录，玩家与观战者须用新邀请码重新入场。
前端开发：保持后端8000端口运行，在frontend目录执行npm run dev；正式使用前执行npm run build。开发服务器不是第二套游戏后端。
检查依赖：.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
规则/访问检查：.venv\Scripts\python.exe -m unittest discover -s checks -v
Python静态检查：.venv\Scripts\python.exe -m ruff check backend checks run.py
生产构建：在frontend目录执行npm run build（包括TypeScript检查）。
